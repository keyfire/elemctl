# Спецификация elemctl

[English](SPEC.md) · **Русский**

Документ описывает контракт Console API v2 платформы 1С:Предприятие.Элемент
(1cmycloud.com), формат файлов сборки и требования к инструменту elemctl.
Здесь только факты об интерфейсе платформы и требования к продукту:
реализация проектируется с нуля.

## 1. Назначение и состав пакета

Python-пакет `elemctl` состоит из трёх слоёв поверх общего ядра:

1. **Библиотека** - программный клиент Console API v2 и операции высокого
   уровня: сборка и развёртывание. Только стандартная библиотека Python.
2. **CLI** - консольная команда `elemctl`, точка входа `elemctl` в
   `[project.scripts]`.
3. **MCP-сервер** - те же операции в виде инструментов для AI-агентов, транспорт
   stdio. Зависимость `mcp>=1.2,<3` подключается необязательным extra
   `elemctl[mcp]`. Берётся эргономичный класс сервера пакета `mcp`: `FastMCP` в
   mcp 1.x, `MCPServer` в mcp 2.x.

Требования пакета: имя `elemctl`, версия 0.1.0, Python >= 3.10, лицензия MIT,
автор KeyFire, layout `src/elemctl/`, extra `dev` с pytest. Файлы LICENSE,
README.md, .env.example и .gitignore заданы и не меняются.

## 2. Конфигурация подключения

Параметры берутся из трёх источников, по убыванию приоритета:

1. явные аргументы (флаги CLI `--base-url`, `--client-id`, `--client-secret`);
2. переменные окружения;
3. .env-файл: путь из флага `--env-file`, а без него - файл `.env` в текущем
   каталоге, если существует.

Переменные окружения:

| Переменная | Смысл | Обязательна |
|---|---|---|
| `ELEMENT_BASE_URL` | базовый URL платформы с `http://` или `https://`, например `https://1cmycloud.com` | да |
| `ELEMENT_CLIENT_ID` | Client-Id для получения токена | да |
| `ELEMENT_CLIENT_SECRET` | Client-Secret | да |
| `ELEMENT_APP_ID` | приложение по умолчанию | нет |
| `ELEMENT_PROJECT_ID` | проект по умолчанию | нет |
| `ELEMENT_SPACE_ID` | пространство по умолчанию | нет |
| `ELEMENT_CA_FILE` | дополнительный PEM-файл CA для частного облака | нет |
| `ELEMENT_TLS_STRICT` | строгая проверка сертификатов по RFC 5280; по умолчанию `true` | нет |
| `ELEMENT_TLS_VERIFY` | проверка сертификата и имени сервера; по умолчанию `true` | нет |

Формат .env: строки `KEY=VALUE`. Пустые строки и строки, начинающиеся с `#`,
пропускаются. Перед именем допускается префикс `export `, а значение можно взять
в одинарные или двойные кавычки. Кодировка UTF-8, возможен BOM, поэтому читать
надо как `utf-8-sig`. Хвостовой слэш у `ELEMENT_BASE_URL` обрезается. Непустой базовый URL
должен начинаться с `http://` или `https://`.

## 3. Аутентификация

Получение токена: `POST {base}/console/sys/token`

- заголовок `Authorization: Basic base64(client_id:client_secret)`;
- тело `grant_type=client_credentials`, Content-Type
  `application/x-www-form-urlencoded`.

Ответ - JSON-объект, а токен лежит в первом непустом из полей `id_token`,
`token`, `value`, `access_token`. Особый случай: значение `access_token` бывает
строкой `"Not implemented"`. Это не токен, поле надо пропустить.

Все прочие запросы - с заголовком `Authorization: Bearer {токен}`.

Токен живёт около часа. Кешировать его надо в файле в системном каталоге
временных файлов, который даёт `tempfile.gettempdir()`, а не в жёстко прописанном
`/tmp`: инструмент работает и на Windows. Время жизни кеша - час, а ключ кеша
обязан различать пары base_url и client_id. На ответ 401 токен обновляют
принудительно и повторяют запрос один раз.

## 4. Контракт Console API v2

Общий префикс: `{base}/console/api/v2`. Тела запросов и ответов – JSON, кроме
загрузки сборки. Имена полей пишутся в kebab-case.

Новый справочник консоли называет основной версией Console API 2.1 с префиксом
`{base}/console/api/v2.1`, а версия 2.0 лежит рядом и работает. Клиент остается на 2.0 и
обращается к 2.1 только за тем, чего в 2.0 нет: за расширениями, примененными в приложении
(п. 4.1). На путь, для которого у консоли нет обработчика, она отвечает 401, а не 404, с
текстом `Handler of HTTP request "[<метод>] <путь>" in application "console" not found.` –
так сервер старше метода от него и отказывается. Такой 401 к токену отношения не имеет, и
новый токен получает тот же ответ, поэтому клиент читает текст ответа до обновления токена:
ответ назван методом, которого сервер не знает, а новый токен не запрашивается. Любой другой
401 обновляет токен и повторяет запрос один раз.

### 4.1. Приложения

- `GET /applications` - список. Query-параметр `name` у метода есть, но платформа его игнорирует и возвращает полный список. Это проверено живым вызовом, поэтому по имени фильтрует клиент.
- `GET /applications/{id}` - карточка. Значимые поля ответа: `id`, `status`,
  `uri` (адрес работающего приложения), `error` (текст ошибки, если есть),
  `technology-version`, `date-updated`, `display-name`,
  `publication-context`, `source` (объект с информацией об источнике,
  содержит в т.ч. `project-version` - версию применённой сборки).
- `POST /applications` - создать. Тело:
  - `source` - объект `{"type": "repository"}` плюс ровно один из ключей:
    `project-version-id` (id сборки-источника) либо `image-id` (id проекта);
  - `display-name`, `publication-context` - имя и путь публикации;
  - `development-mode` - булево, создавать ли среду разработки;
  - необязательные `space-id`, `technology-version`.
- `DELETE /applications/{id}` - удалить.
- `PUT /applications/{id}/status/start` - запустить.
- `PUT /applications/{id}/status/stop` - остановить.
- `POST /applications/{id}/actions/debug` - данные для сессии отладки
  (`ApplicationDebugInfo`: `{"debug-token": ..., "debug-address": ...}`).
  Тело запроса пустое; требует включённой отладки на сервере
  (`config/debug.yml` `enabled: true`).
- `POST /applications/{id}/project/update` - применить сборку к приложению.
  Тело: `{"source": {"type": "repository", "image-id": "<id сборки>"}}`
  либо `{"source": {"type": "repository", "project-id": "<id>",
  "assembly-version": "<версия>"}}` (assembly-version необязательна).
- `POST /applications/{id}/project/export` – сборка, на которой работает приложение.
  Справочник описывает метод в 2.0 и в 2.1, живая проверка получила из обоих один и тот же
  архив. Тело запроса пустое, а ответ – сам архив, `application/octet-stream` без
  `Content-Disposition`: файлы сборки, среди них `Assembly.yaml`, упакованные заново, с
  отдельными записями для каталогов. Консоль берет архив у сервера приложения, так что это
  проект, который приложение исполняет. Расширений, примененных в приложении, в архиве нет:
  для них есть свой метод (методы 2.1 ниже). По исходникам консоли выгрузка приложения
  посреди обновления или после неудачного обновления отвечает сборкой, загруженной для
  этого обновления, и проверка на живом сервере во время обновления получила именно ее.
  Манифест – тот, который сервер хранит для сборки: сборка, загруженная в проект,
  возвращается с номером, который дал ей сервер (п. 4.4), и временем загрузки в
  `Created`, а сборка, которая завела свой проект, – с манифестом своего архива.
  Обработчик 2.1 принимает и недокументированный параметр запроса `extension-id` и тогда
  отвечает сборкой этого расширения, как
  `/v2.1/applications/{id}/project/{ExtensionId}/export`; 2.0 параметр не читает.
  Контроллер пускает любого пользователя, прошедшего проверку подлинности, и читает
  приложение с правами этого пользователя.
- `POST /applications/{id}/dumps` - создать дамп. Тело: `include-users`,
  `include-binary-data` (булевы), `description` (строка).
- `GET /applications/{id}/dumps/{dumpId}` - статус дампа.
- `GET /applications/{id}/users` – пользователи, подключённые к приложению, каждый
  `{user-list-id, user-id, presentation, is-admin, token-access-enabled}`. Среди них и
  пользователи панели управления: их платформа подключает сама и называет такого
  пользователя по логину. `token-access-enabled` – доступ пользователя к HTTP-сервисам
  приложения по токену. Без него вызов сервиса токеном этого пользователя получает 500
  "Token access is denied", какие бы права у пользователя ни были.
- `PUT /applications/{id}/users/change-token-access` – переключить этот доступ. Тело:
  `{"user-list-id", "user-id", "enable-access"}`, все три обязательны; ответ – подключение
  в том виде, в каком оно стало. Пользователю, не подключённому к приложению, сервер
  отказывает ответом 500 "Can't change user token access" и причины не называет, поэтому
  клиент сначала находит подключение, а если его нет, называет пользователя сам.
  Справочник описывает метод и в v2, и в v2.1 с одинаковым телом, живая проверка получила
  от обоих одинаковый ответ; клиент берёт префикс v2, как и во всех остальных запросах.
- `GET /me` – пользователь, которому принадлежат реквизиты: `id`, `login`, `presentation`,
  `user-list-id`.
- `GET /v2.1/applications/{id}/project` – проекты, которые работают в приложении:
  `application-project` и примененные расширения в `extension-projects`. У расширения
  есть `id`, `project-id`, `assembly-id`, `enabled`, `order`, `vendor-name`,
  `project-name`, `project-presentation`, `project-version` и `assembly-version`. `id` –
  ид расширения на сервере приложения: `Ид` из `Проект.yaml` расширения, тот
  `configuration-id`, которым ответила его загрузка (п. 4.4). В `assembly-id` расширения
  консоль кладет ид его проекта, и живая проверка с исходниками консоли в этом сходятся,
  так что сборку это поле не называет. Тот же путь в 2.0 отвечает одним проектом
  приложения.
- `POST /v2.1/applications/{id}/project/{ExtensionId}/export` – сборка примененного
  расширения. Тела у запроса нет, ответ – сам архив, `application/octet-stream` без
  `Content-Disposition`: файлы, с которыми сборку загрузили, `Assembly.yaml` в их числе,
  упакованные заново. Сегмент пути – `id` расширения из предыдущего метода, регистр букв
  не важен. Справочник называет параметр идентификатором проекта расширения, но на
  `project-id` сервер отвечает тем же голым 500 "Unable to export extension ... from
  application ...", что и на неизвестное значение, с "Contact administrator for details"
  в `details`. Остановленное приложение отдает сборку так же, удаленное получает 404 уже
  на перечне. В 2.0 такого метода нет: `/v2/...` получает 401 отсутствующего обработчика.
  Контроллер консоли пускает любого вошедшего пользователя (`PermitAuthenticated`) и
  читает приложение с правами этого пользователя.

Статусы приложения: стабильные `Running`, `Stopped`, `Error`; переходные
`Starting`, `Stopping`, `Initializing`, `Updating`, `Frozen`, `Creating`,
`Deleting`. Во время переходов поле `status` может быть и пустым. Справочник
описывает `status` простой строкой и значений не перечисляет, поэтому перечень
собран по живым проверкам. `Deleting` держится, пока идёт задача
`DeleteApplication`, а потом приложение остаётся в перечне со статусом
`Deleted` (п. 6.9). `UNKNOWN` заглавными встречен у приложения, у которого
пропали файлы базы: его нельзя было ни запустить, ни удалить – удаление
начинается с выгрузки данных. Этот статус консоль дает состоянию приложения
на сервере, которому у нее нет имени, поэтому ничто не говорит, что он
окончательный, и клиент не считает его ни стабильным, ни переходным:
ожидание статуса терпит `UNKNOWN` минуту подряд, потом останавливается и
называет статус, а не ждет до конца всего срока.

### 4.2. Версия технологии

- Чтение - из поля `technology-version` карточки приложения (отдельный
  endpoint чтения есть не во всех версиях платформы - не использовать).
- Обновление: `POST /tasks/group-tasks/update-applications-technology`,
  тело `{"technology-version": "<версия>", "applications": ["<app-id>"]}`.
  Возвращает групповую задачу; её статус - `GET /tasks/group-tasks/{taskId}`.

### 4.3. Пространства и проекты

- `GET /spaces` - список пространств.
- `GET /projects` - список проектов; `GET /projects/{id}` - карточка;
  `DELETE /projects/{id}` - удаление. Перечень отдаётся целиком, каким бы ни был
  query, а удалённые проекты остаются в нём с признаком `deleted` и прежним ид.
  Отбор по имени и скрытие удалённых - работа клиента, как и у приложений (п. 4.1).
  Статуса у карточки проекта нет вовсе: о состоянии проекта говорит только
  признак `deleted`.

### 4.4. Сборки проекта (assemblies)

- Загрузка файла сборки - бинарный POST (Content-Type
  `application/octet-stream`, тело - байты файла):
  - `POST /projects/{id}/assemblies` - добавить сборку в существующий проект;
  - `POST /projects` - создать новый проект из сборки либо добавить сборку в
    проект, которому уже принадлежат поставщик и имя манифеста;
  - `POST /spaces/{space-id}/projects` - то же, но новый проект заводится в
    этом пространстве.
  Пространство загрузки в проект уходит необязательным query-параметром
  `space-id`, так, как его пишет справочник. Живая проверка показала, что сервер
  его читает: ид, который не UUID, отклоняет ответом 400, а неизвестное
  пространство – ответом 404. `SpaceId` в PascalCase, который клиент отправлял
  раньше, проходил непрочитанным. У `POST /projects` параметра пространства в
  справочнике нет, и сервер не читает там ни одного написания: новый проект,
  загруженный с `space-id=not-a-uuid`, всё равно создался. Поэтому пространство
  нового проекта уходит в путь `POST /spaces/{space-id}/projects`. Неизвестное
  пространство этот метод отклоняет ответом 404, а сборку, у поставщика и имени
  которой проект уже есть, добавляет в этот проект, как и `POST /projects`.
  Коммит, из которого собрана сборка, уходит параметром `commit-id`:
  справочник описывает его у `POST /projects/{id}/assemblies`, и сервер кладёт
  его в карточку сборки. С этим коммитом и сверяет исходники сторож схемы
  следующего деплоя (п. 7). У того же метода справочник перечисляет ещё
  `branch-name`, `commit-message` и `modified`, и клиент их не отправляет.
  Живая проверка показала, что сервер их принимает, а в карточке не показывает
  ни одного: его `branch-name` – это ветка групповой разработки, а не git, а
  `modified=1` он отклоняет ответом 500. `CommitId`, `BranchName` и
  `CommitMessage` в PascalCase – вовсе не параметры метода, их сервер
  игнорирует. У `POST /projects` параметра коммита в справочнике нет, поэтому
  сборка, которая создаёт свой проект, коммита не несёт. Чего платформа не
  хранит – ветку, признак незакоммиченных правок, каталог исходников, – клиент
  держит в локальном реестре загрузок (п. 7).
  Версию архива две загрузки понимают по-разному. Загрузка в проект,
  `POST /projects/{id}/assemblies`, её вовсе не читает: базу сервер берёт из
  `Версия` описания проекта, а номер дает наибольший, какой он когда-либо
  выдавал в этой базе, плюс один.
  Проверено живьём: архив `1.0.0-i1` стал `1.0.0-1`, следующий, `1.0.0-10001`, –
  `1.0.0-2`, `1.0.0-2`, который в проекте уже был, – `1.0.0-3`, а `1.0.1-7` –
  `1.0.0-502` в проекте, чье описание говорит `1.0.0`. Номер удаленной сборки
  остается за ней: перечень ее больше не показывает, а сервер все равно считает
  от него. Когда с верха перечня сняли `1.0.0-4`, следующая загрузка стала
  `1.0.0-5`, а после снятия `1.0.0-50` и `1.0.0-51` – `1.0.0-52`, хотя перечень
  кончался на `1.0.0-8`; сборка, снятая из середины перечня, ничего не меняет.
  Прочитать счетчик негде: в карточке проекта его нет, перечень удаленную сборку
  не показывает, а карточка удаленной сборки отвечает 404. Эта загрузка отвечает
  карточкой сборки, и её `assembly-version` – номер, который выдал сервер.
  Загрузка по поставщику и имени, `POST /projects`, версию архива сохраняет как
  есть, в том числе с нечисловым суффиксом, а на версию, которая в проекте уже
  есть, отвечает 409 (ниже). Номер удаленной сборки такая загрузка может занять
  снова, и счет проекта от этого назад не идет: архив `1.0.0-2` лег под этим
  номером после того, как прежнюю `1.0.0-2` сняли, а следующая загрузка в проект
  получила `1.0.0-8`, а не `1.0.0-3`. Поэтому суффикс версии, например номер
  запуска CI,
  переживает второй путь и никогда первый: сборку, загруженную в проект, с её
  запуском связывают имя архива и коммит в карточке.
  Ответ несёт id созданной сборки в одном из полей: `image-id`, `assembly-id`
  или `id`. Проверять их надо в этом порядке. Там же лежит объект `artifact` с
  описанием проекта, куда сборка легла: `artifact-id` - ид проекта, он
  открывается карточкой проекта; `configuration-id` - `Ид` из `Проект.yaml`;
  `name` - представление проекта. Панель показывает проект под именем последней
  залитой сборки, то есть под `Name` из манифеста. Поэтому сборка, залитая в
  проект под другим именем, переименовывает и проект, и его группу, а удаление
  сборки этого не откатывает. Клиент в такой загрузке отказывает и называет
  цену. Чужую сборку заливают намеренно, флагом `--force-rename`. Сверка тут
  вспомогательная: если сравнить нечем, потому что манифест не читается или
  карточка проекта недоступна, загрузка идёт как прежде. Невозможность сравнить
  не доказывает опасности.
- **Проект опознаётся парой `Vendor` + `Name` из манифеста** (п. 6.8). Поэтому
  `POST /projects` создаёт проект не всегда: если проект с такой парой уже есть,
  сборка добавляется в него, и в ответе приходит его `artifact-id`. Ответ 409
  `ALREADY_EXISTS` приходит в двух случаях. Первый: залита версия, которая уже
  есть, текст ответа - "Версия сборки ... уже присутствует в группе проекта".
  Второй: ту же пару поставщика и имени регистрируют в другом проекте, текст -
  "Сборка с именем поставщика ... уже зарегистрирована в другом проекте". Второй
  случай не обходится даже генерацией нового `Ид` в `Проект.yaml`.
- `GET /projects/{id}/assemblies` - список сборок. Элемент содержит
  `assembly-version`, строку вида `1.0-42`, и id в поле `id` либо `image-id`.
  Ответ приходит массивом или объектом, у которого список лежит в поле `items`
  или `assemblies`. **Страниц у метода нет, и общего числа он не сообщает.**
  Параметры `limit`, `size`, `pageSize`, `count`, `top`, `maxResults`, `page`,
  `pageNumber`, `offset`, `skip`, `from` и `start` метод игнорирует: ответ на
  все эти запросы совпадает побайтно, а ни в заголовках, ни в теле нет ни
  счётчика, ни курсора. Проверено живыми вызовами на двух установках.
  **Платформа сама удаляет сборки, которыми никто не пользуется,** и возраст
  тут ни при чем: справка вендора называет это автоматическим удалением
  неиспользуемых сборок. Делает это консоль в один момент – когда приложение
  заканчивает применение сборки: фоновое задание перебирает сборки проекта этого
  приложения с той же базовой версией, что у сборки, на которой оно теперь
  работает. Остаются релизная сборка, защищенная сборка, сборка проекта по
  умолчанию, сборка, на которой работает живое приложение проекта или которая в
  него загружена, и сборка с наибольшим номером этой базы. Остальное снимается,
  не больше десяти сборок за одно применение. Сборка, загруженная по поставщику и
  имени (`POST /projects`), защищена с момента загрузки, как и та, из которой
  создан репозиторий проекта, и никакое применение ее не снимет, а сборка,
  загруженная в проект по ид (`POST /projects/{id}/assemblies`), не защищена.
  Библиотечная сборка, от которой не зависит ни одна оставшаяся сборка, уходит
  вместе со сборками своей группы. Поэтому проект, к приложениям которого ничего
  не применяют, хранит все сборки, а сборка, загруженная впрок, переживает
  применение другой, только пока у нее наибольший номер. Так написано в
  исходниках консоли из дистрибутива сервера, и живая проверка на проекте из
  девяти сборок сошлась с ними в каждой строке. Создание приложения за две минуты
  не сняло ничего. Применение `1.0.0-3` еще до ответа сняло `1.0.0-2`, `1.0.0-4`
  и `1.0.0-11`, а оставило `1.0.0-1` и `1.0.0-10`, обе загружены по поставщику и
  имени, `1.0.0-3`, `1.0.0-12` с наибольшим номером и обе сборки `2.0.0`.
  Применение `1.0.0-12` сняло `1.0.0-3`. Применение `2.0.0-1` не сняло ничего, в
  том числе `1.0.0-12`: это применение смотрело только на `2.0.0`. Раньше видели
  и такое: из семнадцати сборок одной дневной серии в перечне осталась одна, та,
  на которой работает приложение, а сборка двухмесячной давности жива: она у
  проекта первая, а загрузка, которая создает проект, идет по поставщику и имени.
  Отсюда требование к клиенту: называть перечень остатком, а не историей проекта
  и не ее страницей.
- `GET /projects/{id}/assemblies/{version}` - карточка сборки, `DELETE
  .../{version}` - удаление. Последний сегмент - то, чем его называет сам метод:
  версия (`assembly-version` или `project-version`, строка вида `1.0-42`), а не
  ид карточки. На UUID метод отвечает 404 "Assembly with version <uuid> not
  found". Проверено живыми вызовами на двух установках разного возраста, ведут
  себя одинаково. Страницы утверждали обратное: только UUID, а на версию 400
  "Version is not a valid UUID". Кто следовал этому утверждению, оставался без
  карточки в любой из форм. При этом ид - тоже адрес, который есть на руках: его
  печатает перечень сборок и возвращает загрузка. Поэтому клиент принимает обе
  формы и находит по списку сборок ту версию, которую метод ждёт. Значение,
  которого нет ни в одной карточке, он называет ненайденным, а не превращает в
  404 из глубин платформы. Если адрес отклонён с 400 или 404, клиент пробует
  сегментом и ид: ни одна доступная установка этого не требует, но описанный
  страницами 400 откуда-то взялся, а вторая форма стоит одного запроса.
  Версия сборки, загруженной в проект, – номер, который дал сервер, а не версия её
  архива (загрузка выше). Удаление сборки платформа отклоняет с 500, пока живо
  созданное из неё приложение (п. 6.9). Когда приложение действительно исчезло,
  тот же запрос проходит. 500 - это ответ, а не непонятый адрес: он поднимается
  как есть и другой формой не переспрашивается.

Версии сборок сравнивают по числовому суффиксу после последнего дефиса: `1.0-10`
новее, чем `1.0-9`. Лексикографическое сравнение даёт неверный порядок.

### 4.5. Ветки среды разработки

- `GET /branches` - список; необязательные query `project-id`, `name`.
- `GET /branches/{id}` - карточка. Поля: `name`, `kind`, `project`,
  `application`, `source-branch`, `deletion-mark`, `version-stamp`.
- `POST /branches` - создать. Тело: `name`, `kind: "development"`,
  `project: {"id": "<id>"}`, необязательно `application: {"id": "<id>"}`.
- `PUT /branches/{id}` - изменить. Платформа держит оптимистическую блокировку,
  поэтому сначала прочитайте карточку, а затем отправьте тело, собранное из
  текущих значений. Это `name`, `kind`, `deletion-mark` и `version-stamp`,
  который обязательно вернуть как есть. Поля `source-branch` и `application`
  свернуть до `{"id": ...}`, а если ид нет, то до `{"name": ...}`. Чтобы
  перепривязать ветку к приложению, замените `application` на
  `{"id": "<новый app-id>"}`.
- Изменения ветки принимает тот же `PUT /branches/{id}` с дополнительным ключом
  тела `write-parameters: {"merge": true}`.
- `DELETE /branches/{id}` - удалить ветку.

Инструмент работает только с документированным Console API v2. Внутренние, то
есть недокументированные, API консоли платформы он не использует и не описывает.

### 4.6. Задачи приложений

`GET /tasks/application-tasks` - список задач всех приложений. Серверного фильтра
нет, фильтровать приходится на клиенте. Поля задачи: `id`, `application-id`,
`status` (в т.ч. `Error`, `Failed`), `operation-type`, `error-message`,
`start-date` (ISO 8601, может оканчиваться на `Z`).

### 4.7. Списки пользователей

Список пользователей держит либо пользователей приложения, у которого список
свой и назван по нему, либо пользователей панели управления, где список один на
установку. То, что панель называет настройками входа, живёт здесь.

- `GET /user-lists` - список списков: `id`, `presentation`, `space-id`. Фильтра
  по имени на сервере нет, фильтровать приходится на клиенте.
- `GET /user-lists/{id}` - полная карточка: `self-registration`,
  `password-policy`, `password-policy-enabled`, `account-services-settings`,
  `confirmations`, шлюзы, `include-personal-data-in-messages`.
- `GET|PUT /user-lists/{id}/settings/self-registration` -
  `{enabled, phone-required, email-required}`. Это и есть "Разрешить
  пользователям регистрироваться самостоятельно" из панели. PUT требует объект
  целиком.
- `GET|POST /user-lists/{id}/settings/account-services-settings`,
  `PUT|DELETE .../{account-service-id}` - сервисы учётных записей списка. Запись:
  `{account-service-id, account-service-type, local-id, enabled,
  create-user-on-auth, additional-settings}`. Тип `Local` аутентифицирует
  паролем, поэтому "Разрешить вход по логину и паролю" из панели - это его
  `enabled`. Остальные типы внешние: `OIDC`, `Cas`, `ActiveDirectory`, `Esia`.
  PUT требует запись целиком.
- `GET /applications/{id}/userlists` - ид списков, подключённых к приложению;
  `POST` подключает, `DELETE` отключает. Обратите внимание на написание: здесь
  без дефиса. Настроек подключения там нет: связь это множество ид и ничего
  больше.
- `GET /user-lists/{id}/users` – пользователи списка, среди полей `id` и `login`. Запись
  несёт и токены доступа пользователя вместе с секретами, поэтому клиент берёт из неё
  только ид.
- Собственный список приложения назван в карточке приложения полем
  `default-user-list`. Это список его пользователей, а список панели, тоже к нему
  подключённый, отдельный.

Две вещи панель умеет, а API нет, поэтому обе остаются ручными:

- состава форм аутентификации приложения в API нет вовсе;
- настройка подключения "пользователи списка подключаются к приложению
  автоматически при входе" тоже не представлена. Её нет ни в `userlists`,
  который есть множество ид, ни в `account-services-settings` приложения: с
  включённой настройкой там ничего не появляется.

Правила разбора ответа сервиса учётных записей принимаются в теле сервиса под
ключом `userPropertiesCalculationRules`. Это `presentation-rule`, `email-rule`,
`phone-rule` и `response-kind`, все они JsonPath или XPath. Ловушек здесь две.
Схема справочника называет то же самое `calculation-rules`, и на такое написание
платформа отвечает 400. А GET правила не возвращает никогда: настройка только на
запись, и подтвердить её применение клиентом API нельзя.

## 5. Формат файла сборки (.xasm / .xlib)

Файл сборки - ZIP-архив (deflate):

- в корне `Assembly.yaml` - манифест, плоские пары ключ-значение:

  ```
  ManifestVersion: 1.0 | 1.1
  ProjectKind: Application | Library | Extension
  Vendor: <поставщик>
  Name: <имя проекта>
  Version: <версия, например 1.0-42>
  Created: <UTC, формат YYYY.MM.DD HH:MM:SS>
  BranchName: <имя git-ветки>
  CommitId: <хэш коммита>
  ```

  Для библиотеки (`ProjectKind: Library`) в конце добавляется строка
  `Release:` (пустое значение); расширение файла `.xlib`, для приложения и
  расширения – `.xasm`.

  Расширение (`ProjectKind: Extension`) пишется с `ManifestVersion: 1.1`, остальные виды –
  с `1.0`. Читателя манифеста сервер выбирает по его версии, а читатель 1.0 знает только
  `Application` и `Library`: расширение с манифестом 1.0 применение отвергает с
  "Неизвестный вид проекта: \"Extension\"". Ту же пару консоль пишет расширению, которое
  создает сама. Расширение, собранное так, на живом сервере применено через
  `project/update` и выгружено обратно файл в файл (п. 4.1).

- далее файлы проекта путями `{vendor}/{name}/...` относительно корня
  репозитория. Каталог проекта обязан лежать по схеме
  `{repo}/{vendor}/{name}/Проект.yaml`. Для приложения и расширения рекурсивно
  включаются библиотеки из `Библиотеки`/`Libraries`, которые доступны локально: консоль
  дает расширению библиотеки так же, как приложению. Расширяемые проекты из
  `РасширяемыеПроекты`/`ExtendedProjects` библиотеками не являются и в архив не попадают.
  Объявленная библиотека без проекта под тем же корнем репозитория остается внешней
  зависимостью платформы. Неподключённые соседние проекты не включаются.
  Разделители путей в архиве - прямые слэши, и на Windows тоже.

Имя файла сборки: `{Имя} {Version}.xasm` (через пробел).

Метаданные проекта берутся из `Проект.yaml`. Это YAML, и достаточно разобрать
плоские пары "ключ: значение" верхнего уровня, а вложенные строки с отступом
пропустить. Двуязычие исходников платформа заявляет сама, дескриптор с
английскими ключами применяется штатно, поэтому каждый ключ читается в обоих
написаниях: `Имя`/`Name`, `Поставщик`/`Vendor`, `Версия`/`Version` (базовая,
например `1.0`) и `ВидПроекта`/`ProjectKind`. Значение `Библиотека` или
`Library` означает библиотеку, `Расширение` или `Extension` – расширение, все прочее –
приложение. Если встретились сразу
оба написания ключа, побеждает русское. Двуязычны и имена служебных файлов:
конвертер платформы принимает `Project.yaml` и `Проект.yaml`, `Subsystem.yaml`
и `Подсистема.yaml`. Поэтому дескриптор ищется обоими именами везде: при поиске
проекта, при поиске локальных библиотек-зависимостей, при разборе архива и при
проверке доступности коммита стражем схемы.

Если версия сборки не задана явно, она собирается как `{базовая версия}-{N+1}`,
где N - счетчик из версии последней сборки проекта той же базовой версии.
`deploy` берет за N больший из двух номеров: номер последней сборки в перечне и
наибольший номер, который локальный реестр загрузок помнит для проекта в этой
базе. Сервер считает от наибольшего номера, какой он когда-либо выдавал, считая
и удаленные сборки (п. 4.4). Проект, поднятый на новую базовую версию, снова
начинает с `-1`, какие бы номера ни
набрала старая база. Когда последней сборки этой базы нет, суффикс берётся из
номера запуска CI в окружении: первое числовое значение из `CI_PIPELINE_IID`,
`GITHUB_RUN_NUMBER`, `BUILD_NUMBER`, именно в этом порядке. Иначе чистый рабочий
каталог CI давал бы `-1` каждый раз. Нет и номера CI - остаётся
`{базовая версия}-1`.

Git-метаданные, то есть хэш коммита и имя ветки, берутся из git-репозитория,
который содержит каталог проекта. Если git недоступен, поля остаются пустыми.

Отбор файлов в архив:

- внутри каталогов `Ресурсы`, на любом уровне и в их подкаталогах, включаются
  файлы любых расширений: по документации платформы ресурс - это произвольный
  файл, например `.pdf`, `.htm`, `.mxl`, `.docx`, `.xsd`;
- вне каталогов ресурсов включаются только расширения: `.yaml .xbsl .xbql
  .md .txt .json` (исходники), `.png .svg .jpg .jpeg .gif .webp .ico`
  (изображения), `.css .htm .html .js .woff .woff2 .ttf .eot` (веб-ресурсы);
- файлы описания клиента SOAP-сервиса включаются, где бы они ни лежали:
  `<ИмяКлиента>.Wsdl.<n>` и `<ИмяКлиента>.Xsd`. Платформа кладёт их рядом с
  элементом проекта, а не в каталог ресурсов, и запрещает переименование,
  поэтому отбирают их по имени, а не по расширению;
- исключаются каталоги `.git`, `.claude`, `.github`, `__pycache__`,
  `node_modules`, `.venv` и все скрытые (начинающиеся с точки);
- исключаются файлы `.gitignore`, `.env`, `.DS_Store`, а также `*.xasm` и
  `*.xlib`, в том числе внутри каталогов ресурсов.

### 5.1. Разбор готового архива

Операция, обратная сборке: по файлу `.xasm` или `.xlib` читаются манифест,
свойства проекта из его `Проект.yaml` внутри архива и состав. Она нужна, чтобы
подключить библиотеку к проекту, не разворачивая её исходники.

Раскладка внутри проекта; о составе достоверно говорят только каталоги:

- каталог первого уровня - это **подсистема**. Файл `Подсистема.yaml` или
  `Subsystem.yaml` **необязателен**, у подсистемы библиотеки его может не быть
  вовсе, поэтому при поиске подсистем на него опираться нельзя;
- вложенный каталог подсистемы - это **пакет**. Файла-описания у пакета нет, и
  каждый каталог даёт сегмент имени;
- полное имя типа: `{vendor}::{name}::{подсистема}[::{пакет}]::{ИмяТипа}`. То же
  имя без последнего сегмента указывается в `Использование` и `импорт`.

Наружу, в подключивший проект, видны только типы с `ОбластьВидимости:
Глобально`, по-английски `VisibilityScope: Global`. По умолчанию стоит
`ВПодсистеме`, он же `InSubsystem`, а глобальная область пишется явно. У
английского дескриптора английские и значения перечислений, поэтому значения
читаются в обоих написаниях.

Совместимость проверяется по свойству `РежимСовместимости` файла `Проект.yaml`.
Свойства `ВерсияТехнологии` в `Проект.yaml` **не существует**: оно относится к
телу запроса Console API на создание приложения, а не к файлу проекта.

## 6. Поведение платформы, которое приходится учитывать

1. **Тихий откат применения.** Когда применение сборки к приложению падает,
   например из-за ошибки компиляции, платформа молча откатывает приложение на
   предыдущую сборку и запускает его. Статус `Running` успеха не означает.
   Достоверно результат проверяют так:
   - взять задачи приложения (п. 4.6) со статусом `Error` или `Failed`, у
     которых `start-date` не раньше начала работы. Старые ошибки из истории не
     в счёт;
   - сверить фактически применённую версию, поле `source.project-version`
     карточки приложения, с версией загруженной сборки;
   - для сведения сделать контрольный GET по `uri` приложения. Коды 401 и 403
     нормальны для закрытых приложений и успеху не противоречат.
2. **Пустой каркас при создании.** На части конфигураций платформы приложение,
   созданное с источником "проект", то есть с `image-id`, равным ид проекта,
   выходит пустым, без данных проекта. Надёжный источник - конкретная сборка в
   `project-version-id`, например последняя сборка проекта.
3. **Удаление с черновиками.** Если в среде разработки приложения есть
   неопубликованные правки, `DELETE /applications/{id}` возвращает 400 с
   `FAILED_PRECONDITION` в теле. Принудительного удаления в API нет, остаётся
   панель управления. Инструмент обязан дать понятную подсказку.
4. **Готовность нового приложения.** После создания приложение какое-то время
   держится в переходных статусах и без `uri`, поэтому нужно предусмотреть
   ожидание готовности: появился `uri` и статус стал стабильным. Статус `Error`
   во время ожидания - сразу ошибка. Чтение карточки, оборванное сетью, – это
   пропущенный опрос, а не конец ожидания: приложение создаётся всё равно.
   `UNKNOWN`, который держится минуту подряд, завершает и это ожидание ошибкой с
   названием статуса (п. 4.1): пока идет задача создания приложения, консоль
   показывает `Initializing`, что бы ни сообщал сервер, поэтому `UNKNOWN` бывает
   только после нее. Перечень задач из п. 4.6 несет задачи всех приложений сразу и обрывается
   чаще других, поэтому оборванное чтение перечня повторяется, всего три раза.
5. **Перезапуск после применения.** `project/update` может сам перезапустить
   приложение. После вызова дождитесь выхода из переходных статусов. Если итог
   не `Running`, остановите приложение, когда оно не в `Stopped`, дождитесь
   `Stopped`, запустите и дождитесь `Running`. Разумные сроки ожидания:
   остановка около 3 минут, запуск и стабилизация около 5 минут, опрос примерно
   раз в 10 секунд. Оборванное сетью чтение карточки и в этих ожиданиях
   считается пропущенным опросом, как в п. 6.4. `UNKNOWN`, который держится
   минуту подряд, завершает любое из них ошибкой с названием статуса (п. 4.1).
6. **Статус `Error` конечный.** Стабильный `Error`, например после неудачного
   применения, - это сразу ошибка: покажите тексты ошибок задач приложения
   (п. 4.6). Останавливать и перезапускать такое приложение не надо, ждать
   другого статуса тоже: из `Error` оно в `Stopped` не переходит, и ожидание
   просто выберет весь отведённый срок.
7. **Windows.** Временные файлы и кеши - только через `tempfile`. Вывод консоли
   надо перевести в UTF-8 вызовом `reconfigure` для stdout и stderr, иначе
   кириллица ломается.
8. **Проект опознаётся поставщиком и именем.** Проект платформы опознаёт пара
   `Vendor` + `Name` из манифеста, а не `Ид` из `Проект.yaml`. Загрузка без ид
   проекта попадает в тот проект, которому эта пара уже принадлежит, а создание
   второго проекта под ту же пару отклоняется с 409 (п. 4.4). Отдельный проект
   получается только переименованием исходников. Поэтому изолированная проверка
   компиляции строится вокруг одноразового приложения, а не одноразового
   проекта.
9. **Удаление идёт в фоне и по порядку.** `DELETE /applications/{id}`
   возвращается сразу, а приложение ещё какое-то время живёт с задачей
   `DeleteApplication`. Пока оно существует, удаление сборки, из которой оно
   создано, отклоняется с 500. Порядок уборки такой: удалить приложение,
   дождаться, когда его карточка ответит 404 или статус станет `Deleted`, и
   только затем удалять сборку. Оборванное сетью чтение карточки в этом
   ожидании тоже считается пропущенным опросом, как в п. 6.4.
10. **Компиляция серверная и происходит при применении.** Локальная сборка
    только упаковывает архив. Синтаксис, типы и видимость исходников проверяет
    серверный компилятор, когда сборку применяют или создают из неё приложение.
    Отдельной конечной точки "скомпилировать" нет. Поэтому проверить исходники,
    не рискуя рабочим приложением, можно единственным способом: поднять из той
    же сборки одноразовое приложение (п. 7, `probe`).
11. **Вход в только что созданное приложение.** Новое приложение получает
    собственный пустой список пользователей (`default-user-list`, п. 4.7), вход
    по логину и паролю в нём выключен, а сервис учётных записей не подключён.
    Поэтому учётные записи, которыми входят в другие приложения, здесь не
    работают. Подключение чужого списка пользователей
    (`POST /applications/{id}/userlists`) вместе с включением локального входа
    этого не меняет, и это проверено. Войти можно учётной записью панели
    управления: её пользователей платформа подключает к приложению сама, и вход
    срабатывает сразу. Инструмент обязан говорить это вслух при создании (п. 7,
    `apps create` и `apps ensure`): из карточки способ входа не виден, а
    перебирать его нельзя, потому что у пользователя есть счётчик неудачных
    попыток.
12. **Сервер ещё стартует.** После запуска или обновления сервер поднимает
    консоль не сразу: после одного обновления она молчала тринадцать минут. Всё
    это время на любой запрос к консоли, включая запрос токена, сервер отвечает
    404 с текстом `Application "console" not found`. Тот же код получает
    отсутствующее приложение или сборка, и отличает их только текст. Клиент
    распознаёт такой ответ в одном месте, для всех своих запросов, и поднимает
    ошибку, которая говорит, что он значит: сервер стартует, повторите, когда
    `/console` начнёт отвечать 302. `deploy` пережидает старт сам на любом шаге
    цикла, не дольше `--server-start-timeout` секунд (по умолчанию 900, 0 – не
    ждать), и называет начало и конец ожидания. Запрос, который консоль отвергла,
    она не обработала, поэтому повторять его безопасно, каким бы ни был метод.
    Остальные команды не ждут: они называют причину и останавливаются.
13. **Снятие применяется без вопросов.** Сборку, в исходниках которой больше нет
    табличной части, сервер применяет как есть: табличная часть уходит, а с ней и
    её строки. Ни отказа, ни предупреждения, задача заканчивается успешно, и
    приложение работает дальше; так было со справочником, у которого в табличной
    части была строка. Так же уходят реквизит табличной части и реквизит самого
    объекта, вместе со значениями, и справочник, чьего описания в исходниках
    больше нет, вместе со всей таблицей: так было с пустым справочником. Сужение
    длины и смена типа, напротив, пересоздают данные объекта. Что с каждым из
    этих случаев делает деплой, сказано в п. 7.

## 7. Требования к CLI

Общие флаги принимаются в любой позиции, в том числе после подкоманды:
`--base-url`, `--client-id`, `--client-secret`, `--env-file`, `--timeout`
(секунды, по умолчанию 60), `--lang`, `--json`, `--quiet`. Флаг `--version` –
исключение, он ставится до подкоманды.

Флаги подключения нужны для разговора с платформой. Команды `build` и `inspect`
к ней не обращаются, поэтому эти флаги они отвергают, а не глотают молча. Вызов
с `--env-file` читается как сборка, привязанная к стенду, и дважды из-за этого
возникал вопрос, не ходит ли локальная сборка на сервер. Вводит в заблуждение
именно молчание. Ничего работавшего отказ не ломает, ведь флаги и так ни на что
не влияли, зато он называет команды, которые к платформе действительно ходят:
`deploy` и `builds upload`. Касается это только флагов. Переменные `ELEMENT_*` и
`.env` рядом с проектом есть всегда, и зависеть от них сборка не должна.

Вывод устроен так: результат уходит JSON-ом в stdout (`ensure_ascii=False`,
отступ 2), прогресс длительных операций - строками в stderr, а ошибка - JSON-ом
с полем `error` в stderr и кодом возврата 1.

Флаг `--json` делает это гарантией, а не просто соглашением: на время вызова
stdout перенаправляется в stderr, и в настоящий stdout пишется только ответ.
Вызывающая сторона разбирает stdout целиком. Без флага любая строка,
напечатанная обработчиком или плагином, остаётся в потоке перед ответом. Отказ и
в этом режиме уходит в stderr, а stdout остаётся пустым.

Флаг `--quiet` на время вызова глушит поток хода работы: строки прогресса,
сводки и предупреждения, которые идут в stderr, в том числе `context.log`
команды плагина. Ответ в stdout и отказ в stderr с кодом возврата остаются, а
форма ответа не меняется: для нее есть ключи `--brief` и `--json`. Раньше
команда плагина с `--quiet` в конце получала отказ "unrecognized arguments"
еще до начала работы.

`apps list` и `builds list` печатают счётчик и отметку об усечении после
ответа, никогда раньше. У остальных команд строка в stderr может прийти и
раньше ответа – например, предупреждение, которое печатает
`ELEMENT_TLS_VERIFY=false`, или собственный ход работы другой команды; это
касается и этих двух команд тоже. Разбирать объединённый поток целиком
по-прежнему небезопасно, безопасен только stdout, прочитанный отдельно.

Команды, в скобках - существенные флаги:

- `token` - получить и напечатать токен.
- `apps list [--name --status --include-deleted --brief]`, `apps get [APP_ID]`, `apps find NAME [--include-deleted]`,
  `apps create NAME [--project-id --version-id --latest-build --space-id
  --tech-version --no-dev-mode --wait --verify --no-verify]`,
  `apps ensure NAME [--project-id --version-id --latest-build --space-id
  --tech-version --no-dev-mode --wait --verify --no-verify --apply]`,
  `apps apply [APP_ID] VERSION_ID`,
  `apps delete APP_ID`, `apps start [APP_ID]`, `apps stop [APP_ID]`,
  `apps users [APP_ID]`, `apps token-access APP_ID [--user --enable --disable]`,
  `apps export [APP_ID] [--output]`, `apps export-extension [APP_ID] EXTENSION [--output]`.
  - `apps list --name` фильтрует по подстроке имени без учёта регистра и делает
    это на клиенте, потому что платформа query-параметр игнорирует (п. 4.1).
    Ключ `--status` отбирает по статусу целиком, несколько статусов пишут через
    запятую. Ключ `--brief` печатает вместо полных карточек краткие: ид, имя,
    статус, uri, применённая версия.
  - `apps list` скрывает удалённые приложения. Они остаются в перечне платформы
    со статусом `Deleted`, и стенд, живущий не первый месяц, отвечает сотнями
    карточек, из которых живых единицы. Вернуть их можно ключом
    `--include-deleted`, то же делает `--status deleted`: отбор, который ответил
    бы пустотой, хуже, чем отсутствие отбора. Молчаливое сокрытие само по себе
    ловушка, поэтому команда заканчивается строкой итога в stderr - "живых 7 из
    324", а при дополнительном отборе ещё и числом показанных. В stdout при этом
    остаётся тот же массив JSON, сколько бы ни было срезано.
  - `apps get` добавляет к карточке поле `applied-build` – краткую карточку
    сборки, на которой работает приложение: ветку и коммит из карточки сборки
    либо из локального реестра загрузок, в том же виде, что печатает
    `builds list --brief`. Когда карточка применённой сборки не называет, поле
    равно null.
  - `APP_ID` у `apps get`, `delete`, `start`, `stop`, `debug` и `users` - это ид
    приложения (UUID) либо его точное имя. Значение, не похожее на UUID,
    разрешается по списку точным совпадением без учёта регистра, причём
    удалённые приложения не в счёт. Нет совпадений - ошибка. Несколько
    совпадений - тоже ошибка, с перечнем ид: разрушающие команды не должны
    угадывать.
  - `apps find` ищет имя по точному совпадению без учёта регистра среди полей
    `name`, `display-name` и `publication-context`. Вывод -
    `{"id": ..., "found": true|false}`, код возврата 0 в обоих случаях:
    отсутствие приложения это ответ, а не ошибка. Ненулевой код возврата
    означает сбой запроса и сопровождается JSON-ом с полем `error` в stderr.
    В скриптах проверяйте поле `found`, а не код возврата.
  - Удалённые приложения остаются в списке платформы со статусом `Deleted` и
    прежним `id`. `apps find` их пропускает: найденный id обязан быть пригоден
    для работы, иначе вызывающий получит id, на котором `apps get` и `deploy`
    отвечают 404. Флаг `--include-deleted` возвращает прежнее поведение, то есть
    поиск среди всех приложений, включая удалённые.
  - `apps ensure` идемпотентно приводит приложение с данным именем в
    существование: ищет по правилам `apps find`, где удалённые не в счёт, и
    создаёт только при отсутствии. Вывод -
    `{"id": ..., "created": true|false, "sign-in": ...}`, а `created: false`
    означает, что приложение уже было и его не трогали. Флаги создания те же,
    что у `apps create`, и действуют, только когда создание происходит, в том
    числе `--version-id`. Поэтому у существующего приложения ответ несёт ещё
    `applied`, то есть стоит ли на нём запрошенная сборка, и
    `applied-version-id`, то есть какая стоит: молчание об этом стоило стенда,
    ушедшего в работу на прежней сборке. Привести приложение к сборке тем же
    вызовом позволяет флаг `--apply`, отдельно это делает `apps apply`. Флаг
    `--verify` поднимает вердикт о приложении, на котором запрошенная сборка уже
    стоит, со сверки по карточке до полной проверки. Созданному приложению
    `ensure` отвечал `applied: true` на веру, ведь оно из этой сборки и создано,
    а теперь отвечает проверенным вердиктом всякий раз, когда проверка была.
    Существующее приложение никогда не пересоздаётся: `delete` и `create` дают
    новый URL и рвут внешние привязки к прежнему.
  - `apps apply [APP_ID] VERSION_ID` применяет уже загруженную сборку к
    приложению и проверяет результат (п. 6.6). Применение не факт, пока не
    проверено: при сбое платформа молча откатывает приложение на прежнюю сборку
    и запускает его. Вывод - отчёт проверки, код возврата 1, когда сборка не
    применилась. До этой команды применение было доступно только инструментом
    MCP, а долгие операции просят запускать CLI фоном.
  - `apps create` и `apps ensure` заканчиваются тем, что говорят, как войти в
    приложение (п. 6.11). Это поле `sign-in` вывода вида
    `{"url", "account": "control-panel", "hint", "note"}` и те же две фразы в
    stderr. Поле `url` - адрес приложения из карточки. Пока адреса нет, а при
    создании без `--wait` его нет, там стоит `null`, и подсказка говорит, откуда
    его взять. Поле `account` - код, а не текст: войти можно учётной записью
    панели управления, и примечание объясняет, почему учётные записи, которыми
    входят в другие приложения, здесь не работают.
  - `--latest-build` берёт источником последнюю сборку проекта и защищает от
    пустого каркаса (п. 6.2). `--wait` дожидается готовности (п. 6.4), проверяет
    итог (п. 6.6) и выводит финальную карточку.
  - Источник из `--version-id` команда ищет в перечне сборок проекта до того, как
    что-либо создать. Проект – `--project-id`, а без флага – `ELEMENT_PROJECT_ID`.
    Платформа удаляет сборки, которыми никто не пользуется, и из удалённой сборки
    приложение не создаёт: она отвечает голым 400 "Can't create application", а
    такой отказ читается как предел числа приложений. Поэтому команда отказывает
    сама. Отказ называет причину и предлагает сборку, на которой работает
    приложение проекта, а если такого приложения нет – `--latest-build`. Проект из
    `ELEMENT_PROJECT_ID` отказ называет отдельно: сборка может оказаться из другого
    проекта. Без проекта искать негде, и создание идёт как раньше.
  - Дождаться значит проверить. Неудачное применение платформа откатывает на
    прежнюю сборку, и приложение всё равно поднимается в статусе `Running`,
    поэтому карточка, отданная после ожидания, ещё не доказывает, что работает
    запрошенная сборка. `--wait` заканчивается той же проверкой, что делают
    `apps apply` и `verify-deploy`: ид применённой сборки против запрошенной,
    задачи приложения, упавшие с начала создания, доступность uri. Отчёт
    попадает в поле `verify` вывода, а непройденная проверка - в код возврата 1.
    Флаг `--verify` просит проверку отдельно и сам дожидается готовности, потому
    что проверять ещё создающееся приложение не на чем. Флаг `--no-verify`
    возвращает прежнее простое ожидание. Без обоих флагов, как и раньше, ничего
    не ждётся и ничего не проверяется.
  - Приложение существует с того момента, как ответило создание, поэтому
    оборванное ожидание или проверка его не теряют. Вывод всё равно несёт ид:
    карточку у `apps create`, поле `id` у `apps ensure` с `applied: null`, ведь
    проверки не было. Поле `wait-error` хранит ошибку, на которой оборвалось
    ожидание, stderr называет вызов `verify-deploy` для проверки сборки позже, а
    код возврата – 1. Раньше ответом была голая сетевая ошибка без ида, и ид
    приложения, поднявшегося через несколько минут, приходилось искать по имени.
  - `apps users [APP_ID]` печатает пользователей, подключённых к приложению, так, как
    их отдаёт `GET /applications/{id}/users` (п. 4.1): `user-list-id`, `user-id`,
    `presentation`, `is-admin`, `token-access-enabled`. Логина среди них нет:
    пользователя панели управления платформа называет логином в `presentation`, а
    остальных – их представлением. Команда только читает, поэтому приложение по
    умолчанию берётся из `ELEMENT_APP_ID`, а заканчивается она строкой итога в stderr:
    сколько пользователей подключено, сколько из них администрирует приложение и у
    скольких есть доступ к его HTTP-сервисам по токену. До этой команды перечень был
    виден только в отказе `apps token-access`.
  - `apps token-access APP_ID` показывает или переключает доступ пользователя к

  `builds delete VERSION [--project-id]`. `builds upload` отправляет коммит,
  который называет манифест архива, параметром `commit-id` (п. 4.4), и называет
  в stderr сборку, которую сервер пронумеровал не так, как её архив (п. 4.4).
  `builds upload` сообщает выбранную цель в выводе полями `project-id` и
  `project-id-source` (`flag`, `env` либо ничего) и пишет в stderr, когда цель
  пришла из `ELEMENT_PROJECT_ID`. Ключ `--new-project` отключает привязку из
  окружения и всегда создаёт новый проект, с `--project-id` он несовместим. Ключ
  `--force-rename` разрешает загрузку сборки с чужим именем, которая переименует
  проект-цель.
  `builds list` показывает десять свежих сборок, а `--limit 0` снимает срез.
  Заканчивается команда строкой итога в stderr: она называет, какой из двух срезов
  перед читателем - срез инструмента по `--limit` или уборка платформы (раздел 4.4:
  платформа сама удаляет сборки, которыми никто не пользуется, и возраст тут ни при
  чём). "30 из 30" без этой строки читалось как вся история проекта. Про уборку
  строка судит по фактам ответа, а не по длине перечня: номера сборок одной базовой
  версии платформа выдаёт подряд, поэтому пропуск в нумерации – это уже снятая
  сборка, и строка говорит, что пропуски есть, не считая их. Пропуск бывает и
  скачком: загрузка по поставщику и имени сохраняет номер архива, и следующая
  загрузка в проект считает от него. Вживую за `1.0.0-3` шли `1.0.0-500` и
  `1.0.0-501`, а номеров между ними не было никогда. Отметки `created` соседей
  скачок от потери не отличают – сервер выдал четыре номера за треть секунды, –
  поэтому их отличает локальный реестр загрузок: пропуск под сборкой, которую эта
  машина загрузила по поставщику и имени, строка называет скачком и уборкой его не
  считает. Сборки, загруженной так с другой машины, в реестре нет, и её пропуск
  по-прежнему читается как удаление. Пропуск бывает скачком и удалением сразу.
  Вживую перечень шел от `1.0.0-8` сразу к `1.0.0-52`, после того как удалили
  `1.0.0-50`, загруженную по поставщику и имени, и `1.0.0-51`, а строка называла
  пропуск только удалением; скачок к `1.0.0-10` поверх `1.0.0-4`, которую сняла
  уборка, она называла скачком и не удалением. Поэтому пропуск под скачком этой
  машины остается скачком, только пока реестр не знает внутри него ни одной
  загрузки в этот проект. Пропуск с такой загрузкой внутри, под скачком или со
  сборкой скачка внутри, строка называет и тем и другим: сборку, которая принесла
  номер из архива, и загрузки этой машины, которых в перечне уже нет, – первые три
  и сколько еще. Такой пропуск считается удалением. На пустом перечне строка
  говорит, что сборок у проекта нет, а на перечне, где номера нет ни у одной
  сборки, – что судить по нумерации не по чему, вместо того чтобы называть
  нумерацию сплошной.
  `--brief` печатает ид, версии, дату, ветку и коммит сборки. Ветку и коммит
  команда берёт из карточки, если платформа их заполнила, иначе из локального
  реестра загрузок, а поля `branch-name-source` и `commit-id-source` говорят,
  откуда ответ: `platform`, `registry` или null, когда не знает никто. Только
  реестр знает `dirty` – были ли в дереве незакоммиченные правки – и
  `project-dir`, каталог, из которого собрана сборка.
- Локальный реестр загрузок. Каждая загрузка elemctl – `deploy`, `builds upload`,
  `probe` – дописывает строку JSON в файл `uploads.jsonl` в каталоге данных
  пользователя: `ELEMCTL_DATA_DIR`, если переменная задана, иначе
  `%LOCALAPPDATA%\elemctl` в Windows и `$XDG_STATE_HOME/elemctl`
  (`~/.local/state/elemctl`) в остальных системах. В строке – ид сборки, ид проекта,
  версия, ветка, коммит, признак `dirty`, каталог исходников, архив, стенд, команда,
  приложение, для которого загружали (цель деплоя, одноразовое приложение пробника),
  путь загрузки (`project` – в проект по ид, `vendor-name` – по поставщику и имени)
  и время. Платформа хранит один коммит, и когда с одной машины выкатывают несколько
  сессий, сборку на приложении нельзя было связать с рабочим деревом, из которого
  она пришла. Реестр локальный: сборок, загруженных с другой машины, из CI или
  версией elemctl без реестра, в нём нет. Если реестр не удалось записать, это
  предупреждение в stderr, а не отказ – сборка к тому времени уже на сервере;
  реестр, который не читается, считается пустым. Сторож схемы `deploy` берёт отсюда
  коммит примененной сборки, когда в ее карточке коммита нет. Отсюда же `deploy`
  считает номер следующей сборки: версия, которую получила сборка проекта,
  остается в реестре и после того, как сборку сняли (п. 5). Реестр хранит 1000
  последних загрузок, `ELEMCTL_REGISTRY_LIMIT` задаёт другое число, а `0` – хранить
  все: когда файл перерастёт предел на десятую часть, следующая загрузка обрежет его
  до последних строк. Файл переписывается рядом с собой и подменяется
  переименованием, а строку, которую тем временем дописал другой процесс, обрезка
  переносит; если система подмену не дала, файл остаётся как был до следующей
  загрузки.
- `build [--project-dir --output --build-version --last-build --commit

  архив. Вывод: `file`, `name`, `vendor`, `version`, `version-source`
  (`flag`, `last-build`, имя CI-переменной либо `default`), `kind`, `branch`,
  `commit` и `dirty`, то есть есть ли в каталоге проекта незакоммиченные
  изменения; `null` там означает, что git недоступен. Версия отдаётся отдельным
  полем, чтобы CI не выковыривал её из имени файла. Без `--project-dir` каталог
  проекта ищется автоматически: берётся первый каталог с `Проект.yaml` вглубь от
  текущего. Значение `--kind` по умолчанию определяется по `ВидПроекта`. Ключ
  `--require-clean` прерывает работу до сборки, когда в каталоге проекта есть
  незакоммиченные изменения. Недоступный git - тоже отказ: подтвердить чистоту

- `deploy [--app-id --project-id --project-dir --output --build-version
  --branch --commit --dry-run --require-clean --allow-data-loss
  --server-start-timeout]` -
  полный цикл: сборка -> загрузка -> применение -> перезапуск -> проверка
  фактического применения (п. 6.1). Вывод - JSON-отчёт с полями: `app-id`,
  `uri`, `status`, `version`, `assembly-id`, `assembly-version` (версия, которую
  сервер дал загруженной сборке), `renumbered` (true, когда это не версия архива,
  null, когда загрузка её не назвала), `applied-version`, `applied`
  (true, false либо null, когда фактическую версию определить не удалось),
  `uri-status`, `problems` (список строк, тексты платформы как пришли),
  `problems-lines` (то же построчно: JSON экранирует многострочный отказ в
  `
` и `	` ровно там, где его надо читать), `ok` (булево), `dirty` и `dirty-files`
  (незакоммиченные изменения каталога проекта на момент сборки). Сборка снимает
  текущее состояние диска, поэтому расхождение с HEAD должно быть видно;
  предупреждение идёт и в stderr, а `null` означает, что git недоступен. Поле
  `hint` указывает на журнал сервера, когда задача отвергнута без ошибки
  компиляции в тексте. Платформа может ответить одним "Contact administrator for
  details", и тогда причина лежит в журнале сервера: последняя строка
  `Caused by`, а `SrcPath:` рядом называет файл, на котором остановилось
  применение. Применение, после которого приложение в статусе `Error`,
  заканчивает деплой ошибкой, и эта ошибка несёт ту же подсказку. Код
  возврата 0 только при `ok`. Сборку, загруженную в проект, сервер нумерует сам
  (п. 4.4), поэтому явный `--build-version`, который он не сохранит, – с
  нечисловым суффиксом, без суффикса, с базой, отличной от `Версия` проекта, –
  деплой называет в stderr до сборки, а сборку, которую сервер пронумеровал не так,
  как ее архив, – сразу после загрузки. Без `--build-version` деплой считает номер
  от большего из перечня сборок и локального реестра загрузок (п. 5): номер
  удаленной сборки сервер повторно не выдает, а реестр помнит номера, полученные
  загрузками этой машины. Сборки, загруженной с другой машины и потом снятой, нет
  ни там, ни там, поэтому счет еще может отстать, и тогда строка после загрузки
  без предупреждения говорит, что номер назначил сервер. Ключ `--dry-run`
  оставляет одну сборку, ключ `--require-clean` дает отказ до сборки при грязном
  дереве. Ключ
  `--server-start-timeout` задаёт, сколько секунд ждать сервер, который ещё
  стартует (п. 6.12).
  До сборки сторож схемы сверяет исходники с коммитом, из которого собрана
  применённая сборка: с `commit-id` её карточки (п. 4.4), а если в карточке коммита
  нет – с коммитом, который помнит об этой сборке локальный реестр загрузок. У
  сборки, создавшей свой проект, коммита в карточке нет, а реестр его знает, если
  сборку загружали с этой машины. Строка в stderr говорит, что коммит взят оттуда, а
  если сборку собирали из дерева с незакоммиченными правками, говорит и это: их
  сверка не видит. Поле `schema-commit` называет коммит, с которым шла сверка, а
  `schema-commit-source` – откуда он взят: `platform` или `registry`. Каталог
  проекта сторож находит так же, как сборка. Сужение длины и смена типа реквизита,
  измерения или ресурса, включая реквизиты табличных частей, и снятие измерения
  пересоздают или ломают данные, поэтому без `--allow-data-loss` деплой их
  отклоняет. Так же деплой отклоняет снятие целиком элемента со своими данными –
  справочника, документа, регистра сведений или накопления, набора констант, плана
  обмена или хранилища настроек, чьего описания в исходниках больше нет: вместе с
  ним уходит вся его таблица со строками. Файла, которого нет, диск не покажет,
  поэтому сторож берёт у git перечень файлов применённого коммита и узнаёт элемент
  по `Ид`. Описание, перенесённое в другую подсистему или переименованное, данные
  сохраняет и сверяется со своим прежним текстом; элемент без `Ид` от перенесённого
  не отличить, и его сторож не трогает. Файл на прежнем месте, но с другим `Ид`
  описывает другой элемент: описание сделано заново, и элемент, которого файл
  описывал прежде, сторож прослеживает так же. Проверено живьём: справочник,
  описанный заново под прежними путём и именем, применился без вопросов и
  оказался пустым, поэтому такой элемент деплой отклоняет как снятие, а отказ
  называет прежний `Ид`, который нужно вернуть, если элемент тот же. Поля двух
  описаний друг с другом не сверяются: это поля разных элементов. Снятие реквизита, ресурса, табличной части
  или реквизита табличной части – сознательная правка, которую сервер применяет без
  вопросов (п. 6.13): деплой называет каждое в stderr и в поле `schema-warnings` и
  идёт дальше. Поля сопоставляются по `Ид`, поэтому переименование данные сохраняет,
  а при переводе описания на другой язык о снятии может сказать только `Ид`. Поле
  `schema-check` говорит, что сделал сторож: `clean`, `warned` (нашлись только
  снятия), `allowed` либо `skipped:<причина>`, когда сравнивать не с чем:
  `no-project-dir`, `read-failed`, `no-applied-build`, `applied-build-not-listed`,
  `no-commit-id` или `commit-unavailable`, и у каждой причины свои слова.
  Пропущенную сверку отчёт называет ещё раз после вердикта: "проверка пройдена" сама
  по себе читалась так, будто схема тоже проверена.
- `verify-deploy [APP_ID] [--app-id --version-id --expected-version --since-minutes]` -
  проверка п. 6.1 отдельной командой, которая ничего не разворачивает. Она смотрит
  задачи приложения в ошибочном статусе за последние `--since-minutes` минут, а в их
  `error-message` лежат файл и позиция ошибки компиляции. Дальше она сверяет
  применённую сборку с ожидаемой: `--version-id` - это ид загруженной сборки и
  надёжная сверка, `--expected-version` - строка версии и запасной путь.
  Заканчивается всё контрольным GET на адрес. Отчёт тот же, что у `deploy`, код
  возврата 0 только при `ok`. Это то, что нужно скрипту CI после `apps create`: сбой
  применения платформа откатывает молча, и статус `Running` сам по себе ничего не
  доказывает.
- `probe [--project-dir --output --build-version --name --space-id --keep
  --require-clean]`, `probe --cleanup APP_ID` - изолированная проверка компиляции исходников: сборка ->
  загрузка -> одноразовое приложение (это и есть компиляция, п. 6.10) -> ошибки
  с файлом и позицией -> уборка. До сборки манифест проверяется на то, без чего
  сервер пробник не примет. Это `Представление` (`Presentation`): без него
  консоль отвечает на загрузку 500 без объяснения. Это `ЯзыкРазработки`
  (`DevelopmentLanguage`): обязательное свойство, без него приложение не
  создаётся. И это `ЯзыкиЛокализации` (`LocalizationLanguages`), когда задан
  `ЯзыкПоУмолчанию` (`DefaultLanguage`): такую пару сервер отклоняет, не называя
  причины. Недостающий ключ останавливает пробник до сборки и загрузки, а ошибка
  называет каждый такой ключ вместе со строкой, которую нужно добавить, в
  написании самого манифеста. `ELEMENT_APP_ID` и `ELEMENT_PROJECT_ID`
  намеренно не используются: у пробника не должно быть возможности достать
  рабочее приложение, а проект-цель выбирает сама платформа по поставщику и
  имени манифеста (п. 6.8). Версия сборки по умолчанию - `{база}-probe-{токен}`.
  Она обязана быть новой каждый раз, потому что повтор даёт 409, и не должна
  выглядеть последней сборкой проекта: счётчик там числовой, и нечисловой
  суффикс держит пробную сборку вне этого сравнения. Уборка идёт и при удачной
  компиляции, и при провале, в порядке п. 6.9: приложение, затем сборка, затем
  проект, и только если пробник сам его создал. Вывод: `ok`, `project-dir`,
  `vendor`, `name`, `file`, `version`, `project-id`, `project-created`,
  `assembly-id`, `app-id`,
  `app-name`, `status`, `errors` (список `{file, entry, line, column,
  environment, message}`, где `file` - путь относительно каталога проекта),
  `messages` (тексты платформы дословно, чтобы ничего не терялось, когда провал
  не компиляционный), `cleanup` (`kept`, `app-deleted`, `assembly-deleted`,
  `project-deleted`, `problems`, `command`, `steps`) и `hint` – та же подсказка о
  журнале сервера, что
  несёт отчёт `deploy`. Поле `hint` заполнено, когда сервер отказал и не назвал
  файла; истёкшее ожидание оставляет его пустым. Стенд, не знающий режима совместимости
  проекта, отказывает проекту целиком, а следом жалуется на типы и свойства
  этого режима в файлах, которых правка не касалась. Такой отказ распознаётся,
  разбор на нём обрывается, `compatibility-refused` называет режим, а
  `messages-dropped` считает производное. Так вердикт о стенде не читается как
  вердикт о коде. Код возврата 0 только при `ok`. Неудавшаяся уборка - это
  проблема в отчёте и в stderr, вердикт компиляции она не меняет. Ключ `--keep`
  оставляет приложение и сборку на стенде для разбора руками. След от пробника
  всё же остаётся: удалённые приложения платформа держит в списке со статусом
  `Deleted` и прежним ид, и убрать их через API нельзя.
  Всё, что пробник оставил, намеренно с `--keep` или из-за шага уборки, который не
  удался, приходит вместе с командами, которые это убирают, – в `cleanup` и в stderr:
  `command` – одна команда, `probe --cleanup APP_ID`, а `steps` – то же вручную в
  порядке п. 6.9, причём сборка адресуется в собственном проекте пробника. Голый
  `builds delete` ищет в проекте из `ELEMENT_PROJECT_ID`, где сборки пробника нет, а
  сборке, удаляемой сразу после её приложения, платформа отказывает ответом 500, пока
  приложение не исчезнет. Обе строки называют `--env-file`, с которым запускали
  пробник.
  `probe --cleanup APP_ID` убирает оставленный на стенде пробник, начиная с его
  приложения, по ид или по имени. Карточка приложения называет проект и сборку, из
  которой оно создано, поэтому между запусками ничего запоминать не нужно. Трогается
  только приложение пробника: его имя начинается с `elemctl-probe-`, версия сборки, на
  которой оно работает, несёт `-probe-` – так узнаётся и пробник, названный через
  `--name`, – или локальный реестр загрузок помнит, что приложение создал probe этой
  машины: так узнаётся пробник, которому дали и `--name`, и `--build-version`, и
  пробник, в который с тех пор выкатывали сборки. Любое другое приложение команда
  отклоняет и называет причину, как и приложение из `ELEMENT_APP_ID`. Порядок – п. 6.9:
  приложение, ожидание, пока оно исчезнет, сборка именно этого пробника (его токен в
  версии либо сборка, загрузку которой пробником помнит реестр) вместе со всеми
  сборками, которые по памяти реестра загружали для этого приложения, и последним
  проект. Сборка, загруженная для пробника, на которой теперь работает другое живое
  приложение, остаётся, а её запись в `builds` называет это приложение в поле `kept`.
  Проект удаляется, только если в нём не осталось ни одной сборки и на нём не работает
  ни одно живое приложение, и никогда, если это проект из `ELEMENT_PROJECT_ID`: обычно
  пробник попадает в проект, которому принадлежат его исходники, то есть в рабочий, а
  проект, созданный самим пробником, остаётся пустым. Сборки, которые другие запуски
  загрузили в приложение пробника с другой машины и которых реестр не знает, остаются
  платформе: сборки, которыми никто не пользуется, она удаляет сама. Повторный запуск
  доделывает то, что оставил первый: приложение, которое уже стало надгробием, второй
  раз не удаляется, ведь перечень хранит его карточку, а уже удалённый проект не
  удаляется снова. Сам запуск ничего не собирает, поэтому ключи запуска пробника рядом с
  `--cleanup` отклоняются. Вывод: `ok`, `app-id`, `app-name`, `project-id`,
  `app-deleted`, `builds` (каждая – `{id, version, deleted}`), `project-deleted`,
  `project-kept` (почему проект оставлен) и `problems`; код возврата 0 только при `ok`.
- `branches list [--project-id --name]`, `branches get ID`,
  `branches create NAME [--project-id --app-id]`,
  `branches update ID [--app-id]`, `branches delete ID`,
  `branches merge ID`.
- `dumps create [APP_ID] [--description]`, `dumps get APP_ID DUMP_ID`.
- `tasks list [--app-id]`, `tasks get-group TASK_ID`.
- `tech get [APP_ID]`, `tech set APP_ID VERSION`.
- `debug-adapter` - путь к каталогу debug-адаптера платформы, принесённому
  плагином (группа точек расширения `elemctl.debug_adapter`, п. 10). Вывод
  `{"path": ..., "found": true, "adapter-class": ...}` при наличии либо
  `{"path": null, "found": false}`; код возврата 0 в обоих случаях. Значение
  `path` - готовое значение настройки `xbsl.debug.adapterPath` для расширения
  VS Code (каталог с подкаталогом `repo/`).
- `plugins` - диагностика: что приносят плагины. В `debug-adapter` идут
  объявленные каталоги адаптера и признак наличия jar. В `commands` - команды
  плагинов с точкой расширения, через которую они пришли, и именем инструмента MCP;
  там стоит `null`, когда команда в MCP не выходит. В `failures` – то, что осталось
  за бортом: плагин, который не загрузился, или команда, которая заняла бы имя
  ядра, и у каждого точка расширения и причина. Ответ выглядит так:
  `{"debug-adapter": [{"path": ...,
  "has-jars": true|false}], "commands": [{"name": ..., "source": ..., "mcp": ...}],
  "failures": [{"source": ..., "error": ...}]}`.
- Подкоманды, которые приносят плагины (п. 10, группа `elemctl.commands`), стоят
  наравне с командами ядра и видны в `--help`. Занять имя команды ядра они не могут;
  справочник команд описывает только ядро. Плагин, который не загрузился, остаётся
  за бортом и CLI не роняет (п. 10): каждая команда называет его в stderr, а вызов
  команды, которой нет, пока плагины не загрузились, получает отказ JSON в stderr
  с их перечнем в поле `plugin-failures`.
- `self-update [--version X]` - обновить установленный elemctl распаковкой колеса с
  PyPI в site-packages, не трогая занятые exe. Штатные pipx и pip ломают установку,
  когда `elemctl.exe` держит работающий MCP-сервер. Здесь обновляются только файлы
  пакета, а стаб exe вызовет новый код. Команда правит `pipx_metadata.json`. Вывод -
  `{updated, from, to}`. Без `--version` последняя версия спрашивается у всех источников
  PyPI. Оба списка выпусков, простой индекс и сводный JSON, кэшируются по узлам и после
  выпуска несколько минут могут называть предыдущую версию, поэтому команда читает оба,
  берёт более новый ответ и запрашивает страницы трёх следующих номеров (`0.44.1`, `0.45.0`
  и `1.0.0` после `0.44.0`): страница нового выпуска доступна сразу после публикации. Если
  источники расходятся, строка в stderr говорит, что назвал каждый. Установку новее всех
  источников команда оставляет как есть и более старым выпуском не заменяет. Версию из
  `--version`, которой ещё нет в индексе, команда ищет на её собственной странице, и только
  ответ 404 там значит, что такой версии нет.
- `mcp` - запустить MCP-сервер; без установленного extra - понятная ошибка
  с подсказкой `pip install "elemctl[mcp]"`.

Позиционные APP_ID и PROJECT_ID, помеченные выше как необязательные, при
отсутствии берутся из конфигурации: `ELEMENT_APP_ID` и `ELEMENT_PROJECT_ID`.
Если и там пусто, будет ошибка.

## 8. Требования к MCP-серверу

Имя сервера `elemctl`, транспорт stdio, реквизиты - из тех же переменных
окружения и `.env`. В instructions сервера надо предупредить о тихом откате
применения (п. 6.1). Инструменты, докстринги у них краткие и по-русски:

`list_apps(name="", status="", include_deleted=False)` - фильтры `apps list`
(п. 7): `name` по подстроке без учёта регистра на клиенте (п. 4.1), `status` по
статусу целиком, удалённые приложения скрыты, пока их не попросят. Ответ - объект
с полями `total`, `live`, `shown`, строкой `summary` и `applications`, так что
скрытое названо, а не угадывается; `get_app(app_id)` – карточка с полем
`applied-build`, как её печатает `apps get` (п. 7), `find_app(name)`,
`create_app(name, project_id="", version_id="", space_id="",
development_mode=True, verify=False)` - при задании только project_id источником
автоматически берётся последняя сборка проекта (п. 6.2); `verify=True` дожидается
приложения и проверяет, что оно работает на запрошенной сборке, складывая отчёт в
поле `verify` ответа (ту же проверку делает `ensure_app(verify=True)` – и для
созданного приложения, и для найденного); оборванное ожидание оставляет в ответе
ид созданного приложения рядом с полем `wait-error`, где лежит причина, а
`ensure_app` тогда отвечает `applied: null`; `version_id`, которого нет в перечне
сборок проекта, отвергается до создания, как в CLI (п. 7), а проект берётся из
`project_id` либо из `ELEMENT_PROJECT_ID` стенда; `create_app` и
`ensure_app` добавляют к ответу поле `sign-in` - способ войти в приложение
(п. 6.11) в том же виде, что печатает CLI: агент видит только JSON, значит
подсказка обязана быть там;
`start_app(app_id)`, `stop_app(app_id)`, `debug_info(app_id)` - данные для
сессии отладки (требует включённой отладки на сервере), `debug_adapter()` -
путь к debug-адаптеру платформы из плагина (п. 10; локальная операция, к
платформе не обращается), `delete_app(app_id)`
(в докстринге - предупреждение о необратимости и смене URL);
`app_id` у `get_app`/`delete_app`/`start_app`/`stop_app`/`debug_info` - ид
(UUID) либо точное имя приложения (резолв как в CLI); `list_spaces()`,
`list_projects(name="", include_deleted=False)` – фильтры `projects list` (п. 7),
`list_builds(project_id, limit=10, brief=True)` – объект `{total, shown, summary, builds}`:
перечень обязан сказать, весь ли это запас платформы, и судит об этом по пропускам в
нумерации сборок (п. 4.4), называя скачок, который объясняет локальный реестр
загрузок (п. 7), а краткая карточка называет, откуда её ветка и коммит – из
карточки или из локального реестра загрузок, как у `builds list --brief` (п. 7),
`get_build(project_id, version)` - карточка одной сборки целиком, адресуется версией
сборки (п. 4.4; ид принимается и разрешается через перечень),
`build_assembly(project_dir="", output_dir="", version="")`,
`inspect_assembly(file)` - разбор готового архива (п. 5.1; локальная операция),
`deploy(app_id, project_id, project_dir="", version="", branch="", allow_data_loss=False,
server_start_timeout=900)` - возвращает отчёт о развёртывании плюс поле `log` со строками
прогресса и пережидает сервер, который ещё стартует (п. 6.12); `allow_data_loss=True`
пропускает то, что отклоняет сторож схемы, как ключ `--allow-data-loss` в CLI (п. 7), а
без него отказ приходит ошибкой до сборки; `probe(project_dir="", space_id="", keep=False)` – изолированная
проверка компиляции, не трогающая рабочее приложение (п. 7): отчёт плюс поле
`log`; `probe_cleanup(app_id)` – `probe --cleanup` (п. 7), уборка пробника, оставленного
на стенде: отчёт плюс поле `log`; `apply_build(app_id, version_id)`, `verify_deploy(app_id,
expected_version="", since_minutes=30)` - проверка применения по п. 6.1;
`list_app_tasks(app_id="")`, `list_branches(project_id="", name="")`,
`merge_branch(branch_id)`, `list_user_lists(name="")` и
`configure_user_list(list_id="", app_id="", self_registration=None, password_login=None)` -
настройки входа списка пользователей (п. 4.7) одним вызовом: список задаётся ид,
представлением либо приложением, чей это список; оба флага необязательны, без них
инструмент только сообщает состояние (`self-registration-enabled`,
`password-login-enabled`, `changed`); `list_app_users(app_id)` – пользователи,
подключённые к приложению, как их показывает `apps users` (п. 7), объектом
`{app-id, total, summary, users}`; `token_access(app_id, user="", enabled=None)` –
доступ пользователя к HTTP-сервисам приложения по токену, как его показывает и переключает
`apps token-access` (п. 7): `app_id` обязателен, пустой `user` – учётная запись, под которой
работает elemctl, без `enabled` инструмент только читает;
`export_app(app_id, output="")` – сборка, на которой работает приложение, записанная в файл
так же, как это делает `apps export` (п. 7); пустой `output` – текущий каталог процесса
сервера;
`export_extension(app_id, extension, output="")` – сборка расширения, примененного в
приложении, записанная в файл так же, как это делает `apps export-extension` (п. 7); пустой
`output` – текущий каталог процесса сервера.

Рядом с ними регистрируются инструменты, которые приносят плагины (п. 10, группа
`elemctl.commands`): схема строится по объявленным аргументам, описание - `help`
команды, а параметр `env_file` добавляет само ядро. Имя, уже занятое инструментом
ядра, плагин не забирает: такая команда остаётся за бортом, как и плагин, который не
загрузился. Сервер называет их в stderr, который клиент хранит как журнал сервера, и
запускается с остальными.

## 9. Требования к качеству

- Тесты pytest без обращений к сети: разбор .env и приоритеты конфигурации,
  отбор файлов и содержимое архива сборки (включая манифест), автоинкремент
  и числовое сравнение версий, логика итога деплоя (`ok`/`applied`),
  подсказка при `FAILED_PRECONDITION`, поиск приложения по имени, обнаружение
  плагинов через точки расширения и разрешение пути к debug-адаптеру
  (стаб-точки расширения, каталоги во временных папках), извлечение адаптера
  из мини-.car, обновление распаковкой колеса (urllib замокан, колесо и
  site-packages во временных папках).
- Докстринги, комментарии и идентификаторы - английские, включая тесты и
  инструменты: проект публичный и международный. Русский остаётся там, где он
  обращён к пользователю: каталог сообщений i18n, справка argparse,
  user-facing строки, описания инструментов MCP и инструкция сервера, а также
  идентификаторы платформы в цитатах (`Проект.yaml`, `Ресурсы`, `Имя`,
  `Поставщик`) и русские данные тестовых фикстур. Кавычки в тексте прямые
  `"`, тире - среднее `–` (не длинное), многоточие - три точки `...`.
- Библиотека сама в stdout и stderr не печатает: прогресс она отдаёт через
  callback, который передаёт вызывающая сторона.
- Ошибки API поднимаются собственным исключением с деталями ответа сервера,
  сериализуемыми в JSON.

## 10. Плагины (точки расширения)

elemctl обнаруживает внешние пакеты через `importlib.metadata.entry_points`. В
собственном `pyproject.toml` ядро о плагинах ничего не объявляет: оно
потребитель и читает точки расширения при обращении. Так непубликуемые
вендорские артефакты, те самые проприетарные jar 1С, остаются в отдельном
пакете, а публичное ядро - чистым.

Группа **`elemctl.debug_adapter`**. Значением точки расширения бывает путь
(`Path` или `str`) либо функция без аргументов, возвращающая путь
(`() -> Path | str`). Путь указывает на каталог debug-адаптера платформы, то
есть на каталог с подкаталогом `repo/`, где лежат jar-файлы адаптера, среди них
`com.e1c.g5rt.debugger.adapter*.jar`. Это готовое значение настройки
`xbsl.debug.adapterPath` расширения VS Code.

Объявление в пакете-плагине:

```toml
[project.entry-points."elemctl.debug_adapter"]
имя = "мой_пакет:adapter_root"
```

Группа **`elemctl.commands`**. Значением точки расширения бывает `Command`, их
список либо функция без аргументов, возвращающая одно из двух. Одно объявление
служит обеим поверхностям: ядро строит по нему подкоманду CLI и инструмент MCP, а
о том, что команда делает, ничего не знает. Там место команде, которая знает про
чужое окружение: внутренние контуры, смежные системы, приватные стенды. В
публичном ядре такой команде жить нельзя.

```toml
[project.entry-points."elemctl.commands"]
имя = "мой_пакет.commands:commands"
```

Типы объявления экспортируются из `elemctl.plugins`:

- `Argument(name, help="", type=str, default=None, required=False, choices=(), cli_alias="")` -
  `name` это `"--stand"` для опции либо `"stand"` для позиционного аргумента. Имя
  значения, `dest`, получается из имени без ведущих дефисов, а внутренние дефисы
  заменяются подчёркиваниями, ровно как делает argparse. Типы - `str`, `int`,
  `float` и `bool`. Тип `bool` означает флаг: `store_true` в CLI и булево со
  значением по умолчанию `false` в MCP, поэтому позиционным он быть не может.
  Поле `required` действует для опции. Позиционный аргумент обязателен, пока
  `required=False` не сделает его необязательным. Поле `cli_alias` заводит у
  позиционного аргумента синоним-ключ, который действует только в CLI:
  `Argument("page", cli_alias="--page")` принимает и `wiki-get 123`, и
  `wiki-get --page 123`. Схема инструмента MCP при этом не меняется – у
  неё как был, так и остаётся один параметр `page`: синоним лишь удобство
  разборщика CLI, а не второй объявленный аргумент. CLI строит обе формы парой
  взаимно исключающих друг друга аргументов с одним `dest`: обе сразу, как и
  ни одной у обязательного аргумента, – отказ разборщика. У опции `cli_alias`
  быть не может – у неё уже есть имя, каким её вызывать.
- `Command(name, help, handler, arguments=[], mcp=True, mcp_name="")` - `name` это
  подкоманда CLI. Инструмент MCP называется `mcp_name` либо тем же именем с
  дефисами, заменёнными на подчёркивания. `mcp=False` оставляет команду только в
  CLI. Поле `source` заполняет обнаружение, подставляя имя точки расширения.
- `CommandContext` - то, что получает обработчик. В нём `config` - собранная
  конфигурация подключения; `client` - клиент платформы, который строится при
  первом обращении и кешируется, поэтому команда, не обращающаяся к платформе,
  реквизитов не требует; `log(message)` - строки прогресса: CLI печатает их в
  stderr по мере поступления, инструмент MCP собирает в поле `log` ответа.
  Поле `surface` называет, откуда позвали команду: `"cli"` - подкоманда,
  `"mcp"` - инструмент, это значения `SURFACE_CLI` и `SURFACE_MCP`. В
  контексте, собранном вне ядра, тестом или библиотечным вызовом, там `None`.
  Раньше плагин отличал одно от другого только по устройству `log`, а оно
  принадлежит ядру и может поменяться. Плагин, которому приходится работать
  и со старым ядром, читает поле как `getattr(context, "surface", None)`:
  там такого атрибута нет.

Обработчик вызывается как `handler(context, **values)`, а значения приходят по
`dest`. Его результат обязан быть JSON-сериализуемым: CLI его печатает,
инструмент MCP возвращает. Код возврата CLI тоже берётся из результата:

- словарь, в поле `exit-code` которого целое от 0 до 255, завершается этим кодом.
  `bool` целым здесь не считается, а диапазон – то, что процесс возвращает
  переносимо: POSIX оставляет от кода завершения только младшие восемь бит, и 256
  пришло бы как 0;
- иначе словарь с `"ok": false` завершается кодом 1, по тому же соглашению, что у
  отчётов `deploy` и `probe`, а любой другой результат – кодом 0;
- корректный `exit-code` сильнее `ok`: `{"ok": false, "exit-code": 0}` завершается
  кодом 0. Значение другого типа или вне диапазона не учитывается, и решает `ok`.

Имя поля экспортируется как `elemctl.plugins.EXIT_CODE_FIELD`: плагин, которому
приходится работать и со старым ядром, по отсутствию имени узнаёт, что код процесса
там зависит только от `ok`. Инструмент MCP возвращает поле `exit-code` нетронутым,
вместе с остальным результатом. Сам обработчик процесс не завершает: та же функция служит серверу MCP,
где `SystemExit` оставляет вызов без ответа и останавливает сервер. К инструменту
MCP ядро добавляет параметр `env_file`, как у всех инструментов ядра, а к
результату-словарю - поле `log` со строками прогресса.

Поведение обнаружения:

- точки сортируются по имени; `debug_adapter_path()` возвращает первый каталог,
  в котором действительно есть jar адаптера (каталог без `repo/` или без jar
  адаптера пропускается), иначе `None`;
- сбой загрузки точки расширения - ошибка `PluginError`, наследник
  `ElemctlError`, а не тихий пропуск: инструмент, молча потерявший плагин,
  оставил бы пользователя без отладки и без объяснения причины. Под защитой и
  загрузка точки, и вызов функции, которую она называет. Плагин, написанный под
  более новое ядро, падает как раз в этом вызове – `TypeError` о поле, которого
  установленное ядро ещё не знает, – и ошибка называет установленную версию;
- объявление команды проверяется при обнаружении, а не при запуске команды:
  пустое имя, невызываемый обработчик, неподдержанный тип аргумента, булев
  позиционный аргумент, повторяющиеся имена значений, `cli_alias` у опции,
  синоним без дефиса впереди и синоним, совпавший с чужим ключом, – всё это
  `PluginError`;
- аргумент не может занять общий флаг из п. 7, который CLI принимает в любой
  позиции: ни опцией, ни именем значения позиционного аргумента, ни `cli_alias`.
  Такой флаг CLI переносит перед подкомандой и разбирает сам, а подкоманда
  складывает значения туда же, где свои держит корневой разборщик, поэтому
  значение плагина либо не доходило до команды, либо подменяло значение ядра.
  Свой `env_file` плагина к тому же стал бы вторым у его инструмента MCP. Набор
  ровно тот, что переносит CLI, так что флаг, добавленный ядром, сразу закрыт для
  плагинов, а такое объявление – `PluginError`, как и перечисленные выше;
- аргумент не может занять и имя значения, которое в разборе команды держит сам
  CLI, – `command`, `handler`, `plugin_command`, `plugin_commands`,
  `plugin_failures`, – и ключ, на который подкоманда отвечает сама, `-h` и
  `--help`. Позиционный `handler` подменял функцию, которую вызывает CLI,
  строкой, набранной пользователем, и вызов кончался `TypeError`, а опция
  `--help` не давала собрать разборщик всего CLI – с голым
  `argparse.ArgumentError`. Оба перечня читаются с разборщика, который строит CLI,
  так что имя, которое ядро начнет держать, сразу закрыто для плагинов, а такое
  объявление – тоже `PluginError`;
- сбой остаётся при своём плагине. `discover_commands()` возвращает команды, которые
  загрузились, и `PluginFailure` на каждую точку, которая не загрузилась, – в
  `to_dict()` это `{source, error}`; одна плохая команда оставляет за бортом всю
  точку. `plugin_commands()` – строгая форма, она бросает первый сбой. CLI и
  MCP-сервер строятся из `discover_commands()`: сбойный плагин остаётся за бортом,
  а ядро и остальные плагины работают. Раньше один сломанный плагин не давал
  построить разборщик, не работала ни одна команда, даже команды ядра, а ответом
  была трассировка Python;
- занять имя, которое уже есть у ядра, плагин не может - ни подкомандой CLI, ни
  инструментом MCP. Такая команда остаётся за бортом, и о ней сообщается так же,
  как о плагине, который не загрузился; своё имя ядро сохраняет;
- переменная окружения `ELEMCTL_NO_PLUGINS=1` отключает обнаружение: остаются
  только штатные возможности ядра. Её ставит генератор справочника команд,
  поэтому справочник описывает только ядро.

Поверхности, использующие механизм: CLI `debug-adapter`/`plugins` (п. 7) и
подкоманды плагинов, MCP-инструмент `debug_adapter` (п. 8) и инструменты плагинов,
а также расширение VS Code, которое при пустой настройке `adapterPath` запрашивает
путь у `elemctl debug-adapter`.

Сам адаптер извлекается из дистрибутива платформы скриптом `tools/extract_adapter.py`
(чистый код, в дистрибутив пакета не входит – `prune`): каталог
`data/ide/theia/plugins/@1c-appengine-plugin/bin/debugger/` из `.car` копируется в
`<output>/<версия>/`, обновляется `index.json`. Проприетарные jar в публичный пакет не
включаются – их несёт отдельный пакет-плагин.
