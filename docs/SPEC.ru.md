# Спецификация elemctl

[English](SPEC.md) · **Русский**

Документ описывает контракт Console API v2 технологии 1С:Элемент (1cmycloud.com),
формат файлов сборки и требования к elemctl. Описания интерфейсов и условий
выполнения предназначены для разработчиков клиентов и расширений инструмента.

## 1. Назначение и состав пакета

Python-пакет `elemctl` состоит из трех слоев поверх общего ядра:

1. **Библиотека** - программный клиент Console API v2 и операции высокого
   уровня: сборка и развертывание. Только стандартная библиотека Python.
2. **CLI** - консольная команда `elemctl`, точка входа `elemctl` в
   `[project.scripts]`.
3. **MCP-сервер** - те же операции в виде инструментов для AI-агентов, транспорт
   stdio. Зависимость `mcp>=1.2,<3` подключается необязательным extra
   `elemctl[mcp]`. Используется серверный класс пакета `mcp`: `FastMCP` в
   mcp 1.x, `MCPServer` в mcp 2.x.

Пакет `elemctl` требует Python >= 3.10 и распространяется по лицензии MIT; автор – KeyFire. Исходники находятся в `src/elemctl/`, extra `dev` включает pytest. Первоначальная версия пакета – 0.1.0. Актуальная хранится в `elemctl.__version__`; pyproject.toml читает ее динамически.

## 2. Конфигурация подключения

Параметры берутся из трех источников, по убыванию приоритета:

1. явные аргументы (флаги CLI `--base-url`, `--client-id`, `--client-secret`);
2. переменные окружения;
3. .env-файл: путь из флага `--env-file`, а без него - файл `.env` в текущем
   каталоге, если существует.

Переменные окружения:

| Переменная | Смысл | Обязательна |
|---|---|---|
| `ELEMENT_BASE_URL` | базовый URL сервера с `http://` или `https://`, например `https://1cmycloud.com` | да |
| `ELEMENT_CLIENT_ID` | Client-Id для получения токена | да |
| `ELEMENT_CLIENT_SECRET` | Client-Secret | да |
| `ELEMENT_APP_ID` | приложение по умолчанию | нет |
| `ELEMENT_PROJECT_ID` | проект по умолчанию | нет |
| `ELEMENT_SPACE_ID` | пространство по умолчанию | нет |
| `ELEMENT_CA_FILE` | дополнительный PEM-файл CA для частного облака | нет |
| `ELEMENT_TLS_STRICT` | строгая проверка сертификатов по RFC 5280; по умолчанию `true` | нет |
| `ELEMENT_TLS_VERIFY` | проверка сертификата и имени сервера; по умолчанию `true` | нет |

Формат .env: строки `KEY=VALUE`. Пустые строки и строки, начинающиеся с `#`,
пропускаются. Перед именем допускается префикс `export `, а значение можно взять
в одинарные или двойные кавычки. Кодировка UTF-8, возможен BOM, поэтому читать
надо как `utf-8-sig`. Хвостовой слэш у `ELEMENT_BASE_URL` обрезается. Непустой базовый URL
должен начинаться с `http://` или `https://`.

## 3. Аутентификация

Получение токена: `POST {base}/console/sys/token`

- заголовок `Authorization: Basic base64(client_id:client_secret)`;
- тело `grant_type=client_credentials`, Content-Type
  `application/x-www-form-urlencoded`.

Ответ - JSON-объект, а токен лежит в первом непустом из полей `id_token`,
`token`, `value`, `access_token`. Особый случай: значение `access_token` бывает
строкой `"Not implemented"`. Это не токен, поле надо пропустить.

Все прочие запросы - с заголовком `Authorization: Bearer {токен}`.

Срок действия токена составляет около часа. Кешировать его надо в файле в системном каталоге
временных файлов, который дает `tempfile.gettempdir()`, а не в жестко прописанном
`/tmp`: инструмент работает и на Windows. Время жизни кеша - час, а ключ кеша
обязан различать пары base_url и client_id. На ответ 401 токен обновляют
принудительно и повторяют запрос один раз.

## 4. Контракт Console API v2

Общий префикс: `{base}/console/api/v2`. Тела запросов и ответов – JSON, кроме
загрузки сборки. Имена полей пишутся в kebab-case.

В справочнике консоли основной версией указана Console API 2.1 с префиксом
`{base}/console/api/v2.1`. Версия 2.0 также доступна. Клиент использует 2.0,
а к 2.1 обращается для работы с примененными расширениями (раздел 4.1).

Неподдерживаемый метод возвращает 401 с текстом
`Handler of HTTP request "[<метод>] <путь>" in application "console" not found.`
Этот ответ проверяется до обновления токена: клиент сообщает о неподдерживаемом
методе и не повторяет запрос токена. Для остальных ответов 401 токен обновляется,
затем запрос повторяется один раз.

### 4.1. Приложения

- `GET /applications` - список. Query-параметр `name` у метода есть, но Console API игнорирует его и возвращает полный список. Это проверено живым вызовом, поэтому по имени фильтрует клиент.
- `GET /applications/{id}` - карточка. Значимые поля ответа: `id`, `status`,
  `uri` (адрес работающего приложения), `error` (текст ошибки, если есть),
  `technology-version`, `date-updated`, `display-name`,
  `publication-context`, `source` (объект с информацией об источнике,
  содержит в т.ч. `project-version` - версию примененной сборки).
- `POST /applications` - создать. Тело:
  - `source` - объект `{"type": "repository"}` плюс ровно один из ключей:
    `project-version-id` (id сборки-источника) либо `image-id` (id проекта);
  - `display-name`, `publication-context` - имя и путь публикации;
  - `development-mode` - булево, создавать ли среду разработки;
  - необязательные `space-id`, `technology-version`.
- `DELETE /applications/{id}` - удалить.
- `PUT /applications/{id}/status/start` - запустить.
- `PUT /applications/{id}/status/stop` - остановить.
- `POST /applications/{id}/actions/debug` - данные для сессии отладки
  (`ApplicationDebugInfo`: `{"debug-token": ..., "debug-address": ...}`).
  Тело запроса пустое; требует включенной отладки на сервере
  (`config/debug.yml` `enabled: true`).
- `POST /applications/{id}/project/update` - применить сборку к приложению.
  Тело: `{"source": {"type": "repository", "image-id": "<id сборки>"}}`
  либо `{"source": {"type": "repository", "project-id": "<id>",
  "assembly-version": "<версия>"}}` (assembly-version необязательна). Сборку
  расширения принимает тот же метод и применяет рядом со сборкой приложения:
  `source.project-version-id` карточки по-прежнему называет сборку приложения, а
  расширение появляется в `extension-projects` метода 2.1 ниже, с версией сборки в
  `assembly-version`. Проверено вживую на применении, которое прошло, и на двух,
  после которых сервер выполнил откат.
- `POST /applications/{id}/project/export` – сборка, на которой работает приложение.
  Справочник описывает метод в 2.0 и в 2.1, живая проверка получила из обоих один и тот же
  архив. Тело запроса пустое, а ответ – сам архив, `application/octet-stream` без
  `Content-Disposition`: файлы сборки, среди них `Assembly.yaml`, упакованные заново, с
  отдельными записями для каталогов. Консоль берет архив у сервера приложения, так что это
  проект, который приложение исполняет. Расширений, примененных в приложении, в архиве нет:
  для них есть свой метод (методы 2.1 ниже). По исходникам консоли выгрузка приложения
  посреди обновления или после неудачного обновления отвечает сборкой, загруженной для
  этого обновления, и проверка на живом сервере во время обновления получила эту сборку.
  Манифест – тот, который сервер хранит для сборки: сборка, загруженная в проект,
  возвращается с номером, который дал ей сервер (п. 4.4), и временем загрузки в
  `Created`, а сборка, которая завела свой проект, – с манифестом своего архива.
  Обработчик 2.1 принимает и недокументированный параметр запроса `extension-id` и тогда
  отвечает сборкой этого расширения, как
  `/v2.1/applications/{id}/project/{ExtensionId}/export`; 2.0 параметр не читает.
  Контроллер допускает любого пользователя, прошедшего проверку подлинности, и читает
  приложение с правами этого пользователя.
- `POST /applications/{id}/dumps` - создать дамп. Тело: `include-users`,
  `include-binary-data` (булевы), `description` (строка).
- `GET /applications/{id}/dumps/{dumpId}` - статус дампа.
- `GET /applications/{id}/users` – пользователи, подключенные к приложению, каждый
  `{user-list-id, user-id, presentation, is-admin, token-access-enabled}`. Среди них и
  пользователи панели управления: их сервер подключает автоматически; в представлении такого пользователя используется логин. `token-access-enabled` – доступ пользователя к HTTP-сервисам
  приложения по токену. Без него вызов сервиса токеном этого пользователя получает 500
  "Token access is denied", какие бы права у пользователя ни были.
- `PUT /applications/{id}/users/change-token-access` – переключить этот доступ. Тело:
  `{"user-list-id", "user-id", "enable-access"}`, все три обязательны; ответ – подключение
  в том виде, в каком оно стало. Пользователю, не подключенному к приложению, сервер
  отказывает ответом 500 "Can't change user token access" и причины не называет, поэтому
  клиент сначала находит подключение, а если его нет, называет пользователя сам.
  Справочник описывает метод и в v2, и в v2.1 с одинаковым телом, живая проверка получила
  от обоих одинаковый ответ; клиент берет префикс v2, как и во всех остальных запросах.
- `GET /me` – пользователь, которому принадлежат реквизиты: `id`, `login`, `presentation`,
  `user-list-id`.
- `GET /v2.1/applications/{id}/project` – проекты, которые работают в приложении:
  `application-project` и примененные расширения в `extension-projects`. У расширения
  есть `id`, `project-id`, `assembly-id`, `enabled`, `order`, `vendor-name`,
  `project-name`, `project-presentation`, `project-version` и `assembly-version`. `id` –
  ид расширения на сервере приложения: `Ид` из `Проект.yaml` расширения, тот
  `configuration-id`, которым ответила его загрузка (п. 4.4). В `assembly-id` расширения
  указывается ид его проекта. Это подтверждено проверкой и исходниками консоли; поле не содержит ид сборки. Тот же путь в 2.0 отвечает одним проектом
  приложения.
- `POST /v2.1/applications/{id}/project/{ExtensionId}/export` – сборка примененного
  расширения. Тела у запроса нет, ответ – сам архив, `application/octet-stream` без
  `Content-Disposition`: файлы, с которыми сборку загрузили, `Assembly.yaml` в их числе,
  упакованные заново. Сегмент пути – `id` расширения из предыдущего метода, регистр букв
  не важен. Справочник называет параметр идентификатором проекта расширения, но на
  `project-id` сервер отвечает тем же ответом 500 без пояснения "Unable to export extension ... from
  application ...", что и на неизвестное значение, с "Contact administrator for details"
  в `details`. Остановленное приложение отдает сборку так же, удаленное получает 404 уже
  на перечне. В 2.0 такого метода нет: `/v2/...` получает 401 отсутствующего обработчика.
  Контроллер консоли допускает любого пользователя, прошедшего проверку подлинности (`PermitAuthenticated`) и
  читает приложение с правами этого пользователя.

Статусы приложения делятся на две группы:

- стабильные: `Running`, `Stopped`, `Error`;
- переходные: `Starting`, `Stopping`, `Initializing`, `Updating`, `Frozen`,
  `Creating`, `Deleting`.

Во время перехода поле `status` может быть пустым. Справочник определяет это поле
как строку без перечня значений; приведенный список составлен по результатам
проверок на стендах. Статус `Deleting` сохраняется во время задачи
`DeleteApplication`. После ее завершения запись остается в списке со статусом `Deleted`.

Статус `UNKNOWN` наблюдался у приложения с отсутствующими файлами базы. Запуск
и удаление были недоступны, поскольку удаление начинается с выгрузки данных.
Консоль использует `UNKNOWN` для состояния сервера приложения, которому
не сопоставлено имя статуса. Это не подтверждает окончательное состояние.
Клиент не относит его к стабильным или переходным: если `UNKNOWN` сохраняется
минуту подряд, ожидание прекращается с сообщением об этом статусе.

### 4.2. Версия технологии

- Чтение - из поля `technology-version` карточки приложения (отдельный
  endpoint чтения есть не во всех версиях сервера - не использовать).
- Обновление: `POST /tasks/group-tasks/update-applications-technology`,
  тело `{"technology-version": "<версия>", "applications": ["<app-id>"]}`.
  Возвращает групповую задачу; ее статус - `GET /tasks/group-tasks/{taskId}`.

### 4.3. Пространства и проекты

- `GET /spaces` - список пространств.
- `GET /projects` - список проектов; `GET /projects/{id}` - карточка;
  `DELETE /projects/{id}` - удаление. Перечень отдается целиком, каким бы ни был
  query, а удаленные проекты остаются в нем с признаком `deleted` и прежним ид.
  Отбор по имени и скрытие удаленных - работа клиента, как и у приложений (п. 4.1).
  В карточке проекта нет статуса. Состояние определяется по признаку `deleted`. Вид проекта указан в `project-kind`: `Application`, `Library`
  или `Extension`, а `Group` - у группы проектов, которая включается в список вместе с ее участниками.

### 4.4. Сборки проекта (assemblies)

- Загрузка файла сборки - бинарный POST (Content-Type
  `application/octet-stream`, тело - байты файла):
  - `POST /projects/{id}/assemblies` - добавить сборку в существующий проект;
  - `POST /projects` - создать новый проект из сборки либо добавить сборку в
    проект с тем `Ид`, что записан в ее `Проект.yaml`;
  - `POST /spaces/{space-id}/projects` - то же, но новый проект заводится в
    этом пространстве.
#### Параметры загрузки

Пространство для загрузки в существующий проект задается необязательным
query-параметром `space-id`. При проверке сервер вернул 400 для значения, не
соответствующего UUID, и 404 для неизвестного пространства. Параметр `SpaceId`
в PascalCase игнорируется.

У `POST /projects` параметр пространства не описан и не обрабатывается ни в одном
написании: запрос с `space-id=not-a-uuid` создал проект. Для создания проекта
в определенном пространстве используется `POST /spaces/{space-id}/projects`.
Неизвестное пространство возвращает 404. Если проект с `Ид` сборки уже существует,
сборка добавляется в него, как при `POST /projects`.

Для `POST /projects/{id}/assemblies` коммит передается параметром `commit-id`
и сохраняется в карточке сборки. Проверка схемы следующего развертывания
сравнивает исходники с этим коммитом. Параметры `branch-name`, `commit-message`
и `modified` также описаны и принимаются сервером, но не выводятся в карточке.
`branch-name` означает ветку групповой разработки, а не git. Значение `modified=1`
возвращает 500. Параметры `CommitId`, `BranchName` и `CommitMessage` в PascalCase
игнорируются. Для `POST /projects` параметр коммита не описан; у сборки, создающей
проект, коммит в карточке отсутствует.

elemctl передает только коммит. Ветка, признак незакоммиченных изменений и каталог
исходников записываются в локальный реестр загрузок.

#### Нумерация загруженных сборок

`POST /projects/{id}/assemblies` не использует версию архива. Базовая версия
читается из `Версия` описания проекта. Номер сборки равен наибольшему когда-либо
выданному номеру этой базовой версии плюс один. В проверках получены такие результаты:

| Версия архива | Версия после загрузки |
|---|---|
| `1.0.0-i1` | `1.0.0-1` |
| `1.0.0-10001` | `1.0.0-2` |
| `1.0.0-2`, уже существующая в проекте | `1.0.0-3` |
| `1.0.1-7`, при `1.0.0` в описании проекта | `1.0.0-502` |

Удаление сборки не уменьшает счетчик. После удаления `1.0.0-4` с конца списка
следующей стала `1.0.0-5`. После удаления `1.0.0-50` и `1.0.0-51` следующая
загрузка получила `1.0.0-52`, хотя список заканчивался на `1.0.0-8`. Удаление
сборки из середины списка также не изменяет счетчик. Сам счетчик через API
недоступен: в карточке проекта его нет, удаленные сборки не перечисляются,
а запрос карточки удаленной сборки возвращает 404. Назначенный номер доступен
в `assembly-version` ответа на загрузку.

Загрузка без ид проекта, `POST /projects`, сохраняет версию архива, включая
нечисловой суффикс. Если версия уже существует, возвращается 409. Номер удаленной
сборки можно использовать повторно, но счетчик проекта не уменьшается: после
повторной загрузки архива `1.0.0-2` следующая загрузка в проект получила
`1.0.0-8`, а не `1.0.0-3`. Таким образом, суффикс с номером запуска CI сохраняется
при загрузке без ид проекта, но не при загрузке в проект по его ид.

Команда `elemctl deploy` до сборки предупреждает, если сервер изменит заданную
версию. После загрузки выводится фактически назначенная версия. Без явной версии
используется больший номер из списка сборок и локального реестра загрузок.
Реестр содержит номера сборок этой машины, включая впоследствии удаленные.
Если сборка была загружена с другой машины и удалена, ее номера может не быть
в обоих источниках. В таком случае сообщение после загрузки указывает,
что номер назначен сервером.

#### Проект в ответе на загрузку

Ид созданной сборки читается из `image-id`, `assembly-id` или `id` в этом порядке.
Объект `artifact` содержит сведения о проекте:

- `artifact-id` – ид, по которому доступна карточка проекта;
- `configuration-id` – `Ид` из `Проект.yaml`;
- `name` – представление проекта.

В панели проект отображается под `Представление` последней загруженной сборки,
а не под `Name` из манифеста. Это подтверждено загрузками с одним `Ид`
и разными `Name` и представлениями. Сборка с другим именем переименовывает проект
без отдельного сообщения сервера; следующая сборка с прежним именем возвращает его.
Переименование затрагивает проект и его группу; удаление сборки не возвращает
прежнее имя. Если несовпадение известно до загрузки, `builds upload` отклоняет
операцию без `--force-rename`. Проверка вспомогательная: если манифест не читается
или карточка проекта недоступна, загрузка продолжается без сравнения имен.

Загрузка без ид проекта также может переименовать существующий проект. Сервер
выбирает его по `Ид`, а отдельного метода поиска по этому полю нет. Поэтому
`builds upload` читает список проектов до загрузки и сравнивает с ним `artifact`
ответа. В результате указывается выбранный проект, признак его создания
и предупреждение о переименовании.

- **Проект опознается по `Ид` из `Проект.yaml`**, возвращаемому в `configuration-id`.
  При `POST /projects` сначала ищется действующий проект с этим `Ид` в пространстве
  загрузки, затем в остальных пространствах. Если он найден, сборка добавляется
  в него независимо от поставщика и имени в манифесте. Ид выбранного проекта
  возвращается в `artifact-id`.

  Пара `Vendor` + `Name` должна быть уникальна среди проектов пространства.
  В проверке сборки `acme/crm`, `acme/crm-next` и `globex/crm` с одним `Ид`
  включались в один проект и изменяли его имя. Сборка `acme/crm` с новым `Ид`
  получила 409.

  Ответ 409 `ALREADY_EXISTS` имеет две причины:

  - версия уже загружена: "Версия сборки ... уже присутствует в группе проекта";
  - новый `Ид` использует занятую пару поставщика и имени:
    "Сборка с именем поставщика ... уже зарегистрирована в другом проекте".
    Начатое создание проекта с таким `Ид` отменяется.

  В исходниках консоли поиск по `Ид` выполняет `FindProjectById`. При проверке
  назначение сборок в существующий проект подтверждено также для
  `POST /spaces/{space-id}/projects`. Для отдельного временного проекта тех же
  исходников необходимы новый `Ид` и новая пара поставщика и имени.

- `GET /projects/{id}/assemblies` - список сборок. Элемент содержит
  `assembly-version`, строку вида `1.0-42`, и id в поле `id` либо `image-id`.
  Ответ приходит массивом или объектом, у которого список лежит в поле `items`
  или `assemblies`. **Страниц у метода нет, и общего числа он не сообщает.**
  Параметры `limit`, `size`, `pageSize`, `count`, `top`, `maxResults`, `page`,
  `pageNumber`, `offset`, `skip`, `from` и `start` метод игнорирует: ответ на
  все эти запросы совпадает побайтно, а ни в заголовках, ни в теле нет ни
  счетчика, ни курсора. Проверено живыми вызовами на двух установках.
**Консоль автоматически удаляет сборки, которыми никто не пользуется, независимо
  от возраста.** Проверка выполняется, когда приложение заканчивает применение
  сборки. Фоновое задание обрабатывает сборки проекта этого приложения с той же
  базовой версией, что у примененной сборки. За одно применение удаляется
  не больше десяти сборок. Сохраняются:

  - релизные и защищенные сборки;
  - сборка проекта по умолчанию;
  - сборки работающих приложений и сборки, загруженные в приложения;
  - сборка с наибольшим номером этой базовой версии.

  Сборка, загруженная без ид проекта (`POST /projects`), защищена с момента
  создания, как и сборка, из которой создан репозиторий проекта. Загрузка
  в проект по ид (`POST /projects/{id}/assemblies`) не устанавливает защиту.
  Библиотечная сборка без оставшихся зависимых сборок удаляется вместе со своей группой.

  Сборки проекта расширения автоматически не удаляются. Применение расширения
  запускает то же обновление, но последующая очистка проверяет проект и базовую
  версию приложения. Проект расширения сохраняет сборки до ручного удаления
  или удаления вместе с проектом.

  Это подтверждено проверкой: приложение работало на `1.0.0-1`, а в его проект
  по ид были загружены `1.0.0-2` и `1.0.0-3`. В проекте расширения находились
  сборки с `1.0.0-1` по `1.0.0-4`. Применение расширения `1.0.0-2` удалило
  `1.0.0-2` из проекта приложения и не удалило сборки расширения. Последующее
  применение `1.0.0-4` сохранило сборки расширения `1.0.0-2` и `1.0.0-3`.

  Проект, к приложениям которого сборки не применяются, сохраняет все сборки.
  Заранее загруженная сборка защищена номером только пока он наибольший.
  Отдельная проверка девяти сборок подтвердила исходники консоли из дистрибутива:

  - создание приложения за две минуты наблюдения ничего не удалило;
  - применение `1.0.0-3` до возврата ответа удалило `1.0.0-2`, `1.0.0-4`
    и `1.0.0-11`; сохранились `1.0.0-1` и `1.0.0-10`, загруженные без ид
    проекта, примененная `1.0.0-3`, наибольшая `1.0.0-12` и обе сборки `2.0.0`;
  - применение `1.0.0-12` удалило `1.0.0-3`;
  - применение `2.0.0-1` ничего не удалило, включая `1.0.0-12`, поскольку
    очистка относилась только к базовой версии `2.0.0`.

  Ранее из семнадцати сборок дневной серии осталась только примененная, а первая
  сборка проекта двухмесячной давности сохранилась: она была загружена без ид
  проекта. Клиент должен описывать ответ как перечень сохранившихся сборок,
  а не историю проекта или страницу истории.

- `GET /projects/{id}/assemblies/{version}` - карточка сборки, `DELETE
  .../{version}` - удаление. Последний сегмент - это версия, как метод ее и
  называет: `assembly-version` или `project-version`, строка вида `1.0-42`. Ид
  карточки сюда не подходит: на UUID метод отвечает 404 "Assembly with version
  <uuid> not found". Проверено живыми вызовами на двух установках разного
  возраста, ведут себя одинаково. При этом ид - тоже адрес, который есть на
  руках: его печатает перечень сборок и возвращает загрузка. Поэтому `elemctl`
  принимает обе формы. Версия определяется по списку сборок. Если значения нет
  ни в одной карточке, возвращается сообщение об отсутствующей сборке,
  а если адрес отклонен с 400 или 404, пробует сегментом и ид - на случай
  установки, которой нужна эта форма. Версия сборки, загруженной в проект, – номер,
  который дал сервер, а не версия ее архива. Удаление сборки сервер отклоняет с
  500, пока существует созданное из нее приложение. После его удаления тот же
  запрос выполняется успешно. Сборка, использованная только при применении,
  включая применение с последующим откатом, может быть удалена. Ответ 500
  не означает ошибочный формат адреса: он возвращается вызывающей стороне
  без повторной попытки с другой формой адреса.

Версии сборок сравнивают по числовому суффиксу после последнего дефиса: `1.0-10`
новее, чем `1.0-9`. Лексикографическое сравнение дает неверный порядок.

### 4.5. Ветки среды разработки

- `GET /branches` - список; необязательные query `project-id`, `name`.
- `GET /branches/{id}` - карточка. Поля: `name`, `kind`, `project`,
  `application`, `source-branch`, `deletion-mark`, `version-stamp`.
- `POST /branches` - создать. Тело: `name`, `kind: "development"`,
  `project: {"id": "<id>"}`, необязательно `application: {"id": "<id>"}`.
- `PUT /branches/{id}` - изменить. Сервер использует оптимистическую блокировку,
  поэтому сначала прочитайте карточку, а затем отправьте тело, собранное из
  текущих значений. Это `name`, `kind`, `deletion-mark` и `version-stamp`,
  который обязательно вернуть как есть. Поля `source-branch` и `application`
  свернуть до `{"id": ...}`, а если ид нет, то до `{"name": ...}`. Чтобы
  перепривязать ветку к приложению, замените `application` на
  `{"id": "<новый app-id>"}`.
- Изменения ветки принимает тот же `PUT /branches/{id}` с дополнительным ключом
  тела `write-parameters: {"merge": true}`.
- `DELETE /branches/{id}` - удалить ветку.

Инструмент работает только с документированным Console API v2. Внутренние, то
есть недокументированные, API консоли управления он не использует и не описывает.

### 4.6. Задачи приложений

`GET /tasks/application-tasks` - список задач всех приложений. Серверного фильтра
нет, фильтровать приходится на клиенте. Поля задачи: `id`, `application-id`,
`status` (в т.ч. `Error`, `Failed`), `operation-type`, `error-message`,
`start-date` (ISO 8601, может оканчиваться на `Z`).

### 4.7. Списки пользователей

Список пользователей держит либо пользователей приложения, у которого список
свой и назван по нему, либо пользователей панели управления, где список один на
установку. В этом списке хранятся настройки входа из панели управления.

- `GET /user-lists` - список списков: `id`, `presentation`, `space-id`. Фильтра
  по имени на сервере нет, фильтровать приходится на клиенте.
- `GET /user-lists/{id}` - полная карточка: `self-registration`,
  `password-policy`, `password-policy-enabled`, `account-services-settings`,
  `confirmations`, шлюзы, `include-personal-data-in-messages`.
- `GET|PUT /user-lists/{id}/settings/self-registration` -
  `{enabled, phone-required, email-required}`. Это и есть "Разрешить
  пользователям регистрироваться самостоятельно" из панели. PUT требует объект
  целиком.
- `GET|POST /user-lists/{id}/settings/account-services-settings`,
  `PUT|DELETE .../{account-service-id}` - сервисы учетных записей списка. Запись:
  `{account-service-id, account-service-type, local-id, enabled,
  create-user-on-auth, additional-settings}`. Тип `Local` аутентифицирует
  паролем, поэтому "Разрешить вход по логину и паролю" из панели - это его
  `enabled`. Остальные типы внешние: `OIDC`, `Cas`, `ActiveDirectory`, `Esia`.
  PUT требует запись целиком.
- `GET /applications/{id}/userlists` - ид списков, подключенных к приложению;
  `POST` подключает, `DELETE` отключает. Обратите внимание на написание: здесь
  без дефиса. Настроек подключения там нет: связь это множество ид и ничего
  больше.
- `GET /user-lists/{id}/users` – пользователи списка, среди полей `id` и `login`. Запись содержит токены доступа пользователя и секреты, поэтому клиент берет из нее
  только ид.
- Собственный список приложения назван в карточке приложения полем
  `default-user-list`. Это список его пользователей, а список панели, тоже к нему
  подключенный, отдельный.

Следующие настройки доступны только в панели управления:

- состава форм аутентификации приложения в API нет;
- настройка подключения "пользователи списка подключаются к приложению
  автоматически при входе" тоже не представлена. Ее нет ни в `userlists`,
  который есть множество ид, ни в `account-services-settings` приложения: с
  включенной настройкой там ничего не появляется.

Правила разбора ответа сервиса учетных записей принимаются в теле сервиса под
ключом `userPropertiesCalculationRules`. Это `presentation-rule`, `email-rule`,
`phone-rule` и `response-kind`, все они JsonPath или XPath. Ловушек здесь две.
Схема справочника называет то же самое `calculation-rules`, и на такое написание
сервер возвращает 400. А GET правила не возвращает никогда: настройка только на
запись, и подтвердить ее применение клиентом API нельзя.

## 5. Формат файла сборки (.xasm / .xlib)

Файл сборки - ZIP-архив (deflate):

- в корне `Assembly.yaml` - манифест, плоские пары ключ-значение:

  ```
  ManifestVersion: 1.0 | 1.1
  ProjectKind: Application | Library | Extension
  Vendor: <поставщик>
  Name: <имя проекта>
  Version: <версия, например 1.0-42>
  Created: <UTC, формат YYYY.MM.DD HH:MM:SS>
  BranchName: <имя git-ветки>
  CommitId: <хэш коммита>
  ```

  Для библиотеки (`ProjectKind: Library`) в конце добавляется строка
  `Release:` (пустое значение); расширение файла `.xlib`, для приложения и
  расширения – `.xasm`.

  Расширение (`ProjectKind: Extension`) пишется с `ManifestVersion: 1.1`, остальные виды –
  с `1.0`. Читателя манифеста сервер выбирает по его версии, а обработчик версии 1.0 поддерживает только
  `Application` и `Library`: применение расширения с манифестом 1.0 отклоняется с ошибкой
  "Неизвестный вид проекта: \"Extension\"". Ту же пару консоль пишет расширению, которое
  создает сама. Расширение, собранное так, на живом сервере применено через
  `project/update` и выгружено обратно файл в файл (п. 4.1).

- далее файлы проекта путями `{vendor}/{name}/...` относительно корня
  репозитория. Каталог проекта обязан лежать по схеме
  `{repo}/{vendor}/{name}/Проект.yaml`. Для приложения и расширения рекурсивно
  включаются библиотеки из `Библиотеки`/`Libraries`, которые доступны локально: консоль
  дает расширению библиотеки так же, как приложению. Расширяемые проекты из
  `РасширяемыеПроекты`/`ExtendedProjects` библиотеками не являются и в архив не попадают.
  Объявленная библиотека без проекта под тем же корнем репозитория остается внешней зависимостью приложения 1С:Элемента. Неподключенные соседние проекты не включаются.
  Разделители путей в архиве - прямые слэши, и на Windows тоже.

Имя файла сборки: `{Имя} {Version}.xasm` (через пробел).

Метаданные проекта берутся из `Проект.yaml`. Это YAML, и достаточно разобрать
плоские пары "ключ: значение" верхнего уровня, а вложенные строки с отступом
пропустить. 1С:Элемент поддерживает двуязычные исходники, дескриптор с
английскими ключами применяется штатно, поэтому каждый ключ читается в обоих
написаниях: `Имя`/`Name`, `Поставщик`/`Vendor`, `Версия`/`Version` (базовая,
например `1.0`) и `ВидПроекта`/`ProjectKind`. Значение `Библиотека` или
`Library` означает библиотеку, `Расширение` или `Extension` – расширение, все прочее –
приложение. Если встретились сразу
оба написания ключа, используется русское значение. Двуязычны и имена служебных файлов:
конвертер 1С:Элемента принимает `Project.yaml` и `Проект.yaml`, `Subsystem.yaml`
и `Подсистема.yaml`. Поэтому дескриптор ищется обоими именами везде: при поиске
проекта, при поиске локальных библиотек-зависимостей, при разборе архива и при
проверке доступности коммита стражем схемы.

Если версия сборки не задана явно, она собирается как `{базовая версия}-{N+1}`,
где N - счетчик из версии последней сборки проекта той же базовой версии.
`deploy` берет за N больший из двух номеров: номер последней сборки в перечне и
наибольший номер проекта, сохраненный в локальном реестре загрузок для этой базовой версии. Сервер считает от наибольшего номера, какой он когда-либо выдавал, считая
и удаленные сборки (п. 4.4). Проект, поднятый на новую базовую версию, снова
начинает с `-1`, какие бы номера ни
набрала старая база. Когда последней сборки этой базы нет, суффикс берется из
номера запуска CI в окружении: первое числовое значение из `CI_PIPELINE_IID`,
`GITHUB_RUN_NUMBER`, `BUILD_NUMBER`, в указанном порядке. Иначе чистый рабочий
каталог CI давал бы `-1` каждый раз. Нет и номера CI - остается
`{базовая версия}-1`.

Git-метаданные, то есть хэш коммита и имя ветки, берутся из git-репозитория,
который содержит каталог проекта. Если git недоступен, поля остаются пустыми.

Отбор файлов в архив:

- внутри каталогов `Ресурсы`, на любом уровне и в их подкаталогах, включаются
  файлы любых расширений: по документации 1С:Элемента ресурс - это произвольный
  файл, например `.pdf`, `.htm`, `.mxl`, `.docx`, `.xsd`;
- вне каталогов ресурсов включаются только расширения: `.yaml .xbsl .xbql
  .md .txt .json` (исходники), `.png .svg .jpg .jpeg .gif .webp .ico`
  (изображения), `.css .htm .html .js .woff .woff2 .ttf .eot` (веб-ресурсы);
- файлы описания клиента SOAP-сервиса включаются, где бы они ни лежали:
  `<ИмяКлиента>.Wsdl.<n>` и `<ИмяКлиента>.Xsd`. Файлы расположены рядом с элементом проекта вне каталога ресурсов. Переименование не поддерживается, поэтому используется отбор по имени, а не по расширению;
- исключаются каталоги `.git`, `.claude`, `.github`, `__pycache__`,
  `node_modules`, `.venv` и все скрытые (начинающиеся с точки);
- исключаются файлы `.gitignore`, `.env`, `.DS_Store`, а также `*.xasm` и
  `*.xlib`, в том числе внутри каталогов ресурсов.

### 5.1. Разбор готового архива

Операция, обратная сборке: по файлу `.xasm` или `.xlib` читаются манифест,
свойства проекта из его `Проект.yaml` внутри архива и состав. Она нужна, чтобы
подключить библиотеку к проекту, не разворачивая ее исходники.

Структура проекта определяется по каталогам:

- каталог первого уровня - это **подсистема**. Файл `Подсистема.yaml` или
  `Subsystem.yaml` **необязателен**, у подсистемы библиотеки он может отсутствовать, поэтому при поиске подсистем на него опираться нельзя;
- вложенный каталог подсистемы - это **пакет**. Файла-описания у пакета нет, и
  каждый каталог дает сегмент имени;
- полное имя типа: `{vendor}::{name}::{подсистема}[::{пакет}]::{ИмяТипа}`. То же
  имя без последнего сегмента указывается в `Использование` и `импорт`.

Наружу, в подключивший проект, видны только типы с `ОбластьВидимости:
Глобально`, по-английски `VisibilityScope: Global`. По умолчанию стоит
`ВПодсистеме`, он же `InSubsystem`, а глобальная область пишется явно. У
английского дескриптора английские и значения перечислений, поэтому значения
читаются в обоих написаниях.

Совместимость проверяется по свойству `РежимСовместимости` файла `Проект.yaml`.
Свойства `ВерсияТехнологии` в `Проект.yaml` **не существует**: оно относится к
телу запроса Console API на создание приложения, а не к файлу проекта.

## 6. Особенности работы сервера

1. **Откат без сообщения.** При ошибке применения сборки, например ошибке компиляции,
   сервер восстанавливает предыдущую сборку и запускает приложение. Статус
   `Running` не подтверждает применение. Для проверки:
   - получить задачи приложения из раздела 4.6 со статусом `Error` или `Failed`,
     у которых `start-date` не раньше начала развертывания;
   - сравнить `source.project-version` карточки приложения с загруженной сборкой;
   - для расширения проверить версию и `enabled` в `extension-projects` метода
     `GET /v2.1/applications/{id}/project`. Карточка приложения содержит только
     сборку самого приложения. Без Console API 2.1 применение расширения остается
     непроверенным; это не подтверждает откат;
   - дополнительно выполнить GET по `uri`. Для закрытых приложений ответы
     401 и 403 допустимы.
2. **Создание без данных проекта.** При некоторых настройках сервера источник
   "проект", то есть `image-id` с ид проекта, создает пустое приложение. Для
   получения данных проекта указать конкретную сборку в `project-version-id`,
   например последнюю сборку.
3. **Удаление с неопубликованными изменениями.** Если в среде разработки есть
   такие изменения, `DELETE /applications/{id}` возвращает 400
   `FAILED_PRECONDITION`. Принудительного удаления в API нет; используется
   панель управления. Клиент должен сообщить об этом ограничении.
4. **Готовность нового приложения.** После создания приложение некоторое время
   находится в переходном статусе без `uri`. Необходимо дождаться стабильного
   статуса и появления `uri`. При `Error` ожидание прекращается с ошибкой.
5. **Перезапуск после применения.** `project/update` может перезапустить
   приложение. После вызова дождаться окончания переходного статуса. Если итог
   отличается от `Running`, остановить приложение, если оно еще не `Stopped`,
   дождаться `Stopped`, затем запустить и дождаться `Running`. Ориентиры ожидания:
   3 минуты для остановки, 5 минут для запуска и стабилизации, опрос каждые 10 секунд.
6. **Окончательный статус `Error`.** При стабильном `Error` вернуть ошибку
   и тексты задач приложения. Не следует перезапускать приложение или ожидать
   другого статуса: из `Error` оно не переходит в `Stopped`, и ожидание
   завершится только по предельному сроку.
7. **Windows.** Для временных файлов и кешей использовать `tempfile`. Для stdout
   и stderr установить UTF-8 через `reconfigure`, чтобы сохранить кириллицу.
8. **Идентификация проекта.** Проект опознается по `Ид` из `Проект.yaml`.
   Пара `Vendor` + `Name` должна быть уникальна среди проектов пространства.
   Загрузка без ид проекта может добавить сборку в существующий проект
   с таким `Ид`; создание нового проекта не гарантируется.
9. **Фоновое удаление.** `DELETE /applications/{id}` возвращает ответ до окончания
   задачи `DeleteApplication`. Пока приложение существует, удаление исходной
   сборки завершается 500. Сначала удалить приложение, дождаться 404 при запросе
   его карточки или статуса `Deleted`, затем удалить сборку.
10. **Серверная компиляция.** Локальная сборка упаковывает архив. Проверки
    синтаксиса, типов и видимости выполняются серверным компилятором при
    применении сборки или создании приложения. Отдельного метода компиляции нет.
    Команда `elemctl probe` загружает исходники в их собственный проект с
    одноразовой версией, создает временное приложение для компиляции и удаляет
    оба объекта после проверки. Рабочее приложение не изменяется.
11. **Вход в новое приложение.** У приложения собственный пустой список
    пользователей, указанный в `default-user-list`. Вход по паролю выключен,
    сервис учетных записей отсутствует. Подключение списка другого приложения
    через `POST /applications/{id}/userlists` и включение локального входа
    не обеспечивают вход учетными записями других приложений. Для входа используется
    учетная запись панели управления: ее пользователи подключаются сервером
    автоматически. Способ входа не виден из карточки; подбирать учетную запись
    не следует, поскольку учитываются неудачные попытки.
12. **Запуск сервера.** После запуска или обновления консоль может быть
    недоступна несколько минут; после одного обновления ожидание составило
    тринадцать минут. Все запросы, включая получение токена, возвращают 404
    с текстом `Application "console" not found`. От отсутствующего приложения
    или сборки этот случай отличается текстом ответа. elemctl сообщает о запуске
    сервера; повторный запрос возможен после ответа 302 от `/console`.
    Команда `deploy` ожидает до `--server-start-timeout` секунд, по умолчанию 900;
    значение 0 отключает ожидание. После доступности консоли выполнение
    продолжается. Повтор отклоненного запроса безопасен: консоль его не обработала.
13. **Удаление данных при изменении исходников.** Удаление табличной части из
    исходников приводит к удалению ее строк при применении без предупреждения.
    Это проверено на справочнике с одной строкой в табличной части: задача
    завершилась успешно, приложение продолжило работу. Аналогично удаляются
    реквизиты табличных частей и объектов со значениями, а также весь справочник
    при отсутствии его описания; последнее проверено на пустом справочнике.
    Пересоздание описания под теми же путем и именем с новым `Ид` также удаляет
    данные: после проверки справочник с двумя строками оказался пустым при
    успешной задаче применения.

    Сужение длины и смена типа пересоздают данные объекта. `elemctl deploy`
    отклоняет эти изменения без явного разрешения, как и полное удаление
    справочника, документа или регистра. При удалении реквизита или табличной
    части команда до сборки перечисляет удаляемые данные и продолжает выполнение.

## 7. Требования к CLI

Общие флаги принимаются в любой позиции, в том числе после подкоманды:
`--base-url`, `--client-id`, `--client-secret`, `--env-file`, `--timeout`
(секунды, по умолчанию 60), `--lang`, `--json`, `--quiet`. Флаг `--version` –
исключение, он ставится до подкоманды.

Ключ, который принимает одно значение, нельзя повторить с другим значением:
разборщик отвергает такой вызов до запуска команды, с кодом 2, как любой отказ
argparse, и называет ключ и оба значения. Раньше `--output a --output b` писал
в `b`, и ничто не говорило, что `a` отброшено. Повтор с тем же значением
проходит: скрипт, который собирает командную строку из частей, вполне может
повторить ключ. `--key=value` и `--key value` считаются одним ключом. Значения
сравниваются такими, какими их получит команда, поэтому `--limit 5` и
`--limit 05` совпадают. Правило касается общих флагов, где бы они ни стояли,
ключей каждой команды и ключей, объявленных плагином (п. 10). Ключи, которые
повторяют намеренно (`apps list --status`, `apps token-access --user`,
`probe --cleanup` и аргумент плагина с `multiple`), собирают все значения, а
флаг, названный дважды, значит то же, что и один раз.

Флаги подключения используются для запросов к серверу. Команды `build` и
`inspect` выполняются локально, поэтому отклоняют такие флаги, включая
`--env-file`, до выполнения. Ошибка содержит команды для работы с сервером:
`deploy` и `builds upload`. Ограничение относится только к флагам. Переменные
`ELEMENT_*` и файл `.env` рядом с проектом не должны влиять на локальную сборку.

Результат выводится в stdout как JSON (`ensure_ascii=False`, отступ 2).
Сообщения о ходе длительных операций выводятся в stderr. При ошибке в stderr
возвращается JSON с полем `error`, код завершения равен 1.

С флагом `--json` дополнительный stdout обработчика или плагина перенаправляется
в stderr. В stdout остается только JSON-результат, пригодный для разбора целиком.
При ошибке stdout пуст, JSON ошибки выводится в stderr.
Без флага дополнительный вывод обработчика может оказаться перед результатом.

Флаг `--quiet` отключает сообщения о ходе работы, сводки и предупреждения
в stderr, включая `context.log` команды плагина. Результат в stdout, ошибки
в stderr и код завершения сохраняются. Формат результата задается через
`--brief` и `--json`. Флаг поддерживается и после команды плагина.

У `apps list` и `builds list` счетчик и отметка об усечении выводятся после
результата. Другие сообщения stderr, например предупреждение
`ELEMENT_TLS_VERIFY=false`, могут появиться раньше. Для автоматического разбора
читайте stdout отдельно: объединение потоков не гарантирует корректный JSON.

Команды, в скобках - существенные флаги:

- `token` - получить и напечатать токен.
- `apps list [--name --status --include-deleted --brief]`, `apps get [APP_ID]`, `apps find NAME [--include-deleted]`,
  `apps create NAME [--project-id --version-id --latest-build --space-id
  --tech-version --no-dev-mode --wait --verify --no-verify]`,
  `apps ensure NAME [--project-id --version-id --latest-build --space-id
  --tech-version --no-dev-mode --wait --verify --no-verify --apply]`,
  `apps apply [APP_ID] VERSION_ID`,
  `apps delete APP_ID`, `apps start [APP_ID]`, `apps stop [APP_ID]`,
  `apps users [APP_ID]`, `apps token-access APP_ID [--user --enable --disable]`,
  `apps export [APP_ID] [--output]`, `apps export-extension [APP_ID] EXTENSION [--output]`.
  - `apps list --name` фильтрует по подстроке имени без учета регистра и делает
    это на клиенте, поскольку Console API игнорирует query-параметр (п. 4.1).
    Ключ `--status` отбирает по статусу целиком, несколько статусов пишут через
    запятую либо повторяют ключ. Ключ `--brief` печатает вместо полных карточек
    краткие: ид, имя, статус, uri, примененная версия.
  - `apps list` скрывает записи со статусом `Deleted`. Чтобы включить их,
    используйте `--include-deleted` или `--status deleted`. В stderr выводится
    сводка, например "живых 7 из 324", а при дополнительном отборе – число
    показанных приложений. В stdout сохраняется массив JSON.

  - `apps get` добавляет к карточке поле `applied-build` – краткую карточку
    сборки, на которой работает приложение: ветку и коммит из карточки сборки
    либо из локального реестра загрузок, в том же виде, что печатает
    `builds list --brief`. Когда карточка примененной сборки не называет, поле
    равно null.
  - `APP_ID` у `apps get`, `delete`, `start`, `stop`, `debug` и `users` - это ид
    приложения (UUID) либо его точное имя. Значение, не похожее на UUID,
    разрешается по списку точным совпадением без учета регистра, причем
    удаленные приложения не в счет. Нет совпадений - ошибка. Несколько
    совпадений - тоже ошибка, с перечнем ид: разрушающие команды не должны
    угадывать.
  - `apps find` ищет имя по точному совпадению без учета регистра среди полей
    `name`, `display-name` и `publication-context`. Вывод -
    `{"id": ..., "found": true|false}`, код возврата 0 в обоих случаях:
    отсутствие приложения это ответ, а не ошибка. Ненулевой код возврата
    означает сбой запроса и сопровождается JSON-ом с полем `error` в stderr.
    В скриптах проверяйте поле `found`, а не код возврата.
  - Удаленные приложения остаются в списке сервера со статусом `Deleted` и
    прежним `id`. `apps find` их пропускает: найденный id обязан быть пригоден
    для работы, иначе вызывающий получит id, на котором `apps get` и `deploy`
    отвечают 404. Флаг `--include-deleted` возвращает прежнее поведение, то есть
    поиск среди всех приложений, включая удаленные.
  - `apps ensure` ищет приложение по правилам `apps find`, исключая удаленные,
    и создает его при отсутствии. Результат:
    `{"id": ..., "created": true|false, "sign-in": ...}`.
    Без `--apply` существующее приложение не изменяется; результат содержит `created: false`. Параметры
    создания совпадают с `apps create` и применяются только к новому приложению,
    включая `--version-id`.

    При предварительной сверке существующего приложения результат содержит `applied` – применена ли запрошенная сборка – и `applied-version-id` – идентификатор текущей сборки.
    Если идентификатор не совпадает с карточкой приложения, выполняется поиск
    среди сборок проектов расширений. Сборка расширения проверяется по
    `extension-projects`, как в `apps apply` и `verify-deploy` (п. 6.1).
    Карточка приложения содержит только основную сборку.

    Для расширения `applied-version-id` относится к его текущей сборке,
    а `extension-project-id` и `extension` содержат проект и запись
    `extension-projects`. Без Console API 2.1 проверить расширение нельзя:
    значение `applied` равно `null`.

    Флаг `--apply` применяет запрошенную сборку; отдельная команда – `apps apply`. Если после предварительного несовпадения выполнено применение, в верхнем уровне возвращаются `applied` и `verify`. Сведения о примененной сборке и расширении находятся внутри отчета `verify`.
    Для найденного приложения `--verify` выполняет полную проверку, только если задана сборка и предварительная сверка вернула `applied: true`. При известном несовпадении повторная проверка не выполняется. После создания результат проверки определяет
    `applied`, если проверка выполнялась. Существующее приложение не
    пересоздается: удаление и повторное создание меняют URL и внешние привязки.

  - `apps apply [APP_ID] VERSION_ID` применяет загруженную сборку и проверяет
    результат (п. 6.6). При сбое сервер может восстановить прежнюю сборку и
    запустить приложение без сообщения об откате. Поэтому возвращается отчет
    проверки, а при непримененной сборке – код завершения 1. Команда CLI
    позволяет выполнять длительную операцию фоном. Для сборки расширения
    проверяется список расширений (п. 6.1), а не карточка основной сборки.

  - `apps create` и `apps ensure` возвращают сведения для входа в приложение (п. 6.11). Это поле `sign-in` вывода вида
    `{"url", "account": "control-panel", "hint", "note"}` и те же две фразы в
    stderr. Поле `url` - адрес приложения из карточки. Пока адреса нет, а при
    создании без `--wait` его нет, там стоит `null`, и подсказка содержит способ получения адреса. Поле `account` - код, а не текст: войти можно учетной записью
    панели управления, и примечание объясняет, почему учетные записи, которыми
    входят в другие приложения, здесь не работают.
  - `--latest-build` берет источником последнюю сборку проекта и защищает от
    пустого каркаса (п. 6.2). `--wait` дожидается готовности (п. 6.4), проверяет
    итог (п. 6.6) и выводит финальную карточку.
  - До создания проверяется наличие сборки из `--version-id` в проекте
    `--project-id` или, без этого флага, `ELEMENT_PROJECT_ID`. Сервер удаляет
    неиспользуемые сборки; попытка создания из такой сборки приводит к 400
    "Can't create application" без пояснения, похожему на ограничение числа
    приложений. Предварительная проверка позволяет указать причину.

    Если сборки нет в выбранном проекте, проверяются другие проекты стенда:
    сначала проект из локального реестра загрузок, затем остальные от новых
    к старым. Для этого читаются списки сборок, поскольку отдельного метода
    поиска только по идентификатору нет. Загрузка без идентификатора проекта
    могла добавить сборку в проект, отличный от `ELEMENT_PROJECT_ID`.

    Проект из окружения заменяется найденным с сообщением в stderr. Явный
    `--project-id` не заменяется: возвращается ошибка с нужным проектом и флагом.
    Если сборки нет ни в одном проекте, ошибка предлагает сборку работающего
    приложения выбранного проекта или `--latest-build`, если приложения нет.
    Если другие проекты не удалось прочитать, в ошибке указан источник проекта
    `ELEMENT_PROJECT_ID` и возможность нахождения сборки в другом проекте.
    Без заданного проекта эта предварительная проверка не выполняется.

  - После `--wait` выполняется проверка сборки. Статус `Running` не подтверждает
    успех применения: при ошибке сервер может запустить прежнюю сборку.
    Проверяются идентификатор примененной сборки, задачи с ошибками после начала
    создания и доступность uri, как в `apps apply` и `verify-deploy`.
    Отчет включается в `verify`; непройденная проверка дает код завершения 1.
    Флаг `--verify` также включает ожидание готовности. Флаг `--no-verify`
    оставляет только ожидание. Без флагов ожидания и проверки операция
    возвращается сразу после запроса создания.

  - Ошибка ожидания или проверки не отменяет создание приложения. Результат
    сохраняет его идентификатор: карточку у `apps create` или поле `id`
    и `applied: null` у `apps ensure`, поскольку проверка не завершена.
    Причина записывается в `wait-error`, в stderr выводится команда
    `verify-deploy` для последующей проверки. Код завершения равен 1.
    До исправления возвращалась только сетевая ошибка, и идентификатор
    запустившегося позже приложения приходилось искать по имени.

  - `apps users [APP_ID]` печатает пользователей, подключенных к приложению, так, как
    их отдает `GET /applications/{id}/users` (п. 4.1): `user-list-id`, `user-id`,
    `presentation`, `is-admin`, `token-access-enabled`. Логина среди них нет:
    для пользователя панели управления сервер возвращает логин в `presentation`, а
    остальных – их представлением. Команда только читает, поэтому приложение по
    умолчанию берется из `ELEMENT_APP_ID`, а заканчивается она строкой итога в stderr:
    сколько пользователей подключено, сколько из них администрирует приложение и у
    скольких есть доступ к его HTTP-сервисам по токену. До этой команды перечень был
    виден только в отказе `apps token-access`.
  - `apps token-access APP_ID` показывает или переключает доступ пользователя к
    HTTP-сервисам приложения по токену (п. 4.1). Приложение называют явно, аргументом или
    `--app-id`: `ELEMENT_APP_ID` называет рабочее приложение, и переключение, которое
    открывает его сервисы, не должно попадать туда по умолчанию. `--user` – логин,
    представление или ид пользователя; без него используется учетная запись подключения elemctl (`GET /me`). Без `--enable` и `--disable` команда только
    читает, оба флага сразу – ошибка. После переключения подключение перечитывается,
    поэтому `token-access-enabled` в выводе – состояние, сохраненное сервером после изменения, а
    признак, который не изменился, – ошибка с кодом возврата 1. Вывод –
    `{"app-id", "user", "user-id", "user-list-id", "token-access-enabled", "changed"}`, где
    `changed` показывает, внес ли изменения текущий вызов: уже установленное состояние
    запроса не отправляет. Пользователя, не подключенного к приложению, команда называет
    вместе с подключенными и ничего не отправляет. Ключ `--user` можно повторить, и тогда
    пользователи читаются или переключаются по очереди. Вывод становится
    `{"ok", "app-id", "users"}` с записью на каждого пользователя в порядке ключей: отчет
    выше с `"ok": true` либо `{"ok": false, "user", "error"}` для пользователя, которого не
    удалось найти или переключить. Такой пользователь не останавливает остальных, а код
    возврата равен 1, если не удалась хоть одна запись. Один и тот же пользователь,
    названный дважды, считается одним, и один пользователь сохраняет вывод выше.
  - `apps export [APP_ID]` записывает в файл сборку, на которой работает приложение
    (п. 4.1). `--output` – файл или каталог для него. Без флага файл сохраняется в текущем каталоге под именем `{Имя} {Версия}.xasm` из манифеста архива – так же называется
    сборка, которую собирает elemctl; у сборки, загруженной в проект, это номер, который дал
    ей сервер. Расширений, примененных в приложении, в архиве нет, их записывает
    `apps export-extension`. Команда только читает сервер, поэтому приложение по умолчанию
    берется из `ELEMENT_APP_ID`, как у `apps get`. Вывод – `{app-id, file, size, manifest}`,
    где `file` – полный путь, а `manifest` – `Assembly.yaml` архива. Ответ, который не
    является архивом сборки, отвергается, и файл не пишется. Сервер без этого метода
    получает отказ с причиной и ответом своей консоли (статус 401, п. 4).
  - `apps export-extension [APP_ID] EXTENSION` записывает в файл сборку расширения,
    примененного в приложении (п. 4.1, Console API 2.1). `EXTENSION` – ид расширения, ид
    его проекта, имя или представление проекта; сравнение точное и без учета регистра.
    Значение сначала ищется среди расширений приложения, потому что при неверном значении сервер возвращает 500 без пояснения: при отсутствии совпадений возвращается ошибка со списком расширений приложения, несколько совпадений – ошибка с их перечнем. `--output` – файл или каталог
    для него. Без флага файл сохраняется в текущем каталоге под именем `{Имя} {Версия}.xasm` из
    манифеста архива – так же называется сборка, которую собирает elemctl. Команда только
    читает сервер, поэтому приложение по умолчанию берется из `ELEMENT_APP_ID`, как у
    `apps get`. Вывод – `{app-id, extension-id, project-id, vendor-name, project-name,
    assembly-version, enabled, file, size, manifest}`, где `file` – полный путь, а
    `manifest` – `Assembly.yaml` архива. Ответ, который не является архивом сборки,
    отвергается, и файл не пишется. Сервер без этого метода получает отказ с причиной и
    ответом своей консоли (статус 401, п. 4), без ошибочного сообщения о неудачной авторизации.
- `spaces list`.
- `user-lists list [--name]`, `user-lists get [LIST] [--app]`,
  `user-lists self-registration [LIST] [--app --enable --disable]`,
  `user-lists password-login [LIST] [--app --enable --disable]` - списки пользователей и
  их настройки входа (п. 4.7). Цель задают аргументом `LIST`, это ид либо точное
  представление, и разрешается он как имя приложения: нет совпадений - ошибка,
  несколько - ошибка с перечнем ид. Либо целью служит `--app`, то есть собственный
  список приложения из его `default-user-list`. Задать оба - ошибка. Без `--enable`
  и `--disable` обе команды-настройки только читают текущее состояние, поэтому та
  же команда отвечает на вопрос "как сейчас". Оба флага сразу - ошибка.
  `password-login` работает с сервисом учетных записей типа `Local`. Вывод -
  `{"list-id", "enabled", "changed"}`, где `enabled: null` означает, что такого сервиса у списка нет, поэтому вход по паролю недоступен, а `changed` показывает, внес ли изменения текущий вызов: перевод в состояние, которое уже стоит, запроса не
  делает.
- `projects list [--name --include-deleted]`, `projects get [PROJECT_ID]`,
  `projects delete PROJECT_ID`.
  - `projects list --name` фильтрует по подстроке имени без учета регистра и
    делает это на клиенте, поскольку Console API возвращает весь перечень (п. 4.3).
    Проекты с признаком удаления скрыты, пока не задан `--include-deleted`: это сокращает список при поиске действующего проекта на стендах с большим количеством удаленных записей.
- `builds list [--project-id --limit --brief]`, `builds get VERSION [--project-id]`,
  `builds upload FILE [--project-id --new-project --force-rename --space-id]`,
  `builds delete VERSION [--project-id]`. `builds upload` отправляет коммит,
  который называет манифест архива, параметром `commit-id` (п. 4.4), и называет
  в stderr сборку, которую сервер пронумеровал не так, как ее архив (п. 4.4).
  `builds upload` сообщает цель в выводе полями `project-id` и
  `project-id-source`: `flag` или `env` у проекта, который назвал вызов, `server` у
  проекта, который выбрал сервер, а сообщение в stderr указывает, когда цель взята из
  `ELEMENT_PROJECT_ID`. Ключ `--new-project` отключает привязку из
  окружения и загружает сборку без ид проекта: сервер добавляет ее в существующий проект с
  ее `Ид` либо заводит новый, если такого нет (п. 6.8); с `--project-id` он
  несовместим. Такая загрузка называет этот проект полем `project`,
  `{id, name, configuration-id, created, renamed-from, found-by}`, и строкой в
  stderr. Проект берется из `artifact` ответа (п. 4.4), а ответ без него
  отправляет клиента по перечням сборок (`found-by` – `response` или
  `build-list`). `created` и `renamed-from` сверяются с перечнем проектов,
  прочитанным до загрузки: ид, которого в перечне не было, – проект, который
  загрузка создала, а ид, который был там под другим именем, – проект, который
  она переименовала. О переименовании stderr предупреждает: удаление сборки имя не
  вернет. Раньше ответ печатал `project-id: null`, и проект, который сервер завел
  для сборки, приходилось искать вручную. Перечень, который не прочитался, оставляет в
  `created` null и загрузку не останавливает. Ключ
  `--force-rename` разрешает загрузку сборки с чужим именем, которая переименует
  проект-цель.
  `builds list` по умолчанию показывает десять последних сборок.
  Для полного списка используйте `--limit 0`. В stderr выводится сводка
  с различием между ограничением `--limit` и отсутствующими на сервере
  сборками после очистки (п. 4.4). Автоматическое удаление определяется
  использованием сборки, а не ее возрастом.

  Анализ полноты основан на номерах одной базовой версии. Пропуск обычно означает
  удаление, но возможен скачок: при загрузке без идентификатора проекта
  сохраняется номер архива, и последующая нумерация продолжается с него.
  Например, наблюдалась последовательность `1.0.0-3`, `1.0.0-500`, `1.0.0-501`
  без промежуточных номеров. Даты `created` недостаточны для различения:
  в проверке четыре номера были присвоены за треть секунды.

  Для уточнения используется локальный реестр загрузок. Пропуск перед сборкой,
  загруженной с этой машины без идентификатора проекта, обозначается как скачок,
  если в пропущенном диапазоне нет зарегистрированных загрузок.
  Без локальной записи о скачке, например после загрузки с другой машины,
  пропуск по-прежнему определяется как удаление.

  Один диапазон может включать скачок и удаление. Это наблюдалось между
  `1.0.0-8` и `1.0.0-52` после удаления загруженной без идентификатора проекта
  сборки `1.0.0-50` и следующей `1.0.0-51`. Другой пример – скачок к
  `1.0.0-10` после удаления `1.0.0-4`. Если реестр содержит отсутствующие
  загрузки внутри диапазона, указываются обе причины. Сводка перечисляет
  сборку скачка и первые три отсутствующие загрузки с этой машины, затем
  количество остальных. Такой диапазон учитывается как удаление.

  Для пустого списка выводится сообщение об отсутствии сборок. Если у сборок
  нет номеров, анализ нумерации недоступен. Проекты расширений не участвуют
  в автоматической очистке: пропуск означает ручное удаление. Их сборки
  сохраняются до `builds delete`. Вид проекта читается из карточки;
  если прочитать ее не удалось, используется обычная сводка.

  `--brief` печатает ид, версии, дату, ветку и коммит сборки. Ветку и коммит
  команда берет из карточки, если сервер их вернул, иначе из локального
  реестра загрузок, а поля `branch-name-source` и `commit-id-source` содержат источник: `platform`, `registry` или null, когда данные отсутствуют. Только реестр содержит `dirty` – были ли в дереве незакоммиченные правки – и
  `project-dir`, каталог, из которого собрана сборка.
- Локальный реестр загрузок. Каждая загрузка elemctl – `deploy`, `builds upload`,
  `probe` – дописывает строку JSON в файл `uploads.jsonl` в каталоге данных
  пользователя: `ELEMCTL_DATA_DIR`, если переменная задана, иначе
  `%LOCALAPPDATA%\elemctl` в Windows и `$XDG_STATE_HOME/elemctl`
  (`~/.local/state/elemctl`) в остальных системах. В строке – ид сборки, ид проекта,
  версия, ветка, коммит, признак `dirty`, каталог исходников, архив, стенд, команда,
  приложение, для которого загружали (цель деплоя, одноразовое приложение пробника),
  путь загрузки (`project` – в проект по ид, `no-project-id` – без ид проекта;
  строки, записанные до этого имени, несут `vendor-name` и читаются так же)
  и время. Сервер хранит только коммит, и когда с одной машины выкатывают несколько
  сессий, сборку на приложении нельзя было связать с рабочим деревом, из которого
  она пришла. Реестр локальный: сборок, загруженных с другой машины, из CI или
  версией elemctl без реестра, в нем нет. Если реестр не удалось записать, это
  предупреждение в stderr, а не отказ – сборка к тому времени уже на сервере;
  реестр, который не читается, считается пустым. Сторож схемы `deploy` берет отсюда
  коммит примененной сборки, когда в ее карточке коммита нет. Отсюда же `deploy`
  считает номер следующей сборки: версия, которую получила сборка проекта,
  остается в реестре и после того, как сборку сняли (п. 5). Реестр хранит 1000
  последних загрузок, `ELEMCTL_REGISTRY_LIMIT` задает другое число, а `0` – хранить
  все: когда файл перерастет предел на десятую часть, следующая загрузка обрежет его
  до последних строк. Файл переписывается рядом с собой и подменяется
  переименованием, а строку, которую тем временем дописал другой процесс, обрезка
  переносит; если система подмену не дала, файл остается как был до следующей
  загрузки.
- `build [--project-dir --output --build-version --last-build --commit
  --branch --kind {application,library,extension} --require-clean]` - локально собрать
  архив. Вывод: `file`, `name`, `vendor`, `version`, `version-source`
  (`flag`, `last-build`, имя CI-переменной либо `default`), `kind`, `branch`,
  `commit` и `dirty`, то есть есть ли в каталоге проекта незакоммиченные
  изменения; `null` там означает, что git недоступен. Версия возвращается отдельным полем для использования в CI без разбора имени файла. Без `--project-dir` каталог
  проекта ищется автоматически: берется первый каталог с `Проект.yaml` вглубь от
  текущего. Значение `--kind` по умолчанию определяется по `ВидПроекта`. Ключ
  `--require-clean` прерывает работу до сборки, когда в каталоге проекта есть
  незакоммиченные изменения. При недоступном git проверка также завершается ошибкой: чистоту дерева нельзя подтвердить.
- `inspect FILE` - разобрать готовый архив (п. 5.1). Операция локальная: к серверу не
  обращается, флаги подключения отвергает так же.
- `deploy [--app-id --project-id --project-dir --output --build-version
  --branch --commit --dry-run --require-clean --allow-data-loss
  --server-start-timeout --expected-app-name --expected-app-uri]` – полный цикл:
  сборка, загрузка, применение, перезапуск и проверка результата (п. 6.1).

  JSON-отчет содержит:
  - `app-id`, `uri`, `status` – приложение и его состояние;
  - `version`, `assembly-id`, `assembly-version` – версия архива,
    идентификатор и версия загруженной сборки после нумерации сервером;
  - `renumbered` – `true`, если сервер изменил версию; `null`, если версия
    не определена по ответу загрузки;
  - `applied-version`, `applied` – примененная версия и результат сравнения:
    `true`, `false` или `null`, если фактическую версию определить не удалось;
  - `uri-status` – результат проверки адреса;
  - `problems` – исходные сообщения сервера, `problems-lines` – те же сообщения
    построчно. Это позволяет читать многострочные ошибки без экранирования
    переводов строк и табуляции в длинной строке JSON;
  - `ok` – общий результат;
  - `dirty`, `dirty-files` – незакоммиченные изменения каталога проекта
    на момент сборки. Сборка использует состояние файлов на диске. Отклонение
    от HEAD также выводится в stderr; `null` означает недоступность git;
  - `extension-project-id`, `extension` – сведения о проверке расширения.

  Поле `hint` содержит рекомендацию проверить журнал сервера, если отказ
  не содержит ошибки компиляции. При сообщении "Contact administrator for
  details" причину можно найти в последней строке `Caused by` файла server.log;
  расположенная рядом `SrcPath:` содержит путь к файлу. После применения
  со статусом `Error` деплой завершается ошибкой с той же подсказкой.

  Для `ProjectKind: Extension` проверяется список расширений (п. 6.1).
  `extension-project-id` содержит проект, `extension` – запись `extension-projects`
  или `null`, если расширение отсутствует. Поля `applied-version` и
  `applied-version-id` относятся к сборке расширения, а не к основной сборке.

  Код завершения равен 0 только при `ok`. Параметр `--dry-run` выполняет только
  локальную сборку. С `--require-clean` незакоммиченные изменения отклоняются
  до сборки. Срок ожидания запуска сервера задается через
  `--server-start-timeout` в секундах (п. 6.12).

  При загрузке в проект сервер присваивает номер (п. 4.4). Если явный
  `--build-version` не сохранится из-за нечислового или отсутствующего суффикса
  либо базы, отличной от `Версия` проекта, предупреждение выводится до сборки.
  Отличие версии после загрузки сообщается сразу после ответа сервера.
  Без `--build-version` следующий номер определяется по большему значению
  из списка сборок и локального реестра загрузок (п. 5). Номера удаленных
  сборок не используются повторно. Если сборка загружалась с другой машины,
  а затем была удалена, ее может не быть в обоих источниках. При таком
  расхождении выводится фактический номер от сервера без предупреждения.

  До сборки выполняется проверка схемы относительно коммита примененной сборки.
  Источник – `commit-id` карточки (п. 4.4) или, при его отсутствии, локальный
  реестр загрузок. В карточке сборки, создавшей проект, коммита нет; локальная
  запись доступна, если сборка загружалась с этой машины. В stderr указываются
  источник и наличие незакоммиченных правок в исходной сборке: эти правки
  не входят в сравнение с коммитом. Поля `schema-commit` и `schema-commit-source`
  содержат коммит и источник (`platform` или `registry`). Каталог проекта
  определяется по тем же правилам, что при сборке.

  Без `--allow-data-loss` отклоняются:
  - сужение длины или изменение типа реквизита, измерения или ресурса,
    в том числе реквизита табличной части;
  - удаление измерения;
  - удаление объекта со своей таблицей данных: справочника, документа,
    регистра сведений или накопления, набора констант, плана обмена,
    хранилища настроек. При применении такого изменения удаляется вся таблица.

  Для поиска удаленных описаний читается список файлов примененного коммита
  через git. Объекты сопоставляются по `Ид`. Переименование или перенос
  в другую подсистему не считается удалением: сравнивается прежнее описание.
  При поиске удаленных и перемещенных описаний объект без `Ид` пропускается: надежное сопоставление после переноса невозможно. Файлы по прежнему пути могут сравниваться и без `Ид`.

  Замена `Ид` в прежнем файле означает другой объект. Прежний идентификатор
  проверяется на удаление; поля нового и старого объектов не сравниваются.
  В проверке на сервере замена `Ид` справочника при прежнем пути и имени
  привела к пустому справочнику. Теперь такое изменение отклоняется как
  удаление. Ошибка содержит прежний `Ид` для восстановления идентичности.

  Удаление реквизита, ресурса, табличной части или ее реквизита не блокирует
  деплой (п. 6.13). Каждое изменение выводится в stderr и `schema-warnings`.
  Поля с `Ид` сопоставляются по идентификатору, поэтому переименование сохраняет данные. При переводе описания на другой язык удаление поля без `Ид` не обнаруживается: сопоставить прежнее и новое имена нельзя.

  Поле `schema-check` содержит `clean`, `warned` (только предупреждения
  об удалении), `allowed` или `skipped:<причина>`. Причины пропуска:
  `no-project-dir`, `read-failed`, `no-applied-build`, `no-applied-extension`,
  `applied-build-not-listed`, `no-commit-id`, `commit-unavailable`.
  Каждая причина сопровождается пояснением. Для расширения сравнивается его
  примененная сборка из списка расширений приложения. При первом применении
  сравнивать не с чем: возвращается `no-applied-extension`.
  Пропуск повторно отмечается после результата проверки применения,
  чтобы успех этой проверки не воспринимался как успех проверки схемы.

- `verify-deploy [APP_ID] [--app-id --version-id --expected-version --since-minutes]` -
  проверка п. 6.1 отдельной командой, которая ничего не разворачивает. Она смотрит
  задачи приложения в ошибочном статусе за последние `--since-minutes` минут, а в их
  `error-message` лежат файл и позиция ошибки компиляции. Дальше она сверяет
  примененную сборку с ожидаемой: `--version-id` - это ид загруженной сборки и
  надежная сверка, `--expected-version` - строка версии и запасной путь.
  Заканчивается все контрольным GET на адрес. Отчет тот же, что у `deploy`, код
  возврата 0 только при `ok`. Это то, что нужно скрипту CI после `apps create`: сбой
  применения сервер выполняет откат без сообщения, и статус `Running` сам по себе ничего не
  доказывает. `--version-id`, которого нет в карточке, команда ищет среди
  сборок проектов расширений стенда (`project-kind`, п. 4.3): найденная там сборка -
  сборка расширения, и ее команда проверяет по расширениям приложения, как это
  делает `deploy`, а остальные сборки проверяются по карточке приложения. Поиск стоит перечня
  проектов и одного перечня сборок на каждый проект расширения и идет, только когда
  карточка называет другую сборку. Ключ `--expected-version` сам по себе к проекту
  не ведет, поэтому расширение проверяется по ид сборки.
- `probe [--project-dir --output --build-version --name --space-id --keep
  --require-clean]`, `probe --cleanup APP_ID` – проверка компиляции
  во временном приложении и последующая очистка. Цикл включает сборку, загрузку,
  создание одноразового приложения для компиляции (п. 6.10), получение ошибок
  с файлом и позицией, затем удаление временных объектов.

  До сборки проверяются свойства описания проекта:
  - `Представление` (`Presentation`): без него загрузка отклоняется с 500
    без пояснения;
  - `ЯзыкРазработки` (`DevelopmentLanguage`): без него приложение не создается;
  - `ЯзыкиЛокализации` (`LocalizationLanguages`), если указан
    `ЯзыкПоУмолчанию` (`DefaultLanguage`): отсутствие списка при заданном
    языке также вызывает отказ без пояснения.

  Ошибка перечисляет недостающие ключи и строки для добавления на языке
  исходного описания. Проверка завершается до сборки и загрузки.
  `ELEMENT_APP_ID` и `ELEMENT_PROJECT_ID` не используются при создании:
  рабочее приложение не изменяется, проект определяется сервером по `Ид`
  из описания (п. 6.8). Версия по умолчанию – `{база}-probe-{токен}`.
  Уникальность нужна для исключения 409 при повторе, а нечисловой суффикс
  исключает временную сборку из сравнения последних числовых номеров.

  Очистка выполняется после успешной и неудачной компиляции в порядке п. 6.9:
  приложение, сборка, затем проект, если он был создан этой проверкой.
  Результат содержит:
  - `ok`, `project-dir`, `vendor`, `name`, `file`, `version`;
  - `project-id`, `project-created`, `project-renamed-from`. Последнее поле
    содержит прежнее имя, если сервер переименовал существующий проект
    с `Ид` исходников по новому представлению. Об этом выводится предупреждение
    в stderr; очистка не восстанавливает имя. Если переименования нет – `null`;
  - `assembly-id`, `app-id`, `app-name`, `status`;
  - `errors` – список `{file, entry, line, column, environment, message}`.
    Путь `file` задан относительно каталога проекта;
  - `messages` – исходные сообщения, в том числе для отказов вне компиляции;
  - `cleanup` – `kept`, `app-deleted`, `assembly-deleted`, `project-deleted`,
    `problems`, `command`, `steps`;
  - `hint` – рекомендация проверить журнал сервера, как в `deploy`.
    Она добавляется при отказе без пути к файлу; при таймауте остается пустой.

  Если сервер не поддерживает режим совместимости проекта, могут возникнуть
  производные ошибки типов и свойств в неизмененных файлах. В этом случае
  разбор прекращается после определения причины. `compatibility-refused`
  содержит режим, `messages-dropped` – число пропущенных производных сообщений.
  Это позволяет отличить несовместимость сервера от ошибки исходного кода.

  Код завершения равен 0 только при `ok`. Ошибки очистки записываются в отчет
  и stderr, но не меняют результат компиляции. С `--keep` приложение и сборка
  сохраняются для ручного разбора. Даже после удаления запись приложения
  остается на сервере со статусом `Deleted` и прежним идентификатором;
  удалить такую запись через API нельзя.

  При `--keep` или неудачной очистке результат `cleanup` содержит `command` – `probe --cleanup APP_ID`, если известен идентификатор приложения, иначе `null`. Ручные `steps` перечисляют оставшиеся операции в порядке п. 6.9; они также выводятся в stderr.
  Сборка адресуется в собственном проекте. Без явного проекта `builds delete`
  использует `ELEMENT_PROJECT_ID`, где временной сборки может не быть.
  До завершения удаления приложения удаление сборки возвращает 500.
  Команды очистки включают исходный `--env-file`.

  **Повторная очистка.** `probe --cleanup APP_ID` принимает идентификатор или имя.
  Проект и сборка читаются из карточки приложения. Для подтверждения назначения
  приложения достаточно одного признака:
  - имя начинается с `elemctl-probe-`;
  - версия содержит `-probe-`, в том числе при произвольном `--name`;
  - локальный реестр содержит создание этого приложения через проверку.
    Последний вариант покрывает собственные `--name` и `--build-version`,
    а также приложение, в которое позже загружались другие сборки.

  Приложение без этих признаков и приложение из `ELEMENT_APP_ID` отклоняются
  с объяснением. Очистка удаляет приложение, ожидает его удаления, затем удаляет
  сборку проверки и известные реестру загрузки для этого приложения.
  Сборка проверки определяется по токену версии или записи реестра.
  При наличии записей о сборках в локальном реестре дополнительно проверяется их использование другими действующими приложениями. Найденная используемая сборка сохраняется; в записи `builds` поле `kept` содержит приложение. Если записей реестра нет и сборка найдена только по имени или токену, клиент эту проверку не выполняет. Поэтому сохранение такой сборки при использовании другим приложением не гарантируется; ограничение относится и к очистке с другой машины.

  Проект удаляется последним, только при отсутствии сборок и действующих
  приложений. Проект из `ELEMENT_PROJECT_ID` сохраняется всегда. Обычно исходники
  относятся к рабочему проекту; новый проект, созданный проверкой, после очистки
  остается пустым и может быть удален. Загрузки с другой машины, которых нет
  в реестре, сохраняются для автоматической очистки сервера.

  Повторный вызов завершает незаконченные шаги. Удаленное приложение с сохраненной
  записью и уже удаленный проект повторно не удаляются. Новая сборка не создается;
  параметры запуска `probe` вместе с `--cleanup` отклоняются.
  Результат: `ok`, `app-id`, `app-name`, `project-id`, `app-deleted`,
  `builds` (записи `{id, version, deleted}`), `project-deleted`, `project-kept`
  с причиной сохранения проекта, `problems`. Код завершения 0 соответствует `ok`.

  При повторении `--cleanup` приложения обрабатываются последовательно.
  У проверок одних исходников может быть общий проект; он удаляется после
  последней сборки. Результат имеет вид `{"ok", "cleanups"}` с отчетом на каждое
  приложение в порядке аргументов. Для отказа возвращается
  `{"ok": false, "app-id", "error"}`, где `app-id` – исходное значение.
  Отказ одного приложения не останавливает остальные. Общие `ok` и код 0
  требуют успешной очистки всех приложений. Дубликаты объединяются;
  для одного приложения сохраняется одиночный формат результата.

- `branches list [--project-id --name]`, `branches get ID`,
  `branches create NAME [--project-id --app-id]`,
  `branches update ID [--app-id]`, `branches delete ID`,
  `branches merge ID`.
- `dumps create [APP_ID] [--description]`, `dumps get APP_ID DUMP_ID`.
- `tasks list [--app-id]`, `tasks get-group TASK_ID`.
- `tech get [APP_ID]`, `tech set APP_ID VERSION`.
- `debug-adapter` - путь к каталогу адаптера отладки 1С:Элемента, предоставленному плагином (группа точек расширения `elemctl.debug_adapter`, п. 10). Вывод
  `{"path": ..., "found": true, "adapter-class": ...}` при наличии либо
  `{"path": null, "found": false}`; код возврата 0 в обоих случаях. Значение
  `path` - готовое значение настройки `xbsl.debug.adapterPath` для расширения
  VS Code (каталог с подкаталогом `repo/`).
- `plugins` возвращает диагностику обнаружения плагинов. Поле `debug-adapter`
  содержит объявленные каталоги адаптера и наличие jar. Поле `commands`
  содержит команды с источником точки расширения и именем инструмента MCP;
  если команда недоступна в MCP, имя равно `null`. Поле `failures` содержит
  ошибки загрузки и конфликты имен с ядром, с источником и причиной:
  `{"debug-adapter": [{"path": ...,
  "has-jars": true|false}], "commands": [{"name": ..., "source": ..., "mcp": ...}],
  "failures": [{"source": ..., "error": ...}]}`.
- Подкоманды плагинов из группы `elemctl.commands` (раздел 10) доступны вместе
  с командами ядра и включаются в `--help`. Имена ядра зарезервированы;
  генерируемый справочник описывает только ядро. Ошибка загрузки плагина
  не останавливает CLI. Сведения о ней выводятся в stderr. Если запрошена
  отсутствующая команда и есть ошибки плагинов, ответ JSON в stderr содержит
  поле `plugin-failures` с их перечнем.

- `self-update [--version X] [--stop-holders[=all]]` обновляет elemctl распаковкой
  колеса с PyPI в site-packages. Занятые exe-файлы не заменяются: программа
  запуска использует обновленный код пакета. Это позволяет обновлять пакет,
  когда работающий MCP-сервер использует `elemctl.exe`, в отличие от pipx и pip.
  Также обновляется `pipx_metadata.json`. Результат: `{updated, from, to}`.

  Без `--version` проверяются простой индекс и сводный JSON PyPI. Они кешируются
  разными узлами и могут несколько минут содержать предыдущую версию.
  Выбирается более новая версия из двух ответов, затем проверяются страницы
  трех следующих номеров: `0.44.1`, `0.45.0` и `1.0.0` после `0.44.0`.
  Страница выпуска доступна сразу после публикации. При расхождении источников
  в stderr выводятся обе версии. Если установленная версия новее всех ответов,
  она сохраняется. Явная `--version`, отсутствующая в индексе, проверяется
  по собственной странице; только 404 означает отсутствие такого выпуска.

  Если файлы пакета заняты, выводятся pid и командные строки использующих их
  процессов, а обновление прекращается без изменения установки.
  `--stop-holders` завершает MCP-серверы: для применения нового кода им нужен
  перезапуск. Идущие команды других сессий перечисляются и продолжают работу.
  Если они используют файлы, предлагается дождаться завершения и повторить
  обновление. `--stop-holders=all` завершает также эти команды; их результат
  при прерывании не возвращается.

- `mcp` - запустить MCP-сервер; без установленного extra - понятная ошибка
  с подсказкой `pip install "elemctl[mcp]"`.

Позиционные APP_ID и PROJECT_ID, помеченные выше как необязательные, при
отсутствии берутся из конфигурации: `ELEMENT_APP_ID` и `ELEMENT_PROJECT_ID`.
Если и там пусто, будет ошибка.

Необязательные `--expected-app-name` и `--expected-app-uri` (`expected_app_name` и `expected_app_uri` в библиотеке и MCP) точно сверяют значения карточки приложения на сервере до проверки схемы, сборки и загрузки. Несовпадение или отсутствие ожидаемого поля останавливает деплой. Без этих аргументов дополнительного запроса карточки нет. Локальный `--dry-run` не проверяет приложение на сервере.

## 8. Требования к MCP-серверу

Имя сервера – `elemctl`, транспорт – stdio. Реквизиты читаются из тех же
переменных окружения и `.env`, что в CLI. Инструкции сервера должны описывать
возможный откат без сообщения при неудачном применении (п. 6.1).
Описания инструментов должны быть краткими, на русском языке.

Инструменты должны соответствовать операциям CLI из раздела 7.

- `list_apps(name="", status="", include_deleted=False)` – список приложений.
  Имя фильтруется по подстроке без учета регистра на клиенте (п. 4.1), статус –
  по полному значению. Удаленные приложения скрыты, если не запрошены явно.
  Результат содержит `total`, `live`, `shown`, `summary` и `applications`.
  Счетчики показывают, какая часть серверного списка возвращена.
- `get_app(app_id)` – карточка с `applied-build`, как в `apps get` (п. 7).
  `find_app(name)` выполняет поиск по имени.
- `create_app(name, project_id="", version_id="", space_id="",
  development_mode=True, verify=False)` – создание приложения.
  Если указан только project_id, используется последняя сборка проекта (п. 6.2).
  При `verify=True` выполняются ожидание и проверка запрошенной сборки;
  отчет возвращается в `verify`.
- `ensure_app(name, project_id="", version_id="", space_id="", development_mode=True, verify=False)` выполняет ту же проверку при `verify=True` для созданного приложения. Для найденного приложения полная проверка выполняется только при заданном `version_id` и предварительном результате `applied: true`. При несовпадении повторная проверка не выполняется. Сборка расширения проверяется по списку расширений,
  как в `apps ensure` (п. 7).

Перед созданием `version_id` проверяется по проектам. Поиск начинается
с `project_id` или `ELEMENT_PROJECT_ID` стенда. Если сборка найдена в другом
проекте, значение из окружения заменяется найденным. При явно заданном
`project_id` возвращается ошибка с указанием нужного проекта. Если сборки
нет ни в одном проекте, она считается удаленной, создание отклоняется.

При ошибке ожидания результат сохраняет идентификатор созданного приложения
и причину в `wait-error`. У `ensure_app` в этом случае `applied: null`.
Оба инструмента возвращают `sign-in` со способом входа (п. 6.11),
в том же формате, что CLI. Пояснение включается в JSON, доступный агенту.

- `start_app(app_id)` и `stop_app(app_id)` – запуск и остановка.
- `debug_info(app_id)` – данные сессии отладки. На сервере должна быть включена
  отладка.
- `debug_adapter()` – путь к адаптеру отладки 1С:Элемента из плагина (п. 10).
  Это локальная операция без обращения к серверу.
- `delete_app(app_id)` – удаление. Описание должно предупреждать о необратимости
  и смене URL при повторном создании.

В `get_app`/`delete_app`/`start_app`/`stop_app`/`debug_info` параметр `app_id`
принимает UUID или точное имя приложения. Определение по имени работает как в CLI.

- `list_spaces()` – список пространств.
- `list_projects(name="", include_deleted=False)` – фильтры `projects list`
  из раздела 7.
- `list_builds(project_id, limit=10, brief=True)` – объект
  `{total, shown, summary, builds}`. В сводке отражаются полнота списка,
  пропуски номеров (п. 4.4) и скачки, подтвержденные реестром загрузок (п. 7).
  Для проекта расширения указывается отсутствие автоматической очистки.
  Краткая карточка содержит источники ветки и коммита: серверную карточку или
  локальный реестр, как в `builds list --brief`.
- `get_build(project_id, version)` – полная карточка сборки по версии (п. 4.4).
  Идентификатор также допускается и определяется через список.
- `build_assembly(project_dir="", output_dir="", version="")` – сборка архива.
- `inspect_assembly(file)` – локальный разбор готового архива (п. 5.1).
- `deploy(app_id, project_id, project_dir="", version="", branch="", allow_data_loss=False,
  server_start_timeout=900, expected_app_name="", expected_app_uri="")` – отчет о развертывании и поле `log`.
  Ожидание запуска сервера описано в п. 6.12. Параметр `allow_data_loss=True`
  разрешает изменения, отклоняемые проверкой схемы, как `--allow-data-loss`
  в CLI (п. 7). Без разрешения возвращается ошибка до сборки.
- `probe(project_dir="", space_id="", keep=False)` – проверка компиляции
  во временном приложении без изменения рабочего (п. 7). Результат – отчет и `log`.
- `probe_cleanup(app_id)` – удаление сохраненного временного приложения,
  как `probe --cleanup` (п. 7). Результат – отчет и `log`. Для списка `app_id`
  возвращаются `{ok, cleanups}` и `log`, как при повторении `--cleanup`.
- `apply_build(app_id, version_id)` – применение сборки.
- `verify_deploy(app_id,
  expected_version="", expected_assembly_id="", since_minutes=30)` – проверка применения по п. 6.1,
  включая расширения (п. 7, `verify-deploy`).
- `list_app_tasks(app_id="")` – задачи приложения.
- `list_branches(project_id="", name="")` и `merge_branch(branch_id)` –
  список и слияние веток.
- `list_user_lists(name="")` – списки пользователей.
- `configure_user_list(list_id="", app_id="", self_registration=None, password_login=None)` –
  настройки входа (п. 4.7). Список задается идентификатором, представлением или
  приложением, которому он принадлежит. Оба флага необязательны. Без них
  возвращается текущее состояние: `self-registration-enabled`,
  `password-login-enabled`, `changed`.
- `list_app_users(app_id)` – пользователи приложения, как в `apps users` (п. 7).
  Результат – `{app-id, total, summary, users}`.
- `token_access(app_id, user="", enabled=None)` – чтение и изменение доступа
  к HTTP-сервисам по токену, как в `apps token-access` (п. 7).
  `app_id` обязателен; пустой `user` означает учетную запись elemctl.
  Без `enabled` выполняется только чтение. Для списка `user` возвращается
  `{ok, app-id, users}` с результатом для каждого, как при повторении `--user`.
- `export_app(app_id, output="")` – запись текущей сборки приложения в файл,
  как в `apps export` (п. 7).
- `export_extension(app_id, extension, output="")` – запись примененной сборки
  расширения в файл, как в `apps export-extension` (п. 7).
  У обоих инструментов пустой `output` означает текущий каталог серверного процесса.

Инструменты плагинов из группы `elemctl.commands` (п. 10) регистрируются вместе
со встроенными. Схема формируется по аргументам, описание берется из `help`,
ядро добавляет `env_file`. Команда с именем встроенного инструмента не регистрируется;
плагин с ошибкой загрузки также пропускается. Их имена выводятся в stderr,
который клиент сохраняет как журнал сервера. Остальные инструменты доступны.

## 9. Требования к качеству

- Тесты pytest без обращений к сети: разбор .env и приоритеты конфигурации,
  отбор файлов и содержимое архива сборки (включая манифест), автоинкремент
  и числовое сравнение версий, логика итога деплоя (`ok`/`applied`),
  подсказка при `FAILED_PRECONDITION`, поиск приложения по имени, обнаружение
  плагинов через точки расширения и разрешение пути к debug-адаптеру
  (стаб-точки расширения, каталоги во временных папках), извлечение адаптера
  из мини-.car, обновление распаковкой колеса (urllib замокан, колесо и
  site-packages во временных папках).
- Докстринги, комментарии и идентификаторы - английские, включая тесты и
  инструменты: проект публичный и международный. Русский остается там, где он
  обращен к пользователю: каталог сообщений i18n, справка argparse,
  user-facing строки, описания инструментов MCP и инструкция сервера, а также
  идентификаторы 1С:Элемента в цитатах (`Проект.yaml`, `Ресурсы`, `Имя`,
  `Поставщик`) и русские данные тестовых фикстур. Кавычки в тексте прямые
  `"`, тире - среднее `–` (не длинное), многоточие - три точки `...`.
- Библиотека сама в stdout и stderr не печатает: прогресс она отдает через
  callback, который передает вызывающая сторона.
- Ошибки API поднимаются собственным исключением с деталями ответа сервера,
  сериализуемыми в JSON.

## 10. Плагины (точки расширения)

elemctl подключает внешние пакеты через `importlib.metadata.entry_points`. Ядро читает точки расширения при обращении, а объявления находятся в `pyproject.toml` пакета плагина. Поэтому проприетарные jar-файлы 1С можно поставлять отдельным пакетом без включения в публичное ядро.

Группа **`elemctl.debug_adapter`**. Значением точки расширения бывает путь
(`Path` или `str`) либо функция без аргументов, возвращающая путь
(`() -> Path | str`). Путь указывает на каталог адаптера отладки 1С:Элемента, то
есть на каталог с подкаталогом `repo/`, где лежат jar-файлы адаптера, среди них
`com.e1c.g5rt.debugger.adapter*.jar`. Это готовое значение настройки
`xbsl.debug.adapterPath` расширения VS Code.

Объявление в пакете-плагине:

```toml
[project.entry-points."elemctl.debug_adapter"]
имя = "мой_пакет:adapter_root"
```

Группа **`elemctl.commands`** принимает `Command`, список команд или функцию
без аргументов, возвращающую один из этих вариантов. По объявлению формируются
подкоманда CLI и инструмент MCP. Реализация команды остается в плагине.
Так подключаются команды для внутренних систем, частных стендов и других
окружений, которые не входят в публичное ядро.

```toml
[project.entry-points."elemctl.commands"]
имя = "мой_пакет.commands:commands"
```

Типы объявления экспортируются из `elemctl.plugins`:

- `Argument(name, help="", type=str, default=None, required=False, choices=(), cli_alias="", multiple=False)` описывает аргумент.
- `Command(name, help, handler, arguments=[], mcp=True, mcp_name="")` описывает команду.
- `CommandContext` передается обработчику вместе со значениями аргументов.

**Имя и тип аргумента.** В `Argument` имя `"--stand"` задает опцию,
а `"stand"` – позиционный аргумент. Имя значения `dest` формируется как в
argparse: начальные дефисы удаляются, внутренние заменяются подчеркиваниями.
Поддерживаются `str`, `int`, `float` и `bool`. Тип `bool` задает флаг:
`store_true` в CLI и логическое значение с начальным `false` в MCP.
Позиционный аргумент не может иметь тип `bool`.

Поле `required` действует для обоих видов аргументов. По умолчанию позиционный
аргумент необязателен; для обязательного укажите `required=True`.

**Псевдоним позиционного аргумента.** Объявление
`Argument("page", cli_alias="--page")` разрешает две формы CLI:
`wiki-get 123` и `wiki-get --page 123`. В MCP остается один параметр `page`.
В разборщике CLI формы взаимно исключают друг друга и используют один `dest`.
Одновременное указание обеих форм, а также отсутствие обеих у обязательного
аргумента приводят к ошибке разбора. Для опции `cli_alias` не поддерживается.

**Несколько значений.** При `multiple=True` обработчик получает список
в порядке командной строки. Если значения не указаны, передается объявленное
значение по умолчанию, преобразованное в список, либо `[]`.
В MCP аргумент имеет тип массива с элементами объявленного типа.

Повторяемая опция использует `action="append"`. Позиционный аргумент принимает
значения подряд: `nargs="+"` для обязательного и `nargs="*"` для необязательного.
Его псевдоним `cli_alias` использует `action="append"`. Поэтому
`wiki-get 123 456` и `wiki-get --page 123 --page 456` передают одинаковые списки;
обе формы по-прежнему взаимно исключаются.

Значение по умолчанию не передается разборщику: аргументы CLI заменяют его,
а не дополняют. Без `multiple` повтор опции с разными значениями отклоняется
(п. 7), повтор с одинаковым значением допустим. Флаг не может быть повторяемым.
Для повторяемого аргумента допустимы `None`, список или кортеж как значение
по умолчанию.

**Совместимость со старым ядром.** Перед объявлением повторяемой опции проверяйте
`hasattr(Argument, "multiple")`. Класс без этого поля отклонит объявление,
и плагин не загрузится. Для повторяемого позиционного аргумента дополнительно
нужен `POSITIONAL_MULTIPLE` из `elemctl.plugins`:
`getattr(plugins, "POSITIONAL_MULTIPLE", False)`. Одной проверки `hasattr`
недостаточно: ядро с поддержкой `multiple` только для опций отклоняет
позиционный вариант с `PluginError`.

**Команда.** Поле `name` в `Command` задает подкоманду CLI. Имя инструмента MCP
берется из `mcp_name`; если оно пустое, используется имя команды с заменой
дефисов на подчеркивания. При `mcp=False` команда доступна только в CLI.
При обнаружении плагина в поле `source` записывается имя точки расширения.

**Контекст.** В `CommandContext` доступны:

- `config` – конфигурация подключения;
- `client` – клиент Console API, который создается при первом обращении и
  кешируется. Для локальной команды без обращения к серверу реквизиты не нужны;
- `log(message)` – передача сообщений о ходе работы. CLI выводит их в stderr,
  инструмент MCP собирает в поле `log` результата;
- `surface` – источник вызова: `"cli"` для подкоманды, `"mcp"` для инструмента,
  значения констант `SURFACE_CLI` и `SURFACE_MCP`. В контексте, созданном вне
  ядра, например тестом или библиотекой, используется `None`.

Для совместимости со старым ядром читайте
`getattr(context, "surface", None)`: атрибут может отсутствовать.
Не определяйте источник вызова по устройству `log`, которое может измениться.

**Результат и код возврата.** Обработчик вызывается как
`handler(context, **values)`, где ключи значений соответствуют `dest`.
Результат должен сериализоваться в JSON: CLI выводит его, MCP возвращает.
Код завершения CLI определяется так:

- Если результат – словарь с целым числом от 0 до 255 в `exit-code`,
  используется этот код. `bool` не допускается. Диапазон обеспечивает
  переносимость: POSIX сохраняет только младшие восемь бит, поэтому 256
  преобразовалось бы в 0.
- Иначе словарь с `"ok": false` соответствует коду 1, как в `deploy` и `probe`.
  Прочие результаты соответствуют коду 0.
- Корректный `exit-code` имеет приоритет над `ok`:
  `{"ok": false, "exit-code": 0}` соответствует коду 0. Значение другого типа
  или вне диапазона игнорируется, после чего проверяется `ok`.

Имя поля экспортируется как `elemctl.plugins.EXIT_CODE_FIELD`. В старом ядре
без этой константы код завершения определяется только по `ok`.
В MCP поле `exit-code` возвращается вместе с остальным результатом.

Обработчик не должен завершать процесс: та же функция выполняется в MCP-сервере,
где `SystemExit` остановит сервер без ответа на запрос. Ядро добавляет
к инструменту MCP параметр `env_file`, как у встроенных инструментов,
а к результату-словарю – поле `log` с сообщениями о ходе работы.

Поведение обнаружения:

- Точки расширения сортируются по имени. `debug_adapter_path()` возвращает
  первый каталог с jar адаптера. Каталог без `repo/` или без нужных jar
  пропускается; при отсутствии подходящего каталога возвращается `None`.
- Ошибка загрузки точки расширения или вызова ее функции оформляется как
  `PluginError`, наследник `ElemctlError`. Для плагина, требующего новое поле
  ядра, возможен `TypeError`; ошибка содержит установленную версию ядра.
- Объявление команды проверяется при обнаружении. Пустое имя, невызываемый
  обработчик, неподдерживаемый тип, позиционный аргумент `bool`, повтор имен
  значений, `cli_alias` у опции, синоним без начального дефиса или с конфликтующим
  ключом, повторяемый флаг и некорректное значение по умолчанию вызывают `PluginError`.
- Нельзя использовать общие флаги CLI из раздела 7 как опции, имена значений
  позиционных аргументов или `cli_alias`. Эти флаги переносятся перед подкомандой
  и разбираются корневым разборщиком. Конфликт может заменить значение ядра
  или сделать параметр плагина недоступным. Собственный `env_file` также
  дублировал бы параметр MCP. Набор зарезервированных флагов читается
  из разборщика CLI, поэтому новые общие флаги автоматически защищены.
- Также зарезервированы имена значений `command`, `handler`, `plugin_command`,
  `plugin_commands`, `plugin_failures` и флаги `-h`, `--help`. Конфликтующий
  `handler` заменяет вызываемую функцию строкой и приводит к `TypeError`;
  собственный `--help` вызывает `argparse.ArgumentError` при построении CLI.
  Оба набора читаются из разборщика. Конфликт оформляется как `PluginError`.
- `discover_commands()` возвращает доступные команды и `PluginFailure`
  для каждой точки с ошибкой. `to_dict()` возвращает `{source, error}`.
  Одна некорректная команда исключает всю точку. Строгая функция
  `plugin_commands()` вызывает первое исключение. CLI и MCP-сервер используют
  `discover_commands()`, поэтому ошибка плагина не останавливает ядро
  и остальные плагины.
- Имя команды ядра защищено как в CLI, так и в MCP. Конфликтующая команда
  пропускается и включается в диагностику ошибок плагинов.
- `ELEMCTL_NO_PLUGINS=1` отключает обнаружение плагинов. Остаются возможности
  ядра. Генератор справочника устанавливает эту переменную для описания ядра.

Поверхности, использующие механизм: CLI `debug-adapter`/`plugins` (п. 7) и
подкоманды плагинов, MCP-инструмент `debug_adapter` (п. 8) и инструменты плагинов,
а также расширение VS Code, которое при пустой настройке `adapterPath` запрашивает
путь у `elemctl debug-adapter`.

Сам адаптер извлекается из дистрибутива 1С:Элемента скриптом `tools/extract_adapter.py`
(чистый код, в дистрибутив пакета не входит – `prune`): каталог
`data/ide/theia/plugins/@1c-appengine-plugin/bin/debugger/` из `.car` копируется в
`<output>/<версия>/`, обновляется `index.json`. Проприетарные jar в публичный пакет не
включаются – их содержит отдельный пакет-плагин.
