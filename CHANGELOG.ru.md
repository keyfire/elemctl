# История изменений

Заметные изменения elemctl, свежие сверху. Записи сгруппированы по дням; версии, вышедшие в этот
день, перечислены в заголовке. Формат основан на
[Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), проект следует
[семантическому версионированию](https://semver.org/lang/ru/).

## 10.08.2026 – 0.28.0

### Документация
- **Перечень инструментов MCP появился на странице.** Семь из двадцати четырёх – `apply_build`,
  `build_assembly`, `find_app`, `inspect_assembly`, `list_app_tasks`, `list_branches`,
  `list_spaces` – не были названы нигде, кроме исходников: страница обходилась фразой "и
  другие". Теперь таблица перечисляет все.
- **Переменные окружения описаны полностью.** На странице настройки не хватало
  `ELEMCTL_NO_PLUGINS` и переменных, которые сборка читает у CI (`CI_PIPELINE_IID`,
  `GITHUB_RUN_NUMBER`, `BUILD_NUMBER`, `CI_COMMIT_BRANCH`, `CI_COMMIT_REF_NAME`,
  `GITHUB_REF_NAME`), а строка `ELEMCTL_NO_PROXY` выпала из таблицы в отдельный абзац и
  показывалась палками. Язык теперь называет и системные `LC_ALL`/`LANG`.
- **Правда вместо устаревших утверждений.** Справочник команд обещал общие флаги только до
  подкоманды, хотя они принимаются в любой позиции; страница платформы не называла `.htm` среди
  расширений архива и не говорила, что внутри каталога `Ресурсы` отбора по расширению нет;
  русский README всё ещё сообщал, что документация только на русском.
- **Один источник на текст.** Разделы README, повторяющие страницы сайта, разошлись в обе
  стороны: README знал про `probe` и списки пользователей, страница – нет; страница знала про
  плагины-команды `elemctl.commands`, README – нет; README обещал два расширения VS Code после
  того, как осталось одно. Теперь источник – страница, а `scripts/sync-docs.mjs` вставляет её
  раздел в README между маркерами.
- **Схема устройства.** `docs/architecture.svg` (и русская пара) – поверхности, движок, цикл
  деплоя с молчаливым откатом и пробник; на главной странице сайта и в README. Палитра следует
  теме читателя, PNG для README рисует `scripts/render-diagrams.py` с принудительной палитрой.
- **Сторож `scripts/docsguard.py` и джоба `docs` в CI.** Проверяет то, что проверяемо
  механически: инструмент без строки в таблице, строка без инструмента, переменная окружения,
  которую код читает и никто не описал, расширение архива, не названное на странице,
  протухший блок README или зеркало чейнджлога, страница без перевода, картинка без файла.
  Каждый класс находки провоцируется тестом (`tests/test_docs_coverage.py`).

### Добавлено
- **`deploy` принимает имя приложения, а не только идентификатор.** Все остальные команды,
  адресующие одно приложение – `apps get`, `apps start`, `apps stop`, `apps debug`, – имя
  принимали и резолвили; деплой же брал значение как есть и слал имя в API, где оно
  идентификатором не является. UUID по-прежнему проходит без запроса.

### Изменено
- **Расширение VS Code уехало из этого репозитория.** Отладка приложений 1С:Элемент – часть
  расширения [XBSL](https://github.com/keyfire/xbsl) с его версии 0.57.0, вместе с кнопкой
  деплоя, которая была там и раньше: из-за разделения путь к elemctl и идентификатор приложения
  приходилось задавать дважды. Здесь осталась сторона elemctl: `apps debug`, `debug-adapter`,
  точка расширения `elemctl.debug_adapter` и скрипт извлечения адаптера.

## 07.08.2026 – 0.26.0, 0.27.0

### Добавлено
- **Проекты с английскими артефактами собираются и деплоятся.** Платформа принимает оба
  написания имён служебных файлов – её конвертер сам проверяет пары, – теперь их разрешает и
  инструмент: `build`/`deploy`/`probe` находят дескриптор с именем `Project.yaml` наравне с
  `Проект.yaml`, локальная библиотека-зависимость ищется любым из имён, а разбор архива читает
  `ElementKind`/`VisibilityScope` (включая английские значения, например `Global`) и пропускает
  `Subsystem.yaml` как описатель. Страж схемы читает и английские ключи реквизитов
  (`Attributes`, `Id`, `Name`, `Type`, `Length`, `MaxLength`) и знает, что два написания имени
  примитивного типа – ОДИН тип: перевод описания не выглядит изменением, разрушающим данные.

### Изменено
- **Загрузка сборки не отправляет параметры коммита и ветки.** `CommitId`/`BranchName`/
  `CommitMessage` уходили query-параметрами загрузки, выглядели рабочими – и не делали ничего:
  в справочнике Console API их нет, а отправленные сервер игнорирует (прямой POST с настоящим
  хэшем ответил `commit-id: null`). Коммит в карточке сборки проставляется только связью
  проекта с репозиторием. Параметры убраны из клиента, флаги `--branch`/`--commit`/
  `--commit-message` – из `builds upload`, `--commit-message` – из `deploy` и его инструмента
  MCP. Ветка и коммит по-прежнему едут ВНУТРИ архива: сборка пишет их в манифест, и у
  `build`/`deploy` флаги `--branch`/`--commit` остались ровно для этого.
- **Пропущенная сверка схемы называется в отчёте, а не только в прогрессе.** Отчёт деплоя несёт
  `schema-check`: `clean`, `allowed` (сужения пропущены `--allow-data-loss`) либо
  `skipped:<причина>` – пропущенная проверка не должна читаться как пройденная. А когда у
  применённой сборки нет коммита, сообщение объясняет механизм: коммит проставляется только
  связью проекта с репозиторием, без неё сверка не заработает никогда – это устройство,
  а не особенность версии сервера.

## 03.08.2026 – 0.25.0

### Изменено
- **Сборка с чужим именем отвергается, а не сопровождается предупреждением.** Панель показывает
  проект под именем ПОСЛЕДНЕЙ залитой сборки, поэтому чужая сборка переименовывает проект и его
  группу – а удаление сборки имя не возвращает. Теперь `builds upload` останавливается с кодом
  возврата 1 и называет цену, а выходы перечислены в сообщении: `--force-rename` – если так и
  задумано, `--new-project` – если сборка чужая. Сверка осталась вспомогательной: сравнить нечем –
  загрузка идёт как прежде.
## 31.07.2026 – 0.23.0, 0.24.0

### Исправлено

- **`self-update` сразу после релиза больше не пропускает его.** Список файлов брался из
  JSON-метаданных PyPI – кэша, который догоняет публикацию минутами: в этом окне команда
  отвечала "уже актуально", а с явной версией – "нет подходящего колеса", потому что файлы
  читались из того же отстающего документа. Теперь список берётся из SIMPLE-индекса (PEP 691),
  последняя версия ранжируется численно (`0.9.0` раньше `0.23.0`, без предрелизов и отозванных
  файлов), а JSON остался запасным путём для индекса, который PEP 691 не понимает. Сначала это
  доказано на движке инструментария, прямо в окне отставания: JSON отдавал ещё прежнюю версию,
  когда индекс уже отдавал новое колесо.

### Изменено

- **MCP-сервер работает с обоими мажорами пакета `mcp`, пин снят.** В `mcp 2.0.0` эргономичный
  класс сервера переехал – `FastMCP` из `mcp.server.fastmcp` стал `MCPServer` в
  `mcp.server.mcpserver`, а старый модуль не оставлен даже псевдонимом, – и свежая установка
  `elemctl[mcp]` брала новый мажор, после чего сервер не поднимался вовсе. Тогдашним ответом был
  пин `mcp>=1.2,<2`: установки он защитил, но заморозил их на 1.x. Теперь импорт сначала пробует
  новое расположение и при неудаче падает на старое, а extra допускает `mcp>=1.2,<3`. Всё, что
  сервер берёт от класса, в обоих мажорах одинаково – именованный параметр `instructions`,
  `@tool()` / `add_tool()`, `run()` по stdio, – поэтому состав инструментов, схемы и описания
  выходят те же; проверено по протоколу вызовами `initialize`, `tools/list` и `tools/call`.
  Различается чтение ответов: `inputSchema` стал `input_schema`, а `call_tool` возвращает
  `CallToolResult` вместо голого списка блоков содержимого. Ровно это прячут
  `tool_input_schema()` и `call_result_content()`, а CI прогоняет набор тестов на обоих мажорах.
- **`serverInfo` называет версию самого elemctl.** mcp 2.x спрашивает версию у сервера и при
  умолчании ставит пустую строку; в mcp 1.x такого параметра не было и подставлялась версия
  пакета `mcp`, которая версией инструмента никогда не являлась.

## 30.07.2026 – 0.22.0

### Добавлено

- **Сборка приложения забирает библиотечные проекты, лежащие рядом.** Если приложение объявляет
  библиотеки, исходники которых находятся под тем же корнем репозитория, их файлы попадают в
  архив вместе с ним, включая транзитивные зависимости; объявленная библиотека без локального
  проекта остаётся внешней зависимостью платформы, а посторонние соседние проекты в архив не
  затягиваются. Вклад @dvkuchin (запрос на слияние #3).

### Исправлено

- **Прокси в окружении больше не выдаёт живой стенд за мёртвый.** При заданном `HTTPS_PROXY`
  любой вызов падал голым обрывом соединения на `/console/sys/token`: urllib честно уважает
  прокси, а прокси, которому до стенда не дотянуться, отказывает ровно так же, как отказал бы
  лежащий стенд - на диагноз ушло два потерянных прогона. Теперь прокси, который заведомо не
  поможет, обходится (петлевые, приватные и link-local адреса, `localhost`, `.local`/`.lan` и
  подобные), `ELEMCTL_NO_PROXY=1` обходит его везде, а неудавшийся вызов, который всё-таки шёл
  через прокси, об этом говорит и называет его. Стенд, доступный только через корпоративный
  прокси, работает как прежде - поведение по умолчанию не менялось.
- **`self-update --stop-holders` больше не снимает собственное дерево процессов.** Запущенная
  через установленную обёртку, команда работает python-потомком лаунчера `elemctl.exe` – по
  имени тот неотличим от держателя, поэтому команда предлагала снять саму себя, и снятие
  обрывало обновление на полпути (страховка отката сохраняла прежнюю установку, но обновление
  не происходило). Теперь из держателей исключено собственное дерево процессов: предки –
  обёртка и то, что её запустило, – и потомки. Остальные живые процессы `elemctl` –
  настоящие держатели – по-прежнему называются и снимаются.

## 28.07.2026 – 0.20.0, 0.21.1

### Добавлено

- **Создание приложения заканчивается способом в него войти.** `apps create` и
  `apps ensure` (и их двойники в MCP) добавляют к ответу поле `sign-in` – адрес, код
  учётной записи `control-panel` и две фразы пояснения, – а CLI печатает то же самое в
  stderr. Почему это стоит говорить вслух: новое приложение получает СВОЙ пустой список
  пользователей, вход по логину и паролю в нём выключен, а сервис учётных записей не подключён,
  поэтому учётные записи, которыми входят в другие приложения,
  здесь не работают – и подключение чужого списка пользователей вместе с включением
  локального входа этого не меняет. Работает учётная запись ПАНЕЛИ УПРАВЛЕНИЯ: её
  пользователей платформа подключает к приложению сама. Раньше это находилось перебором,
  а перебирать как раз нельзя – у пользователя есть счётчик неудачных попыток входа. Пока
  приложение запускается и адреса ещё нет, в `url` стоит `null`, а не догадка, и подсказка
  говорит, откуда адрес взять.

### Изменено

- **`self-update` больше не меняет рабочую установку на пустое место.** Это случилось на
  прошлом выпуске, на той самой машине, которая публикует пакет: `pip install --upgrade`
  упёрся в занятый живой MCP-сессией `elemctl.exe`, удалил пакет, не распаковал новый и
  промолчал – `elemctl --version` ответил `ModuleNotFoundError`. Теперь команда сначала
  ПЕРЕИМЕНОВЫВАЕТ установленный пакет (переименование не проходит, пока файл внутри открыт, и
  в этот момент ещё ничего не удалено), называет держателей по имени и pid (`--stop-holders`
  снимает их) и хранит прежнюю установку, пока новая не ДОКАЖЕТ, что импортируется отдельным
  процессом: битый архив, сорванная распаковка и неимпортируемый пакет возвращают старую на
  место. Держателем считается свой исполняемый файл или интерпретатор, запустивший наши
  модули: клиент, у которого `elemctl mcp` лишь в собственной строке запуска, к снятию не
  предлагается. Порядок перенесён из движка инструментария, где обкатан первым.

## 27.07.2026 – 0.19.0

### Добавлено

- **`user-lists calculation-rules` – переприменить правила, по которым из ответа провайдера
  собирается пользователь.** Пересоздание сервиса входа их сбрасывает, и вернуть можно только
  записью; платформа принимает их в теле сервиса учётных записей под ключом, отличным от того,
  что стоит в СХЕМЕ того же справочника (на него она отвечает 400 – поэтому незнакомый ключ
  команда отвергает по имени, а не отправляет). Чтение сервиса эти правила НЕ возвращает, и
  отчёт говорит именно это: что отправлено, что запрос принят и что подтвердить значение через
  API нельзя – это отвечает панель управления или живой вход. Проверено другое: остальная
  карточка сервиса вернулась неизменной – запись несёт entry целиком, и ошибка тихо потеряла бы
  соседнее поле.

### Исправлено

- **Сборка, сделанная на раннере CI, записывала ветку `HEAD`.** Раннер выкладывает коммит, а
  не ветку, поэтому `git rev-parse --abbrev-ref HEAD` отвечает буквальным `HEAD` – это слово и
  попадало в `BranchName` каждой сборки, уехавшей из пайплайна. Поле манифеста существует,
  чтобы отвечать на вопрос "откуда эта сборка", и не отвечало ровно там, где нужнее всего.
  Отцепленный HEAD теперь берёт имя из окружения CI (`CI_COMMIT_BRANCH`, `CI_COMMIT_REF_NAME`,
  `GITHUB_REF_NAME`), а если ветку не называет никто – поле остаётся ПУСТЫМ: честный пробел
  лучше слова, похожего на имя ветки. Коммит записывался верно и не изменился, чистоту дерева
  по-прежнему решает `git status`.

## 26.07.2026 – 0.15.0, 0.16.0, 0.17.0, 0.18.0

### Добавлено

- **`deploy` называет цель и то, откуда она взялась.** В отчёте рядом с ид появились `app-name`,
  `app-id-source` и `project-id-source`, а сама цель объявляется ПЕРВОЙ строкой прогресса – до
  сборки, пока деплой не в то приложение ещё можно прервать. `--dry-run` показывает ту же цель
  мягко: он обязан собирать архив вообще без настроек, поэтому нечитаемый `.env` оставляет поля
  пустыми, а не роняет сборку.
- **Сборка называет файлы, которые в неё не вошли** (`skipped-files` в отчёте плюс
  предупреждение). Файл с расширением вне списка разрешённых попадает в архив, только если лежит
  в каталоге `Ресурсы`; в любом другом месте он тихо теряется, и платформа сообщает об этом лишь
  на применении – "Неизвестный ресурс". Намеренно исключённые файлы (`.gitignore`, `.env`, ранее
  собранные `.xasm`/`.xlib`) потерей не считаются.

- **Страж разрушающих изменений схемы.** Сужение длины реквизита или смена его типа при
  применении ПЕРЕСОЗДАЁТ данные объекта – расширение длин данные сохраняет, поэтому опасен именно
  узкий класс правок. `deploy` сверяет исходники на диске с состоянием на коммите применённой
  сборки и при находке отказывается работать ДО сборки: ничего не собрано и ничего не загружено.
  Пропустить – флагом `--allow-data-loss`. Реквизиты сопоставляются по `Ид`, как их сопоставляет
  платформа, поэтому переименование под тем же `Ид` молчит. Разбор – без внешних зависимостей, их
  у инструмента нет вовсе: читается блок `Реквизиты`, а всё незнакомое страж пропускает молча –
  он вправе не суметь рассудить, но не вправе выдумать изменение.
  **Чего он не может:** содержимое сборки Console API не отдаёт, скачать применённую и сравнить
  архивы нельзя – сверка держится на `commit-id` карточки сборки. Нет коммита, нет его в локальном
  репозитории – страж говорит, что судить не может, и НЕ мешает деплою: невозможность сравнить не
  есть доказательство опасности. Платформа может игнорировать параметры
  `CommitId`/`BranchName` при загрузке – даже явно переданное значение возвращается пустым, тогда
  как у сборок, загруженных ранее, коммит записан. Там, где это так, страж будет чаще молчать,
  чем судить.

- `elemctl user-lists` – настройки входа списка пользователей, за которыми обычно ходят в
  панель: `list`, `get`, `self-registration [--enable|--disable]` и
  `password-login [--enable|--disable]`. Список адресуется ид, точным представлением либо
  флагом `--app` – собственным списком приложения. Без флага обе команды-настройки только
  читают состояние, поэтому та же команда отвечает на вопрос "как сейчас". За "входом по
  логину и паролю" стоит сервис учётных записей типа `Local`: в ответе `enabled: null`,
  если такого сервиса у списка нет вовсе, а `changed` говорит, изменил ли что-то именно
  этот вызов – перевод в состояние, которое уже стоит, запроса не делает. Со стороны MCP –
  `list_user_lists` и `configure_user_list`, делающий обе настройки одним вызовом.

- Группа точек расширения **`elemctl.commands`** – пакет-плагин приносит собственные команды.
  Значение – `Command`, их список либо функция без аргументов, возвращающая одно из этого;
  одно объявление служит сразу обеим поверхностям, становясь подкомандой CLI и инструментом
  MCP с настоящей схемой, а ядро о том, что команда делает, ничего не знает. Там место
  команде, которая знает про чужое окружение – внутренние контуры, смежные системы, приватные
  стенды – и потому в публичном ядре жить не может. Типы объявления – `Argument`, `Command` и
  `CommandContext` из `elemctl.plugins`; обработчик получает конфигурацию, клиент, который
  строится при первом обращении, и колбэк прогресса. Результат-словарь с `"ok": false` даёт
  код возврата 1, инструмент MCP дополнительно принимает `env_file` и возвращает прогресс
  полем `log`. Занять имя, которое уже есть у ядра, плагин не может – ни подкомандой, ни
  инструментом, – а неверное объявление становится известно при обнаружении, а не при запуске
  команды.
- `plugins` сообщает о командах плагинов (`commands`: имя, точка расширения и имя инструмента
  MCP) рядом с каталогами адаптера.

- `elemctl probe` – изолированная проверка компиляции исходников, не трогающая рабочее
  приложение. Компиляция у этой платформы серверная и происходит на применении сборки,
  поэтому пробник собирает архив, загружает его, создаёт из него ОДНОРАЗОВОЕ приложение –
  это и есть компиляция, – а затем убирает созданное за собой. Ошибки приходят разобранными:
  `file` (путь относительно каталога проекта), `line`, `column`, `environment`
  (`Сервер`/`Клиент`) и текст; сообщения платформы дословно сохраняются в `messages`.
  `ELEMENT_APP_ID` и `ELEMENT_PROJECT_ID` намеренно не используются – пробник не должен
  иметь возможности достать рабочее приложение. Код возврата 0 только при `ok`; `--keep`
  оставляет приложение и сборку на стенде для разбора руками. То же самое – инструментом
  MCP `probe`.

### Исправлено

- **Глобальная опция принимается и после подкоманды.** `--env-file`, `--lang`, `--base-url`,
  `--client-id`, `--client-secret` и `--timeout` объявлены у корневого парсера, поэтому
  `elemctl deploy --env-file .env` падал argparse-фразой "unrecognized arguments", а правило
  порядка приходилось держать в чек-листе и трёх скиллах. Теперь опции поднимаются в начало argv;
  работают обе формы записи, а токены после одиночного `--` не трогаются.
- **Отвергнутый сервером токен больше не живёт в кэше.** Повтор с обновлением токена ждал 401, но
  негодный токен этот сервер отвергает **400 `invalid_request`**, называя причину в
  `error_description` ("JWT strings must contain exactly 2 period characters", "Unable to verify
  RSA signature ..."). Оба ответа воспроизводятся подложенным в кэш токеном –
  отсюда и лечение, записанное как ручное удаление `<TEMP>/elemctl-token-*.json`. Такой отказ
  теперь сбрасывает ФАЙЛ кэша и повторяет запрос один раз; обычный неверный запрос, в описании
  которого о токене ничего нет, не повторяется.

- Задокументированное поведение удаления сборки было неверным: платформа отклоняет его с 500
  только пока живо созданное из этой сборки приложение – после того как приложение
  действительно исчезло, тот же запрос проходит. Поэтому `probe` сначала удаляет приложение,
  дожидается его исчезновения (новый `wait_app_deleted` клиента) и лишь затем удаляет сборку.

### Документация

- Контракт Console API пополнился списками пользователей (п. 4.7): конечные точки настроек,
  смысл сервиса учётных записей `Local` и тот факт, что у связи приложения со списком
  собственных настроек нет. Записано и остальное: состава ФОРМ аутентификации и настройки
  "подключать пользователей автоматически" в API нет вовсе;
  правила разбора ответа сервиса учётных записей принимаются под ключом
  `userPropertiesCalculationRules`, тогда как схема самого справочника называет их
  `calculation-rules` и на такое написание платформа отвечает 400, – а GET их не
  возвращает никогда, то есть настройка на запись; `POST /user-lists` требует карточку
  целиком и на всё меньшее отвечает 500 "Failed to parse json"; неизвестный путь Console
  API отвечает 401 "Handler ... not found", а не 404.

- Проект платформы опознаётся парой `Vendor` + `Name` манифеста, а не `Ид` из `Проект.yaml`:
  загрузка без ид проекта попадает в тот проект, которому пара уже принадлежит, а второй
  проект под ту же пару отклоняется с 409 `ALREADY_EXISTS` (генерация нового `Ид` не спасает).
  Ответ на загрузку описывает этот проект объектом `artifact`: `artifact-id`,
  `configuration-id`, `name`.
