# История изменений

Заметные изменения elemctl, свежие сверху. Записи сгруппированы по дням; версии, вышедшие в этот
день, перечислены в заголовке. Формат основан на
[Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), проект следует
[семантическому версионированию](https://semver.org/lang/ru/).

Новые записи должны содержать ссылку на пул-реквест, например
`([#12](https://github.com/keyfire/elemctl/pull/12))`. Ссылка позволяет проверить
код и причину изменения. Описывайте поведение для пользователя; не включайте
идентификаторы реальных приложений и проектов или внутреннюю инфраструктуру.

Команда `python scripts/changelog-link.py <номер>` добавляет ссылку и обновляет
сгенерированные страницы сайта. Запускайте ее вместо ручного добавления ссылки,
чтобы одновременно обновить обе языковые версии и их зеркала.

## 08.10.2026 – 0.52.0

### Добавлено

- **Проверка целевого приложения перед деплоем.** Параметры `--expected-app-name` и `--expected-app-uri` задают ожидаемые имя и адрес приложения. При несовпадении с карточкой на сервере `deploy` завершается до сборки и загрузки. Проверка доступна также в библиотеке и MCP. ([#58](https://github.com/keyfire/elemctl/pull/58))

## 30.09.2026 – 0.50.0, 0.51.0

### Добавлено

- **Повторяемые опции команд плагинов: `Argument(..., multiple=True)`.** Значения передаются команде списком в порядке указания в CLI, а соответствующий инструмент MCP принимает массив. До этой правки при повторении опции сохранялось только последнее значение: при указании семи файлов загружался один. ([#54](https://github.com/keyfire/elemctl/pull/54))

- **Несколько значений позиционного аргумента плагина: `multiple=True`.** Значения можно указать подряд или повторить ключ `cli_alias`. До исправления при повторении ключа сохранялось только последнее значение. Инструмент MCP принимает массив. Для совместимости со старым ядром проверяйте наличие `plugins.POSITIONAL_MULTIPLE`: без этой возможности объявление аргумента отклоняется. ([#56](https://github.com/keyfire/elemctl/pull/56))

### Изменено

- **Отказ при повторении опции с разными значениями.** Раньше `--output a --output b` записывало результат в `b`, а значение `a` игнорировалось без предупреждения. Теперь CLI завершается с кодом 2; сообщение об ошибке содержит имя опции и оба значения. Это относится и к командам плагинов. Одинаковые значения, повторяемые опции и флаги допускаются. ([#57](https://github.com/keyfire/elemctl/pull/57))

### Исправлено

- **Фильтрация по нескольким статусам в `apps list --status running --status stopped`.** До исправления второй параметр заменял первый, хотя в справке были указаны несколько статусов. Теперь учитываются оба. Перечисление через запятую поддерживается по-прежнему. ([#54](https://github.com/keyfire/elemctl/pull/54))

- **Повторяемые параметры `apps token-access --user` и `probe --cleanup`.** Раньше второе значение заменяло первое без предупреждения. Теперь для каждого пользователя или временного приложения возвращается отдельный результат, а ошибка одного не прерывает обработку остальных. Инструменты MCP также принимают список. ([#55](https://github.com/keyfire/elemctl/pull/55))

## 29.09.2026 – 0.47.0, 0.48.0, 0.49.0

### Добавлено

- **Проект в результате `builds upload` без идентификатора проекта.** Раньше команда выводила `project-id: null`, хотя идентификатор был в ответе сервера. Теперь результат содержит `project-id` и карточку `project`. В stderr выводится сообщение о создании проекта или выборе существующего по `Ид` из `Проект.yaml`. ([#52](https://github.com/keyfire/elemctl/pull/52))

- **Источник вызова команды плагина в `CommandContext.surface`.** Значение равно `SURFACE_CLI` для подкоманды CLI, `SURFACE_MCP` для инструмента MCP и `None` для контекста, созданного вручную. Раньше для определения источника требовалась косвенная проверка `context.log`. ([#47](https://github.com/keyfire/elemctl/pull/47))

- **`--quiet` в любом месте команды.** Раньше при указании флага после команды плагина возникала ошибка "unrecognized arguments". Флаг отключает сообщения о ходе работы и предупреждения в stderr, включая вывод через `context.log` плагина. Результат, ошибки и код возврата сохраняются. ([#47](https://github.com/keyfire/elemctl/pull/47))

- **`apps export-extension` сохраняет сборку расширения, примененного в приложении.** То же делает
  инструмент MCP `export_extension`. Если такого расширения в приложении нет, ошибка перечисляет те,
  что есть. Нужен Console API 2.1. ([#48](https://github.com/keyfire/elemctl/pull/48))
- **Экспорт текущей сборки приложения через `apps export`.** Та же операция доступна в MCP как `export_app`. Сборка, загруженная в проект, экспортируется с номером, присвоенным сервером. Для примененных расширений используется `apps export-extension`. ([#49](https://github.com/keyfire/elemctl/pull/49))

### Изменено

- **Определение проекта сборки в `apps create --version-id`.** Если сборки нет в проекте из `ELEMENT_PROJECT_ID`, выполняется поиск по другим проектам. Если неверный проект задан явно через `--project-id`, создание завершается с ошибкой и указанием нужного проекта. Такое же поведение у инструментов MCP `create_app` и `ensure_app`. ([#52](https://github.com/keyfire/elemctl/pull/52))

- **Сведения об отсутствии автоматической очистки в `builds list` для проекта расширения.** Сборки такого проекта сохраняются до ручного удаления. Пропуск в их нумерации означает удаление вручную. ([#52](https://github.com/keyfire/elemctl/pull/52))

- **Прекращение ожидания после минуты в статусе `UNKNOWN`.** Раньше ожидание продолжалось до полного таймаута: пять минут для `deploy` и десять для нового приложения. Поскольку `UNKNOWN` возможен и при переходных состояниях, предусмотрена минута ожидания. Затем операция завершается с пояснением ошибки. ([#47](https://github.com/keyfire/elemctl/pull/47), [#49](https://github.com/keyfire/elemctl/pull/49))

### Исправлено

- **Сохранение выполняемых команд при `self-update --stop-holders`.** Раньше обновление могло прервать команду ожидания конвейера с кодом 1 без результата. Теперь флаг завершает только MCP-серверы. Остальные команды перечисляются с PID и командной строкой; если они используют файлы пакета, обновление отклоняется до их завершения. Для остановки всех процессов предусмотрен `--stop-holders=all`. ([#53](https://github.com/keyfire/elemctl/pull/53))

- **Предупреждение о переименовании проекта при загрузке без его идентификатора.** Если сервер выбирает проект с тем же `Ид` и другим именем, `builds upload` и `probe` выводят предупреждение и возвращают прежнее имя проекта. Новое имя берется из представления в `Проект.yaml`. Ранее в документации ошибочно было указано поле `Name` манифеста. ([#52](https://github.com/keyfire/elemctl/pull/52))

- **`ROUTE_NAME` вернулась в `elemctl.registry`.** Прошлый выпуск переименовал константу в
  `ROUTE_NO_PROJECT_ID`, и код, который импортировал старое имя, ломался. Теперь старое имя –
  синоним нового. ([#52](https://github.com/keyfire/elemctl/pull/52))
- **Проверка конфликтов между аргументами плагина и ядра.** Параметр плагина `--timeout` не получал значение, `--env-file` препятствовал запуску MCP-сервера, а `handler`, `--help` или `-h` вызывали ошибку команды или всего CLI. Теперь такой плагин не загружается, а сообщение об ошибке содержит его имя. ([#48](https://github.com/keyfire/elemctl/pull/48), [#49](https://github.com/keyfire/elemctl/pull/49))

- **Учет удаленной последней сборки при нумерации в `deploy`.** Сервер учитывает удаленные сборки, которых нет в списке. Для расчета следующего номера теперь используется и локальный реестр загрузок. Сведения об удаленной сборке с другой машины могут отсутствовать; в этом случае выводится фактический номер от сервера. ([#48](https://github.com/keyfire/elemctl/pull/48))

- **`build` собирает проект расширения как расширение.** Теперь в манифесте `ProjectKind: Extension`
  и `ManifestVersion: 1.1`, как у консоли, а `build --kind` принимает `extension`. Раньше сервер
  отвергал даже исправленный вручную архив с ошибкой "Неизвестный вид проекта".
  ([#49](https://github.com/keyfire/elemctl/pull/49))
- **Обработка недоступного метода на старом сервере без повторной авторизации.** Раньше ответ 401 "Handler of HTTP request ... not found" обрабатывался как отказ в токене, после чего выполнялся повторный вход. Теперь клиент сначала проверяет текст ответа и сообщает о неизвестном методе. ([#49](https://github.com/keyfire/elemctl/pull/49))

- **Уточнение сведений о нумерации в `builds list`.** Для пустого списка выводится сообщение об отсутствии сборок, а для сборок без номеров – о недостаточности данных для анализа. Если пропуск связан и со скачком номера, и с удалением, в результате указаны обе причины. ([#49](https://github.com/keyfire/elemctl/pull/49))

- **Предупреждение об отключенной проверке сертификата больше не ссылается на незаданную
  настройку.** Оно называло `ELEMENT_TLS_VERIFY=false`, даже если проверку отключили в коде. Теперь
  `UrllibTransport` принимает причину параметром `tls_off_reason`.
  ([#49](https://github.com/keyfire/elemctl/pull/49))
- **Проверка применения расширения без ложного сообщения об откате.** Карточка приложения содержит номер сборки самого приложения, поэтому `apps apply`, `deploy` и `verify-deploy` раньше ошибочно определяли применение расширения как откат. Теперь проверяется список расширений приложения. На сервере без Console API 2.1 возвращается результат "проверить нельзя". ([#50](https://github.com/keyfire/elemctl/pull/50))

- **Проверка уже примененной сборки расширения в `apps ensure`.** Раньше сравнение с карточкой приложения приводило к ответу `applied: false`. Теперь используется список расширений приложения, как в `apps apply` и `verify-deploy`. Исправление также относится к `ensure_app`. ([#51](https://github.com/keyfire/elemctl/pull/51))

### Документация

- **Спецификация правильно называет флаги, которые принимаются после подкоманды.** В перечне был
  `--version`, который там не принимается, и не было `--lang`, который принимается.
  ([#48](https://github.com/keyfire/elemctl/pull/48))
- **Описание автоматической очистки неиспользуемых сборок.** Сервер выполняет ее после применения сборки в приложении проекта. Проверяется до десяти сборок этой базы; сохраняются используемые сборки, сборка с наибольшим номером, релизные и защищенные сборки. При загрузке по поставщику и имени защита устанавливается сразу. ([#49](https://github.com/keyfire/elemctl/pull/49))

- **Выбор проекта по `Ид` из описания.** Поставщик и имя не определяют идентичность проекта. При загрузке с тем же `Ид` и другим именем сборка добавляется в существующий проект, который переименовывается. Новый `Ид` с уже занятой парой поставщика и имени приводит к ответу 409. ([#50](https://github.com/keyfire/elemctl/pull/50))

- **Исключение сборок расширений из автоматической очистки.** Очистка выполняется для сборок приложения. Все сборки проекта расширения сохраняются до ручного удаления. ([#51](https://github.com/keyfire/elemctl/pull/51))

- **Название маршрута загрузки без идентификатора проекта.** Сервер выбирает проект по `Ид`, а не по поставщику и имени. В новых записях реестра используется `no-project-id`; прежнее значение `vendor-name` остается доступным для чтения. ([#51](https://github.com/keyfire/elemctl/pull/51))

## 27.09.2026 – 0.46.0

### Добавлено
- **Проверка удаления объектов метаданных перед `deploy`.** Раньше проверка схемы учитывала только существующие файлы. Удаленный из исходников справочник, документ или регистр мог быть применен с удалением всей таблицы без предупреждения. Теперь проверяется и список файлов примененного коммита. Удаление таких объектов отклоняется, как и сужение типов, если не задан `--allow-data-loss`. ([#45](https://github.com/keyfire/elemctl/pull/45))

- **Параметр `allow_data_loss` у инструмента MCP `deploy`.** Раньше разрешить сужение типов после отказа проверки схемы можно было только из CLI. Теперь разрешение доступно и через MCP. Сообщение об отказе содержит и параметр MCP, и соответствующий флаг CLI. ([#45](https://github.com/keyfire/elemctl/pull/45))

- **Сведения о перенумерации сборки сервером в `deploy`.** При загрузке в проект сервер присваивает следующий номер базы проекта независимо от версии в архиве. Раньше отчет возвращал `ok`, а перенумерация была видна только по различию `version` и `applied-version`. Теперь до сборки выводится предупреждение о версии, которая не сохранится, а после загрузки – фактический номер. В отчет добавлены `assembly-version` и `renumbered`. ([#45](https://github.com/keyfire/elemctl/pull/45))

- **Список пользователей приложения: `apps users`.** Раньше он был доступен только в сообщении об отказе `apps token-access`. Команда и инструмент MCP `list_app_users` возвращают данные сервера и количество администраторов и пользователей с доступом по токену. ([#46](https://github.com/keyfire/elemctl/pull/46))

- **Проверка изменения `Ид` справочника перед `deploy`.** При замене идентификатора в существующем файле сервер создает новый объект метаданных. Проверка на сервере подтвердила потерю данных справочника, тогда как прежняя проверка учитывала только поля. Теперь замена идентификатора отклоняется как удаление объекта. В ошибке указан прежний `Ид`, который нужно восстановить. ([#46](https://github.com/keyfire/elemctl/pull/46))

### Изменено
- **Коммит из реестра загрузок при проверке схемы `deploy`.** В карточке сборки, при загрузке которой был создан проект, нет коммита. Раньше из-за этого проверка пропускалась, даже если коммит был сохранен локально. Теперь используется запись реестра загрузок, а в отчете указан источник коммита. ([#45](https://github.com/keyfire/elemctl/pull/45))

- **Ограничение реестра загрузок последними тысячей записей.** Раньше файл увеличивался после каждой загрузки без ограничения размера. Когда количество записей превышает предел на 10%, при следующей загрузке старые записи удаляются. Другой предел задается через `ELEMCTL_REGISTRY_LIMIT`; значение `0` отключает ограничение. ([#45](https://github.com/keyfire/elemctl/pull/45))

- **Статусы `Deleting` и `UNKNOWN` в спецификации.** В справочнике статус приложения имеет строковый тип. Добавлены два наблюдавшихся состояния: `Deleting` при удалении приложения и `UNKNOWN` при отсутствии его базы. При ожидании стабильного состояния `UNKNOWN` не считается результатом. ([#46](https://github.com/keyfire/elemctl/pull/46))

### Исправлено
- **Удаление временного приложения с произвольными именем и версией через `probe --cleanup`.** Раньше без стандартных признаков временного приложения очистка отклонялась, и приложение, сборки и проект приходилось удалять вручную. Теперь созданное приложение регистрируется в реестре загрузок. По этой записи можно удалить его и загруженные в него сборки. ([#46](https://github.com/keyfire/elemctl/pull/46))

- **Загрузка в указанное пространство.** Раньше клиент передавал параметр `SpaceId`, который сервер игнорировал. Пространство нового проекта не задавалось, и неверное значение не вызывало ошибки. Теперь при загрузке в проект передается `space-id`, а новый проект создается в пространстве через `POST /spaces/{space-id}/projects`. ([#46](https://github.com/keyfire/elemctl/pull/46))

- **Различение скачка нумерации и автоматического удаления в `builds list`.** При загрузке по поставщику и имени сохраняется номер архива, от которого продолжается нумерация проекта. Раньше пропуск перед таким номером ошибочно объяснялся удалением сборок. Теперь маршрут загрузки сохраняется в реестре, а такой пропуск обозначается как скачок нумерации. ([#46](https://github.com/keyfire/elemctl/pull/46))

## 25.09.2026 – 0.45.0

### Добавлено
- **Связь сборки с исходным кодом.** При загрузке в проект коммит передается под именем параметра из справочника и сохраняется сервером в карточке сборки. Ветка, состояние рабочего дерева и каталог сохраняются только в локальном реестре загрузок. В `builds list --brief` и `apps get` указан источник каждого значения. ([#42](https://github.com/keyfire/elemctl/pull/42))

- **Управление доступом по токену через `apps token-access`.** Раньше вызов HTTP-сервиса с токеном пользователя завершался ответом 500 "Token access is denied", пока доступ не включали в панели управления. Команда и инструмент MCP `token_access` позволяют проверить и изменить настройку, затем прочитать ее повторно. Если пользователь не подключен к приложению, выводится сообщение с его именем. ([#43](https://github.com/keyfire/elemctl/pull/43))

- **Удаление сохраненного временного приложения через `probe --cleanup`.** При ручной очистке `builds delete` без проекта выполняло поиск в проекте из окружения, а не в проекте временного приложения. Новая команда удаляет приложение, его сборку и пустой проект в порядке, предусмотренном сервером. Для приложения, созданного другим способом, очистка отклоняется. Результат `probe --keep` содержит команду очистки и порядок ручного удаления. ([#43](https://github.com/keyfire/elemctl/pull/43))

### Исправлено
- **Сообщение о запуске сервера и ожидание консоли.** Раньше во время запуска консоли команды возвращали 404 без пояснения, а `deploy` завершался на запросе списка сборок. Теперь ошибка содержит причину и рекомендацию повторить запрос после ответа 302 от `/console`. В `deploy` предусмотрено ожидание консоли до `--server-start-timeout` секунд. ([#42](https://github.com/keyfire/elemctl/pull/42))

## 26.07.2026 – 0.15.0, 0.16.0, 0.17.0, 0.18.0

### Добавлено

- **`deploy` указывает цель и источник ее определения.** В отчет добавлены `app-name`, `app-id-source` и `project-id-source`. Цель выводится в первой строке прогресса до сборки, чтобы можно было вовремя обнаружить ошибку.

- **Сборка сообщает об исключенных файлах** через `skipped-files` и предупреждение. Файл с расширением вне списка разрешенных включается только из каталога `Ресурсы`. Ранее исключение такого файла из другого каталога обнаруживалось только при применении.

- **Проверка разрушающих изменений схемы перед развертыванием.** Сужение длины реквизита или смена типа пересоздает данные объекта. `deploy` сравнивает исходники с коммитом примененной сборки и останавливается до сборки при обнаружении таких изменений; `--allow-data-loss` пропускает проверку. Если сравнение невозможно, отчет сообщает об этом и развертывание продолжается.

- **`user-lists` управляет настройками входа списка пользователей.** Доступны команды `list`, `get`, `self-registration` и `password-login`. Две команды настройки без флага только читают состояние. В MCP доступны `list_user_lists` и `configure_user_list`.

- **Точки расширения `elemctl.commands`.** Пакет-плагин может объявить команду, которая становится подкомандой CLI и инструментом MCP. Это позволяет добавлять команды для отдельных окружений вне публичного ядра.

- **`elemctl probe` проверяет компиляцию в изолированном приложении.** Компиляция выполняется на сервере при применении сборки. Команда собирает архив, создает временное приложение и удаляет созданные ресурсы. Ошибки возвращаются с файлом, строкой, колонкой, окружением и текстом.

### Исправлено

- **Глобальная опция принимается и после подкоманды** – `elemctl deploy --env-file .env` больше
  не падает argparse-фразой "unrecognized arguments".
- **Отклоненный токен удаляется из кеша.** Сервер возвращает 400 вместо 401 и указывает причину в `error_description`. При таком ответе файл кеша удаляется, а запрос повторяется один раз.

- **Пробная сборка удаляется после удаления приложения.** Пока созданное из сборки приложение существует, сервер отклоняет удаление сборки. Пробная проверка сначала ожидает удаления приложения.

### Документация

- **Добавлен раздел о списках пользователей** (п. 4.7). Также перечислены настройки, недоступные через Console API: состав форм аутентификации и автоматическое подключение пользователей.
- **Описание выбора проекта по `Vendor` и `Name` в этом выпуске.** Предполагалось, что `Ид` из `Проект.yaml` не используется, а повтор пары приводит к 409 `ALREADY_EXISTS`. Позднейшие проверки уточнили контракт: проект определяется по `Ид`, а пара поставщика и имени должна быть уникальной в пространстве.
