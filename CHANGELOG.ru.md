# История изменений

Заметные изменения elemctl, свежие сверху. Записи сгруппированы по дням; версии, вышедшие в этот
день, перечислены в заголовке. Формат основан на
[Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), проект следует
[семантическому версионированию](https://semver.org/lang/ru/). Спутник отладки для VS Code в
`editors/vscode` выпускается отдельно по тегам `vscode-v*` и здесь не отслеживается.

## Не выпущено

### Добавлено
- Группа точек расширения **`elemctl.commands`** – пакет-плагин приносит собственные команды.
  Значение – `Command`, их список либо функция без аргументов, возвращающая одно из этого;
  одно объявление служит сразу обеим поверхностям, становясь подкомандой CLI и инструментом
  MCP с настоящей схемой, а ядро о том, что команда делает, ничего не знает. Там место
  команде, которая знает про чужое окружение – внутренние контуры, смежные системы, приватные
  стенды – и потому в публичном ядре жить не может. Типы объявления – `Argument`, `Command` и
  `CommandContext` из `elemctl.plugins`; обработчик получает конфигурацию, клиент, который
  строится при первом обращении, и колбэк прогресса. Результат-словарь с `"ok": false` даёт
  код возврата 1, инструмент MCP дополнительно принимает `env_file` и возвращает прогресс
  полем `log`. Занять имя, которое уже есть у ядра, плагин не может – ни подкомандой, ни
  инструментом, – а неверное объявление становится известно при обнаружении, а не при запуске
  команды.
- `plugins` сообщает о командах плагинов (`commands`: имя, точка расширения и имя инструмента
  MCP) рядом с каталогами адаптера.

## 2026-07-26 – 0.15.0

### Добавлено
- `elemctl probe` – изолированная проверка компиляции исходников, не трогающая рабочее
  приложение. Компиляция у этой платформы серверная и происходит на применении сборки,
  поэтому пробник собирает архив, загружает его, создаёт из него ОДНОРАЗОВОЕ приложение –
  это и есть компиляция, – а затем убирает созданное за собой. Ошибки приходят разобранными:
  `file` (путь относительно каталога проекта), `line`, `column`, `environment`
  (`Сервер`/`Клиент`) и текст; сообщения платформы дословно сохраняются в `messages`.
  `ELEMENT_APP_ID` и `ELEMENT_PROJECT_ID` намеренно не используются – пробник не должен
  иметь возможности достать рабочее приложение. Код возврата 0 только при `ok`; `--keep`
  оставляет приложение и сборку на стенде для разбора руками. То же самое – инструментом
  MCP `probe`.

### Исправлено
- Задокументированное поведение удаления сборки было неверным: платформа отклоняет его с 500
  только пока живо созданное из этой сборки приложение – после того как приложение
  действительно исчезло, тот же запрос проходит. Поэтому `probe` сначала удаляет приложение,
  дожидается его исчезновения (новый `wait_app_deleted` клиента) и лишь затем удаляет сборку.

### Документация
- Проект платформы опознаётся парой `Vendor` + `Name` манифеста, а не `Ид` из `Проект.yaml`:
  загрузка без ид проекта попадает в тот проект, которому пара уже принадлежит, а второй
  проект под ту же пару отклоняется с 409 `ALREADY_EXISTS` (генерация нового `Ид` не спасает).
  Ответ на загрузку описывает этот проект объектом `artifact`: `artifact-id`,
  `configuration-id`, `name`.

## 2026-07-25 – 0.14.0

### Добавлено
- Сборка: без явной версии и последней сборки суффикс версии берётся из номера прогона CI
  в окружении (`CI_PIPELINE_IID`, `GITHUB_RUN_NUMBER`, `BUILD_NUMBER` – первое числовое
  значение в этом порядке): чистый рабочий каталог CI больше не даёт `-1` на каждом прогоне,
  и джоба CI сводится к простому `elemctl build`.
- `build` (и `deploy --dry-run`) выводят рядом с `file` поля `name`, `vendor`, `version`,
  `version-source` (`flag`/`last-build`/имя CI-переменной/`default`), `kind`, `branch`,
  `commit` и `dirty` – CI больше не выковыривает версию из имени файла.
- `apps get/delete/start/stop/debug` (CLI) и `get_app`/`delete_app`/`start_app`/`stop_app`/
  `debug_info` (MCP) принимают точное имя приложения наравне с ид: не-UUID резолвится по
  списку без учёта регистра; несколько совпадений – ошибка с перечнем ид, разрушающие
  команды не угадывают.
- `apps list --brief` – краткие карточки (ид, имя, статус, uri, применённая версия), как
  давно умеет инструмент MCP; вместе с `--name` вопрос "жив ли acme-crm-dev" решается парой
  сотен байт вместо десятков килобайт.
- Отчёт деплоя и `elemctl build` показывают незакоммиченные изменения каталога проекта
  (`dirty`, `dirty-files` плюс предупреждение в stderr): сборка снимает текущее состояние
  диска, и расхождение с HEAD должно быть видно. Новый флаг `--require-clean` у `build` и
  `deploy` вместо этого прерывает работу до сборки (недоступный git – тоже отказ:
  подтвердить чистоту дерева нечем).

### Изменено
- `apps list --name` (CLI) и `list_apps(name=...)` (MCP) фильтруют по подстроке имени без
  учёта регистра на клиенте. Платформа игнорирует query-параметр `name` и возвращает полный
  список (проверено живым вызовом), поэтому прежний сквозной фильтр не фильтровал ничего.
- Ключи дескриптора `Проект.yaml` читаются в обоих написаниях – `Имя`/`Name`,
  `Поставщик`/`Vendor`, `Версия`/`Version`, `ВидПроекта`/`ProjectKind` (значения
  `Библиотека`/`Library`), то же для `CompatibilityMode`/`Presentation` в `inspect`:
  двуязычие исходников – заявленная возможность платформы, дескриптор с английскими
  ключами применяется штатно. Раньше такой проект отвергался с "должны быть заполнены
  поля Имя и Поставщик", а смешанный молча получал версию `1.0` вместо заявленной.
- Ожидания статусов приложения считают `Error` терминальным: `deploy` падает сразу с
  ошибками компиляции из задач, а не опрашивает `Stopped` весь 180-секундный таймаут
  (приложение в `Error` до `Stopped` не доходит).

### Исправлено
- `--lang en` теперь английский везде. Около сорока строк, обращённых к пользователю, были
  зашиты в модулях русскими литералами мимо каталога сообщений, и англоязычный пользователь
  всё равно получал русский текст от `deploy` (проблемы отчёта), `self-update` (весь его
  прогресс), ошибок конфигурации, загрузчика плагинов и нескольких ошибок `apps`. Теперь это
  ключи каталога, а тест обходит модули и не даёт новым литералам появиться снова.

## 2026-07-24 – 0.13.1

### Исправлено
- Сборка: файлы из каталогов `Ресурсы` попадают в архив независимо от расширения
  (`.pdf`, `.htm`, `.mxl`, `.docx`, `.xsd` и т.д.) – ресурс по документации платформы
  произвольный файл. Раньше на них действовал общий белый список расширений, файлы
  молча выпадали из сборки, и применение падало с ошибкой "Неизвестный ресурс",
  после чего платформа откатывала деплой. Вне каталогов ресурсов белый список
  действует по-прежнему и пополнился `.htm` (раньше включался только `.html`).

## 2026-07-24 – 0.12.0

### Добавлено
- `builds upload` сообщает цель загрузки: в JSON-выводе появились `project-id` и
  `project-id-source` (`flag`/`env`/нет), а когда цель пришла из `ELEMENT_PROJECT_ID`,
  об этом говорит строка в stderr – раньше сборка молча ложилась в проект из окружения,
  когда задумывался новый проект.
- `builds upload --new-project` загружает сборку новым проектом, игнорируя
  `ELEMENT_PROJECT_ID` из окружения и `.env`-файла.
- `builds upload` предупреждает, когда имя сборки не совпадает с именем проекта-цели:
  панель показывает проект под именем последней залитой сборки, и чужая сборка молча
  переименовывает проект. Проверка вспомогательная и загрузку не блокирует.
- Справочник команд и его генератор под тестами (`tests/test_cli_docs.py`): каждая команда
  отвечает на `--help`, каждая покрыта разделом справочника, страницы остаются свежими, а две
  языковые версии действительно различаются.
