# Elemctl

[English](https://github.com/keyfire/elemctl/blob/main/README.md) · **Русский**

**Документация: [docs.keyfire.ru/elemctl](https://docs.keyfire.ru/elemctl/ru/)**

Утилита командной строки, MCP-сервер и Python-библиотека для управления
приложениями облачной платформы **1С:Предприятие.Элемент** (1cmycloud.com)
через Console API v2.

elemctl ведет приложение на платформе весь его срок жизни, и веб-консоль
для этого не нужна. Он создает приложение, собирает архив `.xasm`/`.xlib`
из исходников проекта, загружает сборку и применяет ее к приложению. Дальше
он проверяет, что применение и правда случилось: платформа умеет молча
откатить. Компиляцию проверяет пробник, который рабочее приложение не
трогает. Отдельные команды ведут ветки среды разработки, дампы и версию
технологии.

Движок один, а обратиться к нему можно тремя способами: командой `elemctl`
из терминала и CI, MCP-сервером для AI-агентов (Claude Code и другие
MCP-клиенты), python-модулем `elemctl` из своих скриптов.

*elemctl is a CLI tool, MCP server and Python library for the
1C:Enterprise.Element (1cmycloud) Console API: manage applications, upload
builds, deploy with a verified apply and check compilation with a probe.
The documentation comes in both languages, and the CLI output is plain JSON.*

Заметки о разработке и новости – в Telegram-канале [1С × ИИ: инженерный цех](https://t.me/ceh_1c_ai).

## Возможности

<!-- features:start -->

- **Приложения**: список, карточка, создание, запуск, остановка и удаление.
  Доступны версия технологии и данные сессии отладки (`apps debug`). Команды
  `apps export` и `apps export-extension` сохраняют в файл сборку приложения
  и сборку примененного расширения. Для второй команды нужен Console API 2.1.
  Список приложений фильтруется по имени на стороне клиента. Параметр `--brief`
  включает краткие карточки. Отдельное приложение указывается по ид или точному имени.
- **Проекты и сборки**: загрузка `.xasm`/`.xlib`, просмотр и удаление сборок.
- **Сборка из исходников**: каталог с `Проект.yaml` и модулями упаковывается
  в архив с манифестом и git-метаданными. Версия определяется по флагу,
  счетчику последней сборки или номеру запуска CI: `CI_PIPELINE_IID`,
  `GITHUB_RUN_NUMBER`, `BUILD_NUMBER`. Версия также включается в результат команды.
  Поддерживаются русские ключи дескриптора и английские `Name`/`Vendor`/`Version`.
  Приложение, библиотека и расширение собираются одинаково. Для расширения
  используется версия манифеста, необходимая серверу для его обработки.
- **Развертывание одной командой**: сборка -> загрузка -> применение ->
  перезапуск -> **проверка фактического применения**. Незакоммиченные изменения
  каталога проекта отмечаются полем `dirty` в отчете. С флагом `--require-clean`
  выполнение останавливается, если в рабочем дереве есть такие изменения.
- **Проверка компиляции** (`elemctl probe`): исходники компилируются на сервере
  во временном приложении. Ошибки содержат файл, строку и колонку. После проверки
  созданные объекты удаляются. Рабочее приложение не изменяется:
  `ELEMENT_APP_ID` и `ELEMENT_PROJECT_ID` при проверке не используются.
- **Списки пользователей** (`elemctl user-lists`): настройка самостоятельной
  регистрации и входа по логину и паролю. Список указывается по ид,
  представлению или приложению, которому он принадлежит.
- **Ветки среды разработки**: список, создание, привязка к приложению и слияние.
- **Дампы**: создание и проверка готовности.
- **MCP-сервер**: операции elemctl доступны как инструменты для ИИ-агентов,
  включая Claude Code и другие MCP-клиенты.
- **Плагины**: внешние пакеты подключаются через точки расширения
  `importlib.metadata`. Плагин может содержать адаптер отладки 1С:Элемента
  (`elemctl debug-adapter`) и дополнительные команды. Из объявления `Command`
  формируются подкоманда CLI и инструмент MCP. Команды для конкретного окружения
  можно разместить в отдельном пакете.
- **Обновление**: `elemctl self-update` обновляет пакет распаковкой колеса,
  в том числе при занятом `elemctl.exe`. В таком случае обновление через pipx
  или pip может повредить установку. Флаг `--stop-holders` завершает
  MCP-серверы, использующие пакет. Выполняемые команды других сессий продолжают работу.
- **В VS Code**: развертывание и отладка доступны через расширение
  [XBSL](https://github.com/keyfire/xbsl). Кнопка развертывания вызывает `elemctl deploy`.
  Данные сессии отладки запрашиваются командой `elemctl apps debug`.

### Проверка того, что сборка применилась

При ошибке применения проекта сервер 1С:Элемента откатывает приложение на
предыдущую сборку без сообщения об откате. После этого приложение может иметь
статус `Running`, поэтому одного статуса недостаточно для проверки развертывания.
Команда `elemctl deploy` проверяет:

1. Задачи приложения со статусом `Error` или `Failed`, начатые после запуска
   развертывания. Более ранние ошибки не учитываются.
2. Фактически примененную версию проекта в поле `source.project-version`.
   Она должна совпадать с загруженной сборкой.
3. Доступность uri приложения контрольным HTTP-запросом. Результат записывается
   в поле `uri-status` отчета и не влияет на успешность развертывания.
   Для закрытых приложений ответы 401 и 403 допустимы.

Код возврата `deploy` равен нулю только после подтверждения применения сборки.

## Установка

<!-- installation:start -->

```bash
pipx install elemctl            # или: pip install elemctl
pip install "elemctl[mcp]"      # с MCP-сервером
```

Нужен Python 3.10 или новее. У ядра и CLI нет внешних зависимостей: только
стандартная библиотека.

## Настройка

<!-- configuration:start -->

Параметры подключения elemctl читает из переменных окружения или файла `.env`
в текущем каталоге. Значение переменной окружения имеет приоритет над значением
из файла.

| Переменная | Назначение |
|---|---|
| `ELEMENT_BASE_URL` | базовый URL сервера с `http://` или `https://`, например `https://1cmycloud.com` |
| `ELEMENT_CLIENT_ID` | Client-Id для получения токена |
| `ELEMENT_CLIENT_SECRET` | Client-Secret |
| `ELEMENT_APP_ID` | приложение по умолчанию (необязательно) |
| `ELEMENT_PROJECT_ID` | проект по умолчанию (необязательно) |
| `ELEMENT_SPACE_ID` | пространство по умолчанию (необязательно) |
| `ELEMENT_CA_FILE` | дополнительный PEM-файл CA для частного облака (необязательно) |
| `ELEMENT_TLS_STRICT` | строгая проверка сертификатов по RFC 5280; по умолчанию `true` |
| `ELEMENT_TLS_VERIFY` | проверка сертификата и имени сервера; по умолчанию `true` |

Client-Id и Client-Secret выпускают в панели управления 1cmycloud, в разделе
интеграций Console API. Шаблон файла –
[.env.example](https://github.com/keyfire/elemctl/blob/main/.env.example).

### Настройка через `.env`

Для настройки подключения необходимо скопировать шаблон в каталог запуска `elemctl`:

```bash
cp .env.example .env
```

В файле необходимо указать адрес сервера, Client-Id и Client-Secret:

```dotenv
ELEMENT_BASE_URL=https://1cmycloud.com
ELEMENT_CLIENT_ID=client-id
ELEMENT_CLIENT_SECRET=client-secret
```

Без параметра `--env-file` инструмент ищет файл с точным именем `.env` в
**текущем каталоге запуска**. Это не обязательно каталог проекта и не каталог,
куда установлен `elemctl`. В репозитории `elemctl` файл `.env` исключен из Git.
При создании такого файла в другом репозитории необходимо добавить `.env`
в `.gitignore`, чтобы секрет не попал в коммиты и журналы.

Для файла конфигурации в другом каталоге необходимо указать путь. Для
MCP-сервера, фоновых запусков и CI рекомендуется использовать абсолютный путь:

```bash
elemctl --env-file /opt/elemctl/cloud.env apps list
```

Параметр можно ставить и после команды:

```bash
elemctl apps list --env-file /opt/elemctl/cloud.env
```

Относительный путь рассчитывается от текущего каталога. Для работы с разными
стендами можно использовать отдельные файлы, не изменяя переменные процесса:

```bash
elemctl --env-file ./env/public-cloud.env apps list
elemctl --env-file ./env/local-cloud.env apps list
```

Пример конфигурации локального облака с доверенным, но устаревшим внутренним CA,
который Python 3.13 отклоняет из-за строгой проверки RFC 5280:

```dotenv
ELEMENT_BASE_URL=https://cloud.internal.example
ELEMENT_CLIENT_ID=client-id
ELEMENT_CLIENT_SECRET=client-secret
ELEMENT_TLS_STRICT=false
```

Если внутренний CA уже доверен, но Python 3.13 отклоняет его с ошибкой
`Basic Constraints of CA cert not marked critical`, необходимо задать
`ELEMENT_TLS_STRICT=false`. Проверка цепочки, срока действия, подписи и имени
сервера сохраняется. Выключается только строгий профиль RFC 5280 в
OpenSSL. Если есть возможность, лучше исправить или перевыпустить сам CA.

Если частного CA нет в системном хранилище, необходимо указать
`ELEMENT_CA_FILE=/path/to/internal-ca.pem`. Значение
`ELEMENT_TLS_VERIFY=false` полностью отключает проверку сертификата и имени
сервера. Это крайняя мера и только для изолированной тестовой сети. При
отключенной проверке каждая команда печатает предупреждение в stderr, а в
stdout остается только ответ. Формат JSON для обработки по конвейеру сохраняется.
Допустимые логические значения: `true`/`false`, `yes`/`no`, `on`/`off`
и `1`/`0`.

`ELEMCTL_NO_PROXY` позволяет отправлять запросы без прокси окружения. Это
необходимо, если внутренний адрес недоступен через прокси или прокси заменяет
сертификат сервера. Проверка TLS остается включенной. Если прямое соединение
завершается ошибкой `CERTIFICATE_VERIFY_FAILED`, настроить доверенный CA
или параметры `ELEMENT_TLS_*`.

Переменную `ELEMCTL_NO_PROXY` можно задать в файле `.env` подключения. Если
одноименная переменная окружения задана, используется ее значение. Это позволяет
одному MCP-серверу обслуживать несколько стендов через `env_file`. Сервер
выполняет по одному вызову за раз, а настройка из файла применяется только к
запросам соответствующего стенда.

Изменения файла вступают в силу при следующем вызове без перезапуска сервера,
если обновилась метка времени изменения или изменился размер файла. Ключ кеша клиента включает
`env_file` и эти два атрибута. Если `env_file` не задан, используется `--env-file` сервера или `.env` из рабочего
каталога. Изменение прав доступа без изменения времени и размера файла не приводит
к обновлению кеша.

Это поведение относится к серверу `elemctl mcp`. Если приложение передает серверу
объект `Config` напрямую, без файла, конфигурация сохраняется на весь срок работы
процесса.

### Поведение инструмента

`ELEMCTL_LANG`, `ELEMCTL_NO_PLUGINS`, `ELEMCTL_DATA_DIR` и `ELEMCTL_REGISTRY_LIMIT`
задаются только переменными окружения. В файле `.env` подключения эти настройки
не читаются. Для `ELEMCTL_NO_PROXY` поддерживаются оба источника, как описано выше.

| Переменная | Назначение |
|---|---|
| `ELEMCTL_LANG` | язык сообщений и справки (`ru`, `en`); флаг `--lang` имеет приоритет |
| `ELEMCTL_NO_PROXY` | обходить прокси окружения во всех вызовах (петлевые и приватные адреса обходятся и так); также читается из `.env` стенда |
| `ELEMCTL_NO_PLUGINS` | не искать плагины: работать только со штатными возможностями ядра |
| `ELEMCTL_DATA_DIR` | каталог локального реестра загрузок; по умолчанию `%LOCALAPPDATA%\elemctl` в Windows и `$XDG_STATE_HOME/elemctl` (`~/.local/state/elemctl`) в остальных системах |
| `ELEMCTL_REGISTRY_LIMIT` | сколько загрузок хранит локальный реестр загрузок; по умолчанию 1000, `0` – хранить все |

### Локальный реестр загрузок

Сервер хранит коммит сборки, загруженной в существующий проект. Дополнительные
сведения о загрузке elemctl записывает в локальный файл `uploads.jsonl`.
Запись включает идентификатор сборки и проекта, версию, ветку, коммит, признак
незакоммиченных изменений, каталог исходников, стенд, команду и время загрузки.
Реестр заполняется при вызовах `deploy`, `builds upload` и `probe`.

Команды `builds list --brief` и `apps get` дополняют ветку и коммит из реестра,
если эти поля отсутствуют в карточке сборки на сервере. Для каждого значения указывается
источник. Сведения о сборках, загруженных с другой машины, из CI или версией
elemctl без реестра, в локальном файле отсутствуют.

Ошибка записи реестра приводит к предупреждению и не отменяет загрузку. Файл
можно удалить; при этом будет удалена только история загрузок этой машины.
По умолчанию реестр хранит 1000 последних загрузок. Параметр
`ELEMCTL_REGISTRY_LIMIT` задает другой предел; значение `0` отменяет ограничение.
Если число записей превышает предел на 10 %, следующая загрузка сокращает файл
до последних записей.

### Окружение CI

При сборке используются стандартные переменные CI. Если они заданы, версию
можно определить без отдельного флага и изменения исходников:

| Переменная | Назначение |
|---|---|
| `CI_PIPELINE_IID` | номер запуска; из него берется суффикс версии сборки, когда нет ни `--build-version`, ни предыдущей сборки |
| `GITHUB_RUN_NUMBER` | то же, второй по очереди |
| `BUILD_NUMBER` | то же, третий по очереди; берется первое числовое значение |
| `CI_COMMIT_BRANCH` | имя ветки для манифеста, когда git в отцепленном `HEAD` |
| `CI_COMMIT_REF_NAME` | то же, второй по очереди |
| `GITHUB_REF_NAME` | то же, третий по очереди; значение `HEAD` отбрасывается, и поле остается пустым |

## Быстрый старт

<!-- quickstart:start -->

```bash
# список приложений
elemctl apps list

# карточка приложения (статус, uri, фактическая версия проекта)
elemctl apps get <app-id>

# создать приложение, только если его ещё нет:
# {"id": ..., "created": true|false, "sign-in": ...} - последнее поле это способ войти
# --wait дожидается приложения И проверяет, на какой сборке оно правда работает
elemctl apps ensure acme-crm-dev --project-id <project-id> --latest-build --wait

# полный цикл деплоя из исходников с проверкой применения
elemctl deploy --app-id <app-id> --project-id <project-id> --project-dir acme/crm

# скомпилировать исходники на сервере, не трогая рабочее приложение:
# ok и ошибки с файлом, строкой и колонкой; за собой убирает
elemctl probe --project-dir acme/crm

# данные для сессии отладки: {"debug-token": ..., "debug-address": ...}
# (нужна включённая отладка на сервере: config/debug.yml enabled: true)
elemctl apps debug <app-id>

# только собрать архив .xasm, никуда не загружая
elemctl build --project-dir acme/crm --output ./dist

# разобрать готовый архив: манифест, подсистемы, глобальные типы с полными именами
elemctl inspect ./dist/e1c-CurrencyConverter-2.0.xlib

# запретить вход по паролю и саморегистрацию в списке пользователей приложения
elemctl user-lists password-login --app crm-dev --disable
elemctl user-lists self-registration --app crm-dev --disable

# принять изменения ветки среды разработки
elemctl branches merge <branch-id>
```

Все команды пишут JSON в stdout, а прогресс длительных операций – в stderr.
Ошибка возвращается JSON-объектом с полем `error` и кодом возврата 1.

Флаг `--json` гарантирует машиночитаемый вывод и может указываться в любой
позиции. Во время работы команды stdout подменяется на stderr. Поэтому в stdout
записывается только JSON ответа; вывод плагинов и библиотек туда не попадает.
Для чтения ответа следует обработать поток целиком с помощью `json.load`.
При ошибке с `--json` сообщение записывается в stderr, а stdout остается пустым.

Флаг `--quiet` отключает сообщения о ходе работы и предупреждения в stderr.
Расположение и формат ответа и сообщения об ошибке не изменяются. Флаг можно
указывать в любой позиции. При объединении потоков выводится только ответ.

`apps list` и `builds list` печатают счетчик и отметку об усечении после
ответа. У остальных строк в stderr порядок не гарантирован, так что разбирать
безопасно только сам stdout, отдельно от stderr.

Полный список команд дает `elemctl --help`, по группам – `elemctl apps --help`,
`elemctl deploy --help` и так далее.

## Язык

<!-- language:start -->

Сообщения об ошибках, прогресс и текст `--help` выходят на русском и английском.
JSON-результат от языка не зависит. Язык выбирается по очереди: `--lang ru|en`,
затем переменная `ELEMCTL_LANG`, затем системная локаль (`LC_ALL`, потом `LANG`),
затем русский. Флаг `--lang` читается до построения парсера, поэтому
`elemctl --lang en --help` печатает справку по-английски.

## MCP-сервер

<!-- mcp:start -->

MCP-сервер предоставляет инструменты для управления приложениями 1С:Элемента
через Console API. Для подключения используется транспорт stdio:

```bash
pip install "elemctl[mcp]"
claude mcp add elemctl -- elemctl mcp
```

Реквизиты подключения сервер берет из тех же переменных `ELEMENT_*` / `.env`.

### Инструменты

| Инструмент | Что делает |
|---|---|
| `list_apps` | Получение списка приложений с отбором по имени и статусу. |
| `find_app` | Найти приложение по точному имени. Результат содержит id и `found`; удаленные включаются при `include_deleted`. |
| `get_app` | Получить карточку: статус, uri и фактическую версию проекта. Поле `applied-build` содержит ветку и коммит из карточки сборки или локального реестра загрузок. |

| `debug_info` | Получить `debug-token` и `debug-address` для отладки. На сервере должна быть включена отладка. |
| `list_spaces` | Получить список пространств. |
| `list_projects` | Получение списка проектов с отбором по имени. |
| `list_builds` | Получение списка сборок проекта с ограничением количества. |

| `build_assembly` | Собрать архив `.xasm`/`.xlib` из исходников локально, без обращения к серверу 1С:Элемента. |

Параметры `list_apps`, `list_projects` и `list_builds` описаны ниже.

Плагины могут добавлять собственные инструменты. Их подключение описано в разделе
[Плагины](#плагины).

Для подключения к другому стенду инструменты, обращающиеся к серверу 1С:Элемента,
принимают необязательный параметр `env_file`. В нем указывается путь к файлу
`.env` этого стенда. Один сервер может работать с облаком и локальной установкой
без перезапуска.

По умолчанию `list_apps` возвращает краткие карточки с идентификатором, именем,
статусом, адресом и примененной версией. Для получения полных карточек следует
указать `brief=false`. При большом числе приложений полный ответ может содержать
десятки тысяч символов.

Параметр `name` отбирает приложения по подстроке имени без учета регистра. Отбор
выполняется на стороне клиента, поскольку Console API игнорирует параметр запроса.
Параметр `status` отбирает приложения по полному значению статуса. Удаленные
приложения включаются в ответ при `include_deleted`. В ответ входят карточки
`applications`, счетчики `total`, `live` и `shown`, а также строка `summary`,
например "живых 7 из 324".

По умолчанию `list_projects` возвращает краткие карточки: идентификатор, имя,
вид проекта, пространство, счетчик приложений и признак удаления. Для полных карточек укажите `brief=false`. Параметр `name` отбирает проекты по
подстроке имени. Удаленные проекты включаются в ответ при `include_deleted`.

По умолчанию `list_builds` возвращает десять последних сборок. Параметр `limit`
задает другое число, значение `0` снимает ограничение. Краткая карточка содержит
идентификатор, версии, дату, ветку и коммит. Для полных карточек укажите `brief=false`. Источник ветки и коммита, карточка сборки на сервере
или локальный реестр загрузок, также указывается. Ответ включает карточки `builds`,
счетчики `total` и `shown`, а также строку `summary`.

Перечень сборок на сервере не является полной историей проекта. Когда приложение
заканчивает применение сборки, сервер удаляет
неиспользуемые сборки независимо от их возраста.
Сохраняются сборки работающих приложений, сборка с наибольшим номером базовой
версии, релизная сборка и сборки, загруженные без идентификатора проекта. К
последним относится и первая сборка проекта. Разделения перечня на страницы нет.

Номера сборок одной базовой версии выдаются последовательно. Пропуск номера
может указывать на удаленную сборку или на скачок нумерации. Сборка, загруженная
без идентификатора проекта, сохраняет номер архива; последующая нумерация идет
от него. Если локальный реестр содержит такую загрузку над пропуском, `summary`
обозначает его как скачок. Если внутри пропуска есть загрузка этой машины в
проект, `summary` указывает и скачок, и удаление.

Сборки проектов расширений автоматически не удаляются. Их можно удалить вручную;
пропуск номера в таком проекте обозначается в `summary` как удаление.

`get_build` возвращает одну полную карточку. Метод Console API адресуется версией
сборки. Если передан ид, версия предварительно определяется по списку сборок.

`get_app`, `delete_app`, `start_app`, `stop_app` и `debug_info` принимают ид
приложения (UUID) или точное имя. Значение, не похожее на UUID, ищется в списке.
При нескольких совпадениях возвращается ошибка.

### Создание и проверка приложения

`create_app` и `ensure_app` возвращают поле `sign-in` с адресом приложения
и учетной записью для входа. Используется учетная запись панели управления;
учетные записи других приложений для нового приложения недоступны.

Параметр `verify` включает ожидание и проверку фактически примененной сборки.
При ошибке сервер может откатить приложение без сообщения об откате, поэтому
готовность приложения не подтверждает применение запрошенной сборки. Результат
проверки записывается в поле `verify`. Ожидание занимает несколько минут;
для такого вызова рекомендуется фоновый запуск `elemctl`. При прерывании ожидания
в ответе сохраняется ид созданного приложения, а причина указывается в `wait-error`.

Перед созданием `version_id` проверяется по списку сборок проекта `project_id`.
Если `project_id` не задан, используется `ELEMENT_PROJECT_ID` стенда. Если сборки
нет в этом проекте, выполняется поиск по остальным проектам стенда. Загрузка без ид проекта могла включить сборку
в другой проект. В таком случае проект из настроек
заменяется проектом сборки. При явно заданном несовпадающем `project_id` возвращается
ошибка с указанием проекта сборки.

Если сборки нет ни в одном проекте, создание не выполняется. Сервер удаляет сборки,
которыми никто не пользуется, и создание из удаленной сборки завершается HTTP 400.
Сообщение elemctl содержит эту причину и сборку работающего приложения проекта.

### Развертывание и временные приложения

У `deploy` параметр `allow_data_loss` разрешает изменения, отклоняемые проверкой
схемы: сужение, смену типа и полное удаление справочника. В CLI ему соответствует
`--allow-data-loss`. Если сервер еще запускается, ожидание ограничено
`server_start_timeout` секундами, по умолчанию 900. Необязательные
`expected_app_name` и `expected_app_uri` проверяют цель до сборки.

С параметром `keep` инструмент `probe` сохраняет созданные объекты и включает в отчет команды очистки. Если идентификатор приложения неизвестен, `cleanup.command` равно `null`; доступны ручные шаги для известных объектов. `probe_cleanup` удаляет также объекты, оставшиеся
после прерванной очистки. Принадлежность временного приложения определяется по префиксу имени, токену версии или локальному реестру загрузок. Реестр позволяет распознать проверку с собственными именем и версией.
Реестр также содержит сборки, примененные к этому приложению. Сборки удаляются в собственном проекте проверки. Если есть записи реестра, сборки, используемые другими приложениями, сохраняются. Без записей реестра такой проверки нет: распознавание по имени или токену само по себе не гарантирует сохранение используемой сборки. Проект удаляется только при отсутствии сборок и работающих приложений; проект из `ELEMENT_PROJECT_ID` сохраняется.
Приложение, не принадлежащее проверке, отклоняется. При списке `app_id` ошибки
отдельных приложений не останавливают обработку остальных.

### Доступ и экспорт

Без доступа по токену запрос к HTTP-сервису завершается 500 "Token access is denied".
Инструмент `token_access` после изменения повторно читает признак. Пустой `user`
означает учетную запись подключения elemctl. При списке пользователей каждому
соответствует отдельный результат; ошибка одного не останавливает остальных.

У `export_app` и `export_extension` пустой `output` означает текущий каталог
MCP-сервера и имя `{Имя} {Версия}.xasm`. Если метод не поддерживается сервером,
возвращается сообщение об этом ограничении. Если `extension` не соответствует
ни одному расширению, в ошибке перечисляются расширения приложения.

## Плагины

<!-- plugins:start -->

Для подключения внешних пакетов elemctl использует точки расширения
`importlib.metadata`. Плагины обнаруживаются при обращении; объявлять их в
`pyproject.toml` ядра не требуется. Закрытые компоненты можно разместить в
отдельном пакете.

**`elemctl.debug_adapter`**: пакет-плагин объявляет каталог адаптера отладки
1С:Элемента. Это проприетарные jar 1С, в состав elemctl они не входят. Значением
точки расширения бывает путь либо функция без аргументов, возвращающая путь. Путь
указывает на каталог с подкаталогом `repo/`, содержащим jar-файлы адаптера.

**`elemctl.commands`**: пакет-плагин добавляет собственные команды. Значением
точки расширения может быть `Command`, список команд или функция без аргументов,
возвращающая одно из этих значений. По объявлению формируются подкоманда CLI и
инструмент MCP со схемой аргументов. Команды для внутренних систем и стендов
могут находиться в отдельном пакете.

```toml
# pyproject.toml пакета-плагина
[project.entry-points."elemctl.debug_adapter"]
имя = "мой_пакет:adapter_root"     # () -> Path на каталог, содержащий repo/

[project.entry-points."elemctl.commands"]
имя = "мой_пакет.commands:commands"   # () -> list[Command]
```

```python
# мой_пакет/commands.py
from elemctl.plugins import Argument, Command

def warm_up(context, stand="", force=False):
    context.log(f"прогреваем {stand}")          # прогресс: stderr в CLI, поле log в MCP
    # context.surface называет, кто позвал: "cli" или "mcp"
    card = context.client.get_app(stand)        # клиент строится при первом обращении
    return {"ok": True, "status": card.get("status")}

def commands():
    return [Command(
        name="warm-up",
        help="открыть админку свежего стенда",
        handler=warm_up,
        arguments=[Argument("--stand", help="приложение"), Argument("--force", type=bool)],
    )]
```

### Результат команды плагина

Результат обработчика должен сериализоваться в JSON. В CLI он выводится в stdout,
в MCP возвращается вызывающей стороне. Поле `exit-code` задает код возврата CLI,
если содержит целое число от 0 до 255. Например, для трех исходов можно вернуть
0 (различий нет), 1 (есть различия) и 2 (ошибка шага).

Корректное `exit-code` имеет приоритет над `ok`. Если поле отсутствует или содержит
некорректное значение, например строку, `true` или 300, используется `ok`:
словарь с `"ok": false` завершается кодом 1, как отчеты `deploy` и `probe`.
В MCP поле `exit-code` возвращается вместе с результатом.

Для установки кода возврата не следует вызывать `sys.exit` в обработчике.
Тот же обработчик выполняется внутри MCP-сервера: вызов `sys.exit` остановит сервер,
не вернув ответ на запрос.

Поле `context.surface` содержит источник вызова: `"cli"` или `"mcp"`. Его можно
использовать для разного объема вывода в терминале и инструменте MCP. Для
совместимости с ядром без этого поля читать `getattr(context, "surface", None)`.

### Параметры команды плагина

Поддерживаются типы `str`, `int`, `float` и `bool` для флага. Параметр `env_file`
добавляется к инструменту MCP автоматически, поэтому команда плагина может
обращаться к другим стендам так же, как инструменты ядра.

Для позиционного аргумента можно задать синоним CLI:
`Argument("page", cli_alias="--page")`. Тогда допустимы
`elemctl wiki-get 123` и `elemctl wiki-get --page 123`. В схеме MCP остается
один параметр `page`; `cli_alias` изменяет только разбор командной строки.
Одновременное использование обеих форм отклоняется. Для обязательного аргумента
отсутствие обеих форм также считается ошибкой. Без `cli_alias` используется
обычный позиционный аргумент.

Параметр `Argument("--file", multiple=True)` принимает несколько значений:
`elemctl wiki-attach --file a.png --file b.png`. В обработчик передается
`["a.png", "b.png"]` в порядке командной строки. Если ключ не указан, передается
значение по умолчанию в виде списка или `[]`. В MCP используется массив
объявленного типа. Без `multiple` повтор одного ключа с разными значениями
отклоняется. Флаг типа `bool` не может быть повторяемым. Значение по умолчанию
для повторяемого аргумента должно быть списком, кортежем или `None`.

Позиционный аргумент также поддерживает несколько значений:
`Argument("page", multiple=True, cli_alias="--page")` принимает
`elemctl wiki-get 123 456` или `elemctl wiki-get --page 123 --page 456`.
Обработчик в обоих случаях получает `["123", "456"]`. Формы нельзя смешивать.
С `required=True` необходимо хотя бы одно значение. Необязательный аргумент
без значений передает значение по умолчанию списком или `[]`. В MCP остается
один параметр-массив.

### Совместимость плагинов

Команда с именем команды ядра не подключается. Плагин с ошибкой загрузки,
в том числе рассчитанный на более новое ядро, также пропускается. Сведения
о таких плагинах выводятся в stderr и в `elemctl plugins`; остальные продолжают работать.

Для поддержки ядра без повторяемых параметров предварительно проверять
`hasattr(Argument, "multiple")`. Без поля `multiple` весь плагин с таким объявлением
не загрузится. В некоторых версиях ядра поле уже есть, но разрешено только для
опций: повторяемый позиционный аргумент вызывает `PluginError` и исключает плагин.
Для проверки этой возможности использовать признак из `elemctl.plugins`:
`getattr(plugins, "POSITIONAL_MULTIPLE", False)`.

```bash
# путь к адаптеру от установленного плагина (для расширения VS Code):
# {"path": "...", "found": true} либо {"path": null, "found": false}
elemctl debug-adapter

# что приносят плагины - каталоги адаптера и команды
elemctl plugins
```

Для извлечения проприетарных jar-файлов адаптера 1С из дистрибутива 1С:Элемента
используется скрипт `tools/extract_adapter.py`. Полученный каталог можно указать
в `xbsl.debug.adapterPath` или использовать для сборки пакета-плагина. Скрипт
не входит в дистрибутив пакета.

Обнаружение плагинов отключает переменная `ELEMCTL_NO_PLUGINS=1`: тогда работают
только штатные возможности ядра.

## Использование как библиотеки

<!-- library:start -->

```python
from elemctl import Config, ElementClient
from elemctl.deploy import deploy_from_sources

client = ElementClient(Config.from_env())
apps = client.list_apps()

report = deploy_from_sources(
    client,
    app_id="...",
    project_id="...",
    project_dir="acme/crm",
    log=print,
)
assert report.ok, report.problems
```

`list_apps()` возвращает приложения, не помеченные как удаленные. Удаленные
приложения остаются в списке сервера со статусом `Deleted`; на длительно
используемом стенде таких записей может быть несколько сотен. Для полного списка
указать `include_deleted=True`. Метод `list_apps_counted()` возвращает тот же
список в поле `items` и счетчики `total`, `live` и `shown`, используемые CLI
и инструментом MCP.

Проверить компиляцию, не трогая рабочее приложение, можно тем же циклом, что
выполняет команда `probe`:

```python
from elemctl.probe import probe_project

report = probe_project(client, project_dir="acme/crm", log=print)
for error in report.errors:
    print(f"{error['file']}:{error['line']}:{error['column']} {error['message']}")
assert report.ok, report.messages
```

## Формат сборки

<!-- buildformat:start -->

`.xasm` для приложения и `.xlib` для библиотеки – это ZIP-архив:

```
Assembly.yaml            # манифест: ProjectKind, Vendor, Name, Version, ...
{vendor}/{name}/...      # файлы проекта: .yaml, .xbsl, ресурсы
```

Каталог проекта должен лежать по схеме `{repo}/{vendor}/{name}/Проект.yaml`,
потому что пути в архиве строятся от корня репозитория. Приложение это или
библиотека, определяется по полю `ВидПроекта` в `Проект.yaml`. Если приложение ссылается
на библиотеки, исходные проекты которых лежат под тем же корнем репозитория, их
файлы включаются в архив приложения вместе с транзитивными локальными
зависимостями. Библиотека, исходники которой отсутствуют локально, остается
внешней зависимостью приложения 1С:Элемента.

## Ограничения и статус

<!-- limitations:start -->

- Инструмент **неофициальный** и не связан с фирмой "1С". Console API может
  изменяться без предупреждения.
- elemctl использует документированный Console API v2. Внутренние API консоли
  управления не используются и не описываются.
- При некоторых настройках сервера приложение, созданное только по
  `--project-id`, не содержит данных проекта. Для создания из конкретной сборки
  выполнить `elemctl apps create <имя> --project-id <id>
  --latest-build`. MCP-инструмент `create_app` автоматически выбирает последнюю
  сборку. После создания выполнить `elemctl deploy`.
- Если при создании приложение получает статус `Error`, сервер возвращает
  общий текст "Неизвестная ошибка. Обратитесь к администратору". Файлы, строки
  и колонки ошибок компиляции содержатся в задаче приложения. Команды
  `apps create --wait` и `apps ensure` выводят эти сведения после общего
  сообщения, как и `deploy` и `verify`. При откате применения приложение
  может получить статус `Running`. Поэтому `--wait` дополнительно проверяет
  примененную сборку. Если она отличается от запрошенной, код возврата равен 1.
  Флаг `--no-verify` отключает эту проверку и оставляет только ожидание.
- Компиляция выполняется на сервере при применении сборки. Для проверки
  необходимо создать приложение. Команда `probe` создает временное приложение,
  не изменяя рабочее. Проверка занимает несколько минут, сопоставимо с созданием
  приложения. Ее следует выполнять перед развертыванием или в CI.
- Проект 1С:Элемента определяется по `Ид` из `Проект.yaml`. Сборка, загруженная
  без ид проекта, включается в проект с этим `Ид` независимо от пары
  `Vendor` + `Name` в манифесте. При этом имя проекта изменяется по данным сборки.
  Команда `builds upload` возвращает выбранный проект и предупреждает
  о переименовании. Если новому `Ид` соответствует пара, уже занятая другим
  проектом, сервер возвращает 409.
- Для входа в новое приложение используется учетная запись панели управления.
  У приложения собственный пустой список пользователей, вход по паролю выключен,
  сервис учетных записей не подключен. Учетные записи других приложений
  недоступны даже после подключения их списка пользователей и включения
  локального входа. Способ входа содержится в поле `sign-in` ответа команд
  `apps create` и `apps ensure` и в их сообщении в stderr.
- Удаленные приложения остаются в списке сервера со статусом `Deleted` и прежним
  `id`. Обращения `apps get` и `deploy` по этому идентификатору возвращают 404.
  Команды `apps find` и `apps ensure` пропускают такие приложения. Для поиска
  среди удаленных приложений используется `apps find --include-deleted`.
- При неопубликованных изменениях в среде разработки удаление приложения через
  API завершается HTTP 400 `FAILED_PRECONDITION`. Принудительного удаления
  в Console API нет. Для удаления используется панель управления; это условие
  также указывается в сообщении elemctl об ошибке.

- Если приложение пересоздать, то есть удалить и создать заново, у него
  изменится URL. Внешние настройки, использующие этот адрес, например OIDC redirect,
  придется обновить. "Мягкой" очистки данных приложения в Console API нет, ее
  делают в консоли управления.
