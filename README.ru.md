# Elemctl

[English](https://github.com/keyfire/elemctl/blob/main/README.md) · **Русский**

**Документация: [docs.keyfire.ru/elemctl](https://docs.keyfire.ru/elemctl/ru/)**

Утилита командной строки, MCP-сервер и Python-библиотека для управления
приложениями облачной платформы **1С:Предприятие.Элемент** (1cmycloud.com)
через Console API v2.

elemctl ведёт приложение на платформе весь его срок жизни, и веб-консоль
для этого не нужна. Он создаёт приложение, собирает архив `.xasm`/`.xlib`
из исходников проекта, загружает сборку и применяет её к приложению. Дальше
он проверяет, что применение и правда случилось: платформа умеет молча
откатить. Компиляцию проверяет пробник, который рабочее приложение не
трогает. Отдельные команды ведут ветки среды разработки, дампы и версию
технологии.

Движок один, а обратиться к нему можно тремя способами: командой `elemctl`
из терминала и CI, MCP-сервером для AI-агентов (Claude Code и другие
MCP-клиенты), python-модулем `elemctl` из своих скриптов.

*elemctl is a CLI tool, MCP server and Python library for the
1C:Enterprise.Element (1cmycloud) Console API: manage applications, upload
builds, deploy with a verified apply and check compilation with a probe.
The documentation comes in both languages, and the CLI output is plain JSON.*

Заметки о разработке и новости – в Telegram-канале [1С × ИИ: инженерный цех](https://t.me/ceh_1c_ai).

## Возможности

<!-- features:start -->

- **Приложения**: список, карточка, создание, запуск, остановка, удаление,
  версия технологии, данные для сессии отладки (`apps debug`). Список умеет
  фильтровать по имени на стороне клиента и показывать краткие карточки по
  `--brief`. Команды, адресующие одно приложение, принимают его ид либо
  точное имя.
- **Проекты и сборки**: загрузка `.xasm`/`.xlib`, список сборок, удаление.
- **Сборка из исходников**: elemctl упаковывает каталог проекта в архив
  сборки с манифестом и git-метаданными. В каталоге лежат `Проект.yaml` и
  модули. Версию он берёт из флага, из счётчика последней сборки или из
  номера запуска CI в окружении: `CI_PIPELINE_IID`, `GITHUB_RUN_NUMBER`,
  `BUILD_NUMBER`. Её же возвращает поле вывода. Дескриптор с английскими
  написаниями ключей `Name`/`Vendor`/`Version` читается наравне с русским.
- **Развёртывание одной командой**: сборка -> загрузка -> применение ->
  перезапуск -> **проверка фактического применения**. Незакоммиченные
  изменения каталога проекта видны в отчёте полем `dirty`. Ключ
  `--require-clean` останавливает работу, когда дерево грязное.
- **Проверка компиляции без риска для приложения** (`elemctl probe`):
  исходники компилирует сервер, и делает он это в одноразовом приложении.
  Ошибки приходят с файлом, строкой и колонкой. Созданное пробник убирает
  за собой. До рабочего приложения он не дотягивается
  намеренно: `ELEMENT_APP_ID` и `ELEMENT_PROJECT_ID` он не читает.
- **Списки пользователей** (`elemctl user-lists`): настройки входа, за
  которыми обычно ходят в панель управления. Это самостоятельная
  регистрация и вход по логину с паролем. Список адресуют ид,
  представлением либо приложением, которому он принадлежит.
- **Ветки среды разработки**: список, создание, привязка к приложению, слияние.
- **Дампы**: создание и контроль готовности.
- **MCP-сервер**: те же операции в виде инструментов для AI-агентов –
  Claude Code и других MCP-клиентов.
- **Плагины**: точки расширения `importlib.metadata`. Внешний пакет приносит
  debug-адаптер платформы (`elemctl debug-adapter`) и свои команды, и ядро от
  этого не раздувается. Одно объявление `Command` становится сразу и
  подкомандой CLI, и инструментом MCP. Команда, которая знает про ваше
  окружение, живёт в вашем пакете, а не в публичном ядре.
- **Обновление**: `elemctl self-update` обновляет пакет распаковкой колеса.
  Это работает и тогда, когда `elemctl.exe` занят работающим MCP-сервером:
  штатные pipx и pip в таком случае ломают установку.
- **В VS Code**: развёртывание и отладка живут в расширении
  [XBSL](https://github.com/keyfire/xbsl). Оно зовёт elemctl: `elemctl deploy`
  по кнопке развёртывания, `elemctl apps debug` за координатами сессии отладки.

### Проверка того, что сборка применилась

Особенность платформы: когда применение проекта падает, платформа **молча
откатывает** приложение на предыдущую сборку. Статус `Running` об успехе при
этом ничего не говорит. Поэтому `elemctl deploy` статусу не верит и после
работы проверяет три вещи:

1. Задачи приложения со статусом `Error` или `Failed`, начатые после того,
   как команда взялась за работу. Старые ошибки из истории она пропускает.
2. Фактическую версию проекта приложения, поле `source.project-version`. Она
   должна совпасть с только что загруженной сборкой.
3. Доступность uri приложения контрольным HTTP-запросом. Результат идёт в
   поле `uri-status` отчёта и ни на что не влияет: у закрытых приложений 401
   и 403 нормальны.

Код возврата `deploy` равен нулю только тогда, когда сборка действительно
применилась.

## Установка

<!-- installation:start -->

```bash
pipx install elemctl            # или: pip install elemctl
pip install "elemctl[mcp]"      # с MCP-сервером
```

Нужен Python 3.10 или новее. У ядра и CLI нет внешних зависимостей: только
стандартная библиотека.

## Настройка

<!-- configuration:start -->

Реквизиты подключения elemctl берёт из переменных окружения либо из файла
`.env` в текущем каталоге. Переменная окружения сильнее файла.

| Переменная | Назначение |
|---|---|
| `ELEMENT_BASE_URL` | базовый URL платформы, например `https://1cmycloud.com` |
| `ELEMENT_CLIENT_ID` | Client-Id для получения токена |
| `ELEMENT_CLIENT_SECRET` | Client-Secret |
| `ELEMENT_APP_ID` | приложение по умолчанию (необязательно) |
| `ELEMENT_PROJECT_ID` | проект по умолчанию (необязательно) |
| `ELEMENT_SPACE_ID` | пространство по умолчанию (необязательно) |
| `ELEMENT_CA_FILE` | дополнительный PEM-файл CA для частного облака (необязательно) |
| `ELEMENT_TLS_STRICT` | строгая проверка сертификатов по RFC 5280; по умолчанию `true` |
| `ELEMENT_TLS_VERIFY` | проверка сертификата и имени сервера; по умолчанию `true` |

Client-Id и Client-Secret выпускают в панели управления 1cmycloud, в разделе
интеграций Console API. Шаблон файла –
[.env.example](https://github.com/keyfire/elemctl/blob/main/.env.example).

### Настройка через `.env`

Скопируйте шаблон в каталог, из которого будете запускать `elemctl`:

```bash
cp .env.example .env
```

Затем заполните как минимум адрес платформы, Client-Id и Client-Secret:

```dotenv
ELEMENT_BASE_URL=https://1cmycloud.com
ELEMENT_CLIENT_ID=client-id
ELEMENT_CLIENT_SECRET=client-secret
```

Без параметра `--env-file` инструмент ищет файл с точным именем `.env` в
**текущем каталоге запуска**. Это не обязательно каталог проекта и не каталог,
куда установлен `elemctl`. В репозитории `elemctl` файл `.env` исключён из Git.
Если вы заводите такой файл в другом репозитории, добавьте `.env` в его
`.gitignore`: файл хранит секрет, и ему нечего делать ни в коммитах, ни в
журналах работы.

Если конфигурация лежит в другом месте, укажите её явно. Абсолютный путь надёжнее
для MCP-сервера, фоновых запусков и CI:

```bash
elemctl --env-file /opt/elemctl/cloud.env apps list
```

Параметр можно ставить и после команды:

```bash
elemctl apps list --env-file /opt/elemctl/cloud.env
```

Относительный путь считается от текущего каталога. Несколько файлов дают работу
с разными стендами, и переменные процесса при этом менять не нужно:

```bash
elemctl --env-file ./env/public-cloud.env apps list
elemctl --env-file ./env/local-cloud.env apps list
```

Пример конфигурации локального облака с доверенным, но устаревшим внутренним CA,
который Python 3.13 отклоняет из-за строгой проверки RFC 5280:

```dotenv
ELEMENT_BASE_URL=https://cloud.internal.example
ELEMENT_CLIENT_ID=client-id
ELEMENT_CLIENT_SECRET=client-secret
ELEMENT_TLS_STRICT=false
```

Если внутренний CA уже доверен, но Python 3.13 отклоняет его с ошибкой
`Basic Constraints of CA cert not marked critical`, задайте
`ELEMENT_TLS_STRICT=false`. Проверка цепочки, срока действия, подписи и имени
сервера остаётся на месте. Выключается только строгий профиль RFC 5280 в
OpenSSL. Если есть возможность, лучше исправить или перевыпустить сам CA.

Если частного CA нет в системном хранилище, укажите
`ELEMENT_CA_FILE=/path/to/internal-ca.pem`. Значение
`ELEMENT_TLS_VERIFY=false` полностью отключает проверку сертификата и имени
сервера. Это крайняя мера и только для изолированной тестовой сети. При
отключённой проверке каждая команда печатает предупреждение в stderr, а в
stdout остаётся один ответ, так что вывод JSON по конвейеру оно не портит.
Логические значения принимаются такие: `true`/`false`, `yes`/`no`, `on`/`off`
и `1`/`0`.

`ELEMCTL_NO_PROXY` решает другую задачу: направляет запрос мимо прокси окружения.
Он помогает, когда прокси не видит внутренний адрес или подменяет сертификат.
TLS-проверку сервера он не отменяет. Если прямое соединение дошло до сервера и
кончилось ошибкой `CERTIFICATE_VERIFY_FAILED`, настройте доверенный CA или
параметры `ELEMENT_TLS_*`.

В отличие от остальных переменных поведения инструмента ниже, `ELEMCTL_NO_PROXY`
можно задать и в `.env` самого стенда, рядом с реквизитами – переменная
окружения по-прежнему сильнее, если она задана. Это нужно для MCP: один
серверный процесс обслуживает несколько стендов через `env_file`, по одному
вызову за раз, а задать переменную окружения только для одного из них нечем.
Значение из файла действует лишь на запросы этого стенда – второй стенд,
обслуживаемый тем же процессом, облачный он или локальный, оно не затрагивает.
Уже запущенный сервер правку подхватит и без перезапуска, включая стенд по
умолчанию: кеш клиента учитывает не только `env_file` (а без него – свой
`--env-file` сервера, если он был задан при старте, а иначе `.env` рабочего
каталога), но и время изменения и размер файла, так что правка – скажем, эта
самая переменная – войдёт в силу на следующем же вызове к этому стенду.
Изменение, не тронувшее байты, правкой тут не считается: снимите с файла
право на чтение – кеш оставит уже собранного клиента, потому что ни время
изменения, ни размер не сдвинулись. Это про собственный `elemctl mcp`; объект `Config`, переданный серверу
напрямую приложением, которое встраивает elemctl, файла за собой не имеет и
вместо этого остаётся закреплён на весь процесс.

### Поведение инструмента

`ELEMCTL_LANG` и `ELEMCTL_NO_PLUGINS` задаются только окружением – в `.env`
подключения им не место. `ELEMCTL_NO_PROXY` – исключение, о котором сказано
выше: он читает тот же файл, что и подключение.

| Переменная | Назначение |
|---|---|
| `ELEMCTL_LANG` | язык сообщений и справки (`ru`, `en`); флаг `--lang` сильнее |
| `ELEMCTL_NO_PROXY` | обходить прокси окружения во всех вызовах (петлевые и приватные адреса обходятся и так); также читается из `.env` стенда |
| `ELEMCTL_NO_PLUGINS` | не искать плагины: работать только со штатными возможностями ядра |

### Окружение CI

Своих переменных сборка не заводит, зато читает те, что CI выставляет сам.
Поэтому в конвейере не нужны ни флаг версии, ни правка исходников:

| Переменная | Назначение |
|---|---|
| `CI_PIPELINE_IID` | номер запуска; из него берётся суффикс версии сборки, когда нет ни `--build-version`, ни предыдущей сборки |
| `GITHUB_RUN_NUMBER` | то же, второй по очереди |
| `BUILD_NUMBER` | то же, третий по очереди; берётся первое числовое значение |
| `CI_COMMIT_BRANCH` | имя ветки для манифеста, когда git в отцепленном `HEAD` |
| `CI_COMMIT_REF_NAME` | то же, второй по очереди |
| `GITHUB_REF_NAME` | то же, третий по очереди; значение `HEAD` отбрасывается, и поле остаётся пустым |

## Быстрый старт

<!-- quickstart:start -->

```bash
# список приложений
elemctl apps list

# карточка приложения (статус, uri, фактическая версия проекта)
elemctl apps get <app-id>

# создать приложение, только если его ещё нет:
# {"id": ..., "created": true|false, "sign-in": ...} - последнее поле это способ войти
# --wait дожидается приложения И проверяет, на какой сборке оно правда работает
elemctl apps ensure acme-crm-dev --project-id <project-id> --latest-build --wait

# полный цикл деплоя из исходников с проверкой применения
elemctl deploy --app-id <app-id> --project-id <project-id> --project-dir acme/crm

# скомпилировать исходники на сервере, не трогая рабочее приложение:
# ok и ошибки с файлом, строкой и колонкой; за собой убирает
elemctl probe --project-dir acme/crm

# данные для сессии отладки: {"debug-token": ..., "debug-address": ...}
# (нужна включённая отладка на сервере: config/debug.yml enabled: true)
elemctl apps debug <app-id>

# только собрать архив .xasm, никуда не загружая
elemctl build --project-dir acme/crm --output ./dist

# разобрать готовый архив: манифест, подсистемы, глобальные типы с полными именами
elemctl inspect ./dist/e1c-CurrencyConverter-2.0.xlib

# запретить вход по паролю и саморегистрацию в списке пользователей приложения
elemctl user-lists password-login --app crm-dev --disable
elemctl user-lists self-registration --app crm-dev --disable

# принять изменения ветки среды разработки
elemctl branches merge <branch-id>
```

Все команды пишут JSON в stdout, а прогресс длительных операций – в stderr.
Ошибка возвращается JSON-объектом с полем `error` и кодом возврата 1.

Флаг `--json` делает это соглашение гарантией для скриптов, и ставить его
можно в любой позиции. На время работы команды stdout подменяется на stderr,
поэтому в настоящий stdout уходит только JSON ответа. Посторонняя строка туда
не попадёт ни из плагина, ни из библиотеки. Читайте поток целиком через
`json.load`, а не ищите в нём первую скобку. Отказ с `--json` тоже уходит в
stderr, и stdout остаётся пустым: текст в машинном канале конвейер принял бы
за ответ.

`apps list` и `builds list` печатают счётчик и отметку об усечении после
ответа. У остальных строк в stderr порядок не гарантирован, так что разбирать
безопасно только сам stdout, отдельно от stderr.

Полный список команд даёт `elemctl --help`, по группам – `elemctl apps --help`,
`elemctl deploy --help` и так далее.

## Язык

<!-- language:start -->

Сообщения об ошибках, прогресс и текст `--help` выходят на русском и английском.
JSON-результат от языка не зависит. Язык выбирается по очереди: `--lang ru|en`,
затем переменная `ELEMCTL_LANG`, затем системная локаль (`LC_ALL`, потом `LANG`),
затем русский. Флаг `--lang` читается до построения парсера, поэтому
`elemctl --lang en --help` печатает справку по-английски.

<!-- language:end -->

## MCP-сервер

<!-- mcp:start -->

Сервер отдаёт операции платформы как MCP-инструменты (транспорт stdio):

```bash
pip install "elemctl[mcp]"
claude mcp add elemctl -- elemctl mcp
```

Реквизиты подключения сервер берёт из тех же переменных `ELEMENT_*` / `.env`.

### Инструменты

| Инструмент | Что делает |
|---|---|
| `list_apps` | список приложений; удалённые скрыты, пока их не попросят (`include_deleted`), `name` фильтрует по подстроке имени на клиенте, `status` – по статусу целиком; в ответе счётчики и строка `summary` рядом с `applications`, `brief` (по умолчанию) оставляет от карточки id, имя, статус, uri и применённую версию |
| `find_app` | найти приложение по точному имени: id и признак `found`; удалённые пропускаются, если не задан `include_deleted` |
| `get_app` | карточка приложения: статус, uri, фактическая версия проекта |
| `create_app` | создать приложение; по одному `project_id` источником берётся последняя сборка проекта. В ответе `sign-in` – способ войти; `verify` дожидается приложения и проверяет, на какой сборке оно правда работает |
| `ensure_app` | создать приложение по имени, только если его ещё нет; существующее не пересоздаётся (`created: false`); `verify` проверяет, на какой сборке приложение правда работает |
| `start_app` | запустить приложение |
| `stop_app` | остановить приложение |
| `delete_app` | удалить приложение. Отменить это нельзя: данные теряются, а пересозданное получит другой URL |
| `list_app_tasks` | задачи приложений; `app_id` – необязательный фильтр |
| `debug_info` | данные сессии отладки: `debug-token` и `debug-address` (нужна включённая отладка на сервере) |
| `list_spaces` | список пространств |
| `list_projects` | список проектов; `name` фильтрует по подстроке имени на клиенте, удалённые скрыты, пока не задан `include_deleted`; `brief` (по умолчанию) – id, имя, вид проекта, пространство, счётчик приложений, признак удаления |
| `list_builds` | сборки проекта, свежие первыми; ответ – объект `{total, shown, summary, builds}`; `limit` (по умолчанию 10, 0 – все), `brief` (по умолчанию) оставляет ид, версии, дату, ветку и коммит |
| `get_build` | карточка одной сборки целиком; `version` – это версия сборки (`1.0-42`), ид тоже принимается и разрешается по перечню |
| `build_assembly` | локально собрать архив `.xasm`/`.xlib` из исходников (к платформе не обращается) |
| `inspect_assembly` | разобрать готовый архив: манифест, свойства проекта, подсистемы и глобальные типы с полными именами (локально) |
| `deploy` | полный цикл из исходников с проверкой того, что сборка применилась; итог – поле `ok`, детали – `problems` и `log` |
| `probe` | проверить компиляцию серверным компилятором, не трогая рабочее приложение; ошибки с файлом, строкой и колонкой, за собой убирает |
| `apply_build` | применить загруженную сборку к приложению по её ид |
| `verify_deploy` | проверить фактическое применение: задачи с ошибками, сверка применённой сборки, доступность uri |
| `list_user_lists` | списки пользователей; `name` фильтрует по подстроке представления |
| `configure_user_list` | самостоятельная регистрация и вход по паролю; без флагов только показывает состояние |
| `list_branches` | список веток среды разработки; фильтры `project_id` и `name` необязательны |
| `merge_branch` | принять изменения ветки среды разработки |
| `debug_adapter` | путь к debug-адаптеру платформы из плагина; отсутствие плагина – это ответ (`found: false`), а не ошибка (локально) |

Рядом с ними встают инструменты, которые приносят плагины, о них ниже.

Одним окружением дело не ограничено. У каждого инструмента, который обращается
к платформе, есть необязательный `env_file` – путь к `.env` другого стенда. Так
один сервер работает и с облаком, и с локальной установкой, а перезапускать его
с другими реквизитами не нужно.

`list_apps` по умолчанию отдаёт краткие карточки: id, имя, статус, uri и
применённую версию. Полные карточки пространства – это десятки тысяч символов в
ответе агенту, за ними ходят с `brief=false`. Параметр `name` фильтрует по
подстроке имени без учёта регистра и делает это на клиенте, потому что платформа
query-параметр игнорирует. Параметр `status` фильтрует по статусу целиком.
Удалённые приложения скрыты, пока их не попросят через `include_deleted`: на
стенде, живущем не первый месяц, в перечне сотни карточек, из которых живых
единицы. Молча ответ не режется. В нём лежат счётчики `total` (сколько карточек
отдала платформа), `live` (сколько из них не удалено) и `shown`, готовая строка
`summary` вида "живых 7 из 324", а сами карточки – в `applications`.

`list_projects` ведёт себя так же и отдаёт id, имя, вид проекта, пространство,
счётчик приложений и признак удаления. `name` у него тоже фильтрует по подстроке,
а проекты с признаком удаления скрыты, пока не задан `include_deleted`: на стенде,
живущем не первый месяц, их в перечне сотни против единиц живых.

`list_builds` тоже отвечает краткими карточками – ид, версии, дата, ветка,
коммит – и десятью свежими сборками, пока `limit` не скажет иного; значение 0
снимает срез. Карточки лежат в `builds`, рядом с ними счётчики `total` (сколько
сборок отдала платформа) и `shown`, а также строка `summary`. Перечень платформы –
не вся история проекта: платформа сама удаляет сборки, которыми
никто не пользуется, и возраст тут ни при чём. Сборка работающего приложения, первая
сборка проекта и релизная остаются. Страниц у перечня нет, и `summary` прямо
говорит, что перед читателем остаток истории. Считает эта строка по фактам
ответа: номера сборок одной базовой версии платформа выдаёт подряд, поэтому
номер, которого в перечне нет, – это сборка, уже снятая уборкой.

`get_build` отдаёт одну карточку целиком и адресуется версией сборки. Ид тоже
принимается и находится по перечню, потому что адресом метод считает версию, а не
ид карточки.

`get_app`, `delete_app`, `start_app`, `stop_app` и `debug_info` принимают ид
приложения (UUID) либо его точное имя. Значение, не похожее на UUID, разрешается
по списку. Несколько совпадений дают ошибку, а не догадку.

`create_app` и `ensure_app` добавляют к ответу поле `sign-in` – адрес и учётную
запись, которой входят в только что созданное приложение. Запись эта от панели
управления, учётные записи других приложений там не работают, а агент видит один
только JSON. Параметр `verify` у обеих команд дожидается приложения и проверяет,
что оно правда работает на запрошенной сборке: неудачное применение платформа
откатывает молча, а созданное приложение раньше считали готовым на веру. Отчёт
попадает в поле `verify` ответа. Ожидание стоит минут, поэтому такой вызов лучше
запускать фоновой командой `elemctl`.

`version_id`, которого уже нет в перечне сборок проекта, отвергается до создания.
Платформа удаляет сборки, которыми никто не пользуется, и на создание из удалённой
сборки отвечает голым 400. Отказ называет эту причину и сборку, на которой работает
приложение проекта. Проект – `project_id`, а при пустом параметре – `ELEMENT_PROJECT_ID`
стенда.

## Плагины

<!-- plugins:start -->

elemctl подхватывает внешние пакеты через точки расширения `importlib.metadata`.
В своём `pyproject.toml` он о плагинах ничего не объявляет и читает их при
обращении. Так непубликуемые вендорские артефакты живут отдельным пакетом, а ядро
elemctl остаётся чистым и общедоступным.

**`elemctl.debug_adapter`**: пакет-плагин объявляет каталог debug-адаптера
платформы. Это проприетарные jar 1С, в состав elemctl они не входят. Значением
точки расширения бывает путь либо функция без аргументов, возвращающая путь. Путь
указывает на каталог с подкаталогом `repo/`, где и лежат jar-файлы адаптера.

**`elemctl.commands`**: пакет-плагин приносит собственные команды. Значением точки
расширения бывает `Command`, их список либо функция без аргументов, возвращающая
одно из двух. Одного объявления хватает на обе поверхности: elemctl строит по нему
подкоманду CLI и инструмент MCP с настоящей схемой, а о том, что команда делает,
ничего не знает. Там и место команде, которая знает про ваше окружение: внутренние
контуры, смежные системы, ваши стенды. В публичном ядре такой команде жить нельзя.

```toml
# pyproject.toml пакета-плагина
[project.entry-points."elemctl.debug_adapter"]
имя = "мой_пакет:adapter_root"     # () -> Path на каталог, содержащий repo/

[project.entry-points."elemctl.commands"]
имя = "мой_пакет.commands:commands"   # () -> list[Command]
```

```python
# мой_пакет/commands.py
from elemctl.plugins import Argument, Command

def warm_up(context, stand="", force=False):
    context.log(f"прогреваем {stand}")          # прогресс: stderr в CLI, поле log в MCP
    card = context.client.get_app(stand)        # клиент строится при первом обращении
    return {"ok": True, "status": card.get("status")}

def commands():
    return [Command(
        name="warm-up",
        help="открыть админку свежего стенда",
        handler=warm_up,
        arguments=[Argument("--stand", help="приложение"), Argument("--force", type=bool)],
    )]
```

Результат обработчика обязан быть JSON-сериализуемым: CLI его печатает, инструмент
MCP возвращает. Из результата CLI берёт и код возврата. Целое от 0 до 255 в поле
`exit-code` становится кодом возврата как есть, и команда с тремя исходами отдаёт
сценарию "различий нет", "есть различия" и "сбой шага" кодами 0, 1 и 2. Без этого
поля словарь с `"ok": false` завершается кодом 1, по тому же соглашению, что у
отчётов `deploy` и `probe`. Когда поле расходится с `ok`, решает поле. Строку, `true`
или 300 CLI кодом не считает и смотрит на `ok`. Инструмент MCP возвращает поле вместе
с остальным результатом. Вызывать `sys.exit` в обработчике ради кода нельзя: та же
функция работает внутри сервера MCP, где вызов остался бы без ответа, а сервер
остановился бы. Типы аргументов – `str`, `int`, `float` и `bool` для флага. Поле
`env_file` к инструменту MCP добавляет сам elemctl, поэтому команда плагина
дотягивается до других окружений так же, как инструменты ядра. Занять имя, которое
уже есть у ядра, команда не может: это ошибка, а не молчаливая подмена.

Позиционный аргумент может завести синоним-ключ, который действует только в CLI:
`Argument("page", cli_alias="--page")` принимает и `elemctl wiki-get 123`, и
`elemctl wiki-get --page 123`. Схема инструмента MCP от этого не меняется –
у неё как был, так и остаётся один параметр `page`: `cli_alias` меняет только то,
что принимает разборщик CLI, и никак не затрагивает объявленные аргументы. Обе
формы взаимно исключают друг друга: разборщик отказывает и при обеих сразу, и при
отсутствии обеих у обязательного аргумента. Плагин, не объявивший `cli_alias`,
ведёт себя как раньше.

```bash
# путь к адаптеру от установленного плагина (для расширения VS Code):
# {"path": "...", "found": true} либо {"path": null, "found": false}
elemctl debug-adapter

# что приносят плагины - каталоги адаптера и команды
elemctl plugins
```

Сам адаптер, те самые проприетарные jar 1С, достаёт из дистрибутива платформы
скрипт `tools/extract_adapter.py`. Полученный каталог потом указывают вручную в
`xbsl.debug.adapterPath` либо собирают из него пакет-плагин. В дистрибутив пакета
скрипт не входит.

Обнаружение плагинов отключает переменная `ELEMCTL_NO_PLUGINS=1`: тогда работают
только штатные возможности ядра.

## Использование как библиотеки

<!-- library:start -->

```python
from elemctl import Config, ElementClient
from elemctl.deploy import deploy_from_sources

client = ElementClient(Config.from_env())
apps = client.list_apps()

report = deploy_from_sources(
    client,
    app_id="...",
    project_id="...",
    project_dir="acme/crm",
    log=print,
)
assert report.ok, report.problems
```

`list_apps()` отдаёт живые приложения. Удалённые остаются в перечне платформы со
статусом `Deleted`, и на стенде, живущем не первый месяц, их сотни. За полным
перечнем ходят с `include_deleted=True`. `list_apps_counted()` возвращает тот же
список в поле `items` и добавляет счётчики, о которых сообщают CLI и инструмент
MCP: `total`, `live` и `shown`.

Проверить компиляцию, не трогая рабочее приложение, можно тем же циклом, что
выполняет команда `probe`:

```python
from elemctl.probe import probe_project

report = probe_project(client, project_dir="acme/crm", log=print)
for error in report.errors:
    print(f"{error['file']}:{error['line']}:{error['column']} {error['message']}")
assert report.ok, report.messages
```

## Формат сборки

<!-- buildformat:start -->

`.xasm` для приложения и `.xlib` для библиотеки – это ZIP-архив:

```
Assembly.yaml            # манифест: ProjectKind, Vendor, Name, Version, ...
{vendor}/{name}/...      # файлы проекта: .yaml, .xbsl, ресурсы
```

Каталог проекта должен лежать по схеме `{repo}/{vendor}/{name}/Проект.yaml`,
потому что пути в архиве строятся от корня репозитория. Приложение это или
библиотека, говорит поле `ВидПроекта` в `Проект.yaml`. Если приложение ссылается
на библиотеки, исходные проекты которых лежат под тем же корнем репозитория, их
файлы попадают в архив приложения сами, вместе с транзитивными локальными
зависимостями. Библиотека, на которую ссылка есть, а локально её нет, остаётся
внешней зависимостью платформы.

## Ограничения и статус

<!-- limitations:start -->

- Инструмент **неофициальный**, с фирмой "1С" он не связан. Console API может
  меняться без предупреждения.
- elemctl обращается только к документированному Console API v2. Внутренние
  API консоли платформы он не вызывает и не описывает.
- На части конфигураций платформы приложение, созданное по одному
  `--project-id`, получается пустым каркасом без данных проекта. Надёжнее
  создавать его от сборки: `elemctl apps create <имя> --project-id <id>
  --latest-build`. MCP-инструмент `create_app` подставляет последнюю сборку
  сам. После создания идёт `elemctl deploy`.
- Приложение, созданное со статусом `Error`, платформа сопровождает общим
  текстом "Неизвестная ошибка. Обратитесь к администратору". Подробности
  лежат в задаче приложения: файлы, строки и колонки ошибок компиляции.
  `apps create --wait` и `apps ensure` печатают их следом за общим текстом,
  как это давно делают `deploy` и `verify`, так что ходить за причиной в
  журнал сервера не нужно. Статусом `Error` кончается не всякий сбой:
  неудачное применение откатывается на прежнюю сборку, и приложение
  поднимается в статусе `Running`. Поэтому `--wait` заодно проверяет, на
  какой сборке приложение работает на самом деле, и отвечает кодом возврата
  1, когда сборка не та, которую просили. Ключ `--no-verify` возвращает
  простое ожидание.
- Скомпилировать исходники, ничего не создавая на платформе, нельзя:
  компиляция серверная и происходит при применении сборки. Для этого и есть
  `probe`: он подставляет одноразовое приложение вместо рабочего. Один запуск
  стоит столько же времени, сколько создание приложения, то есть минуты.
  Поэтому место ему перед развёртыванием или в CI, а не в цикле "на каждое
  нажатие".
- Проект платформы опознаётся парой `Vendor` + `Name` из манифеста, а не по
  `Ид` из `Проект.yaml`. Сборка, загруженная без ид проекта, попадает в тот
  проект, которому пара уже принадлежит. Второй проект под ту же пару
  платформа отклоняет с 409.
- В только что созданное приложение входят учётной записью панели
  управления. Приложение получает собственный пустой список пользователей,
  вход по логину и паролю у него выключен, а сервис учётных записей не
  подключён. Поэтому учётные записи, которыми входят в другие приложения,
  здесь не работают. Этого не меняют ни подключение чужого списка
  пользователей, ни включение локального входа. `apps create` и `apps ensure`
  говорят это сами: поле `sign-in` в ответе и тот же текст в stderr.
- Удалённые приложения остаются в списке платформы со статусом `Deleted` и
  прежним `id`. На этом `id` команды `apps get` и `deploy` отвечают 404.
  `apps find` и `apps ensure` такие приложения пропускают. Прежний поиск
  возвращает `apps find --include-deleted`.
- Приложение с неопубликованными правками в среде разработки платформа
  удалить не даёт и отвечает HTTP 400 `FAILED_PRECONDITION`. Принудительного
  удаления в Console API нет, остаётся панель управления. elemctl подсказывает
  это в тексте ошибки.
- Если приложение пересоздать, то есть удалить и создать заново, у него
  сменится URL. Внешние настройки, завязанные на адрес, вроде OIDC redirect,
  придётся обновить. "Мягкой" очистки данных приложения в Console API нет, её
  делают в консоли управления.
